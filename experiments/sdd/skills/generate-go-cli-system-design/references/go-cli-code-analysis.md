# Go CLI 代码证据规则

本资料仅替代鸿蒙领域的代码发现规则。继续使用上游系统设计模板、稳定编号、表格依据、增量刷新及完成校验。

- 从 `.go`、`go.mod`、构建入口确定已有程序边界；没有源码的空基线记录“尚无实现”，保留模板所需 MAP，不虚构组件。空基线是新项目的正常起点：如实记录空基线、文档结构完整时，本阶段即为完成，VERDICT 写 `pass=true`；`pass=false` 只用于文档未完成或有问题。
- 从 `main`、命令分派和参数处理确认入口；命令名称及参数仅按实际代码记录。
- 用包与真实职责划分模块，避免按每个文件或每个函数生成架构模块。
- 接口证据包括命令参数、stdin/stdout/stderr、退出状态、文件格式、包公开接口及外部调用。不要把 CLI 命令伪装成 UI 页面。
- 数据与资源包括文件、流、配置、内存状态及依赖；没有数据库、UI、设备交互时标为不适用。
- 正常、错误、重复调用和资源释放行为必须有代码证据；不能从测试答案或目标需求反推既有实现。
- 类型别名、泛型、build tags、cgo 或外部包信息不足时明确记录分析边界，不凭名称猜测语义。
- 跨轮分析以本轮 origin 为基线。PRD 检查仍比较 origin/main 的实际 diff，继承未变更的系统设计结论。

- 每张表逐字沿用模板的表头和列序，不增删、不改名、不重排；后续变更说明书按模板表头逐行比对。模板列名面向网络服务时，按 CLI 事实填写：外部开放 API 目录中，“名称”填命令名，“提供方”填 `SYS-*`，“调用方”填命令行调用者（用户或外部脚本），“协议”填“其他（CLI）”，“精确定义”填命令行签名以及输入、输出（stdout/stderr/文件）和退出状态，“代码入口”填 `path#symbol`。确实无对应事实的单元格填“不适用”，不要为此改表结构。

输出仍落到调用方指定代码根的 `.system-design/`，遵守原模板结构；不得修改业务源码。
