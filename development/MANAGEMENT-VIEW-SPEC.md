# 管理层视图规范（living，v0.2 · 2026-09-30）

> 取代 v0 / v0.1。范围按用户简化：**单任务；1 IR = 1 大任务；多任务以后就是多个
> 不同 id 的 IR，本期不做路由**。目标只有一条：**模型每次操作只读它这次要用的内容；
> 写回只写增量**。不删 IR——IR 是系统状态，不是每轮的阅读材料。

## 1. 系统状态（由代码拥有，完整持久，不进请求）

事件日志（用户原文/回传/能力变更）· IR（task/content/binding/output；id 与 revision 由代码维护，
文本逐字来自用户原文）· 计划（atoms/relations）· 执行台账与授权（allow/deny、stop 立即生效）·
产物登记（path + 代码计算的 digest + 状态）· 审计（每次调用的视图、补取、delta、耗时与 token）。

## 2. 每次调用 = 一个操作，一份视图

| 操作 | 读（展开） | 清单 | 写 | 协议 |
| --- | --- | --- | --- | --- |
| `update_ir` | items：①引用命中 ②最近修订 ③未决 ④上次补取；**Atom 只出现在清单里** | items + atoms 一行一条 | IR delta | ≤2KB |
| `compile_plan` | items：①②④；atoms：②④（要改哪个再补取） | 同上 | plan delta（assignment / 衔接语 / completion / return_when / permissions） | ≤2KB |
| `assess_return` | 被评估的 atom（target）：①④ | 同上 | 评估 + continue/stop/reuse（必要时请求 compile_plan） | ≤2KB |

**离线复算（`.scratch/view-bytes.mjs`，只读两次真实 run 的 journal）**：

| run `…203358`（旧） | 记录请求 | `update_ir` | `compile_plan` | `assess_return` |
| --- | --- | --- | --- | --- |
| seq 1 | 104,752 | 21,360 | 21,360 | 2,050 |
| seq 3 | 248,945 | 29,627 | 29,627 | 24,695 |
| seq 14 | 450,546 | 8,982 | 8,982 | 25,764 |
| seq 17 | 488,073 | 7,836 | 7,836 | 25,764 |

记录请求随轮数增长到 ~488KB；三个操作视图保持在 2–30KB（`assess_return` 大部分是那个被评估的
Atom 正文 18.5KB），且不随轮数增长。`compile_plan`/`update_ir` 相等是因为这些记录里两操作
命中的对象集合相同（都只展开被点名的 items）。

提问不再是独立操作：任何操作都可以只输出 `questions` 而不派发。

**实测对照**（run `…095735`）：现状第 1 轮请求 **105,578 字节**（合同 53,102 + source_segments 30,650 + events 21,333）；
第 2 轮请求 **251,419 字节**（source_segments 86,722 + 合同 53,102 + compiled 28,346 + events 27,378 + ir 25,882 + source_events 21,333 + assessments 5,864）。
同一份状态下，上表的三次操作视图合计约 **59KB**，并且不随轮数线性增长。
响应 schema 从 27KB/次降到 ≤2KB/次。

## 3. 切片规则（单任务，机械、可追溯）

- **清单（永远可见）**：每个 item 一行 `id | revision | status | ≤80字摘要 | 源事件指针`；
  以及每个 atom 一行 `id | revision | 状态 | ≤80字摘要`。可见性 ≠ 阅读量。
- **展开（全文）四类命中**（每类都按 §2 的对象类型过滤）：①本轮文本点名的 id/路径/输出名（含操作 target）；
  ②最近 N=2 轮 revision 变过的对象；③状态为 pending/executing/unresolved/failed 的对象（IR 操作用 items 的未决状态，
  计划操作不因"atom ready"而展开）；④上次调用点名的补取对象。
- **上限**：展开总量 ≤20KB；超限按 ①>②>③ 截断，**被截断的对象仍在清单里并可补取**；
  截断与规则命中逐条进审计。

## 4. 补取（按需）

输出可带 `need: [{ "ref": "item:r-ingest@2" | "turn:7" | "artifact:a3" | "turn:7@4096-8192", "why": "…" }]`；
代码解析（必须在清单/事件日志/产物登记里存在）→ 追加 `retrieved` 段 → **重发一次**；
第二次输出不得再带 `need`（再带则接受答案、记录未满足的 need）。
上限：≤8 条/次、单条 ≤4KB、一次 ≤12KB、1 轮/调用。**目标补取率 <20%**（超过说明默认切片该改，而不是把 K 加大）。

## 5. 写回（增量）

- 输出 = 本次触达对象的 delta（`ir_delta` / `plan_delta` / `decisions` / `note` / `questions` / `need`）；
  **未触达对象不回传**；revise 带 `expected_revision`；
- 越界写检查（形状）：任何未声明对象的 revision 发生变化 → 拒绝并计数（目标恒为 0）；
- 冲突/失败：只针对那一个对象发差量修复请求；只重试失败的那一次操作；两次失败记为未决并提问。
  **不存在"整批拒绝、整轮无派发"**。

## 6. 分工（消掉"抄写丢细节"这一族失败）

- **atom 的规范正文由代码拼装**：用 `materializeSourceContent` 同款逻辑，从 assignment 选中的 IR items
  逐字拼接；模型不抄规范长文。
- 模型写：哪些 item 归到哪个执行单元、顺序/依赖、衔接语、`completion`、`return_when`、`permissions`、`note`。
- `compile_plan` **不得写 IR**：发现 IR 不足 → 返回 `blocked:{reason}`，代码带 reason 再发一次
  `update_ir`（同一轮 ≤1 次回流；再 blocked 记为未决并提问）。

## 7. 机械检查（只判形状，作用域 = 本次 delta）

schema 合法；revise 的 id 存在且 revision 匹配；引用只允许指向清单里存在的 id；
permissions 的 operation ∈ 宿主能力、path 在 workspace 内；note ≤4KB；越界写拒绝。
没有逐段来源账目、没有 goal_refs/digest 组装、没有 parent_basis 循环、没有整候选覆盖率；
可选核对按操作定点、findings 建议性（进记录与下一轮输入）。

## 8. 刻意简化清单（以及什么时候说明简化过头）

| 简化 | 为什么现在可以 | 观察指标（说明过头就回退/加强） |
| --- | --- | --- |
| 单任务，无路由 | 单任务还没跑明白；多任务=多个 IR | —（本期不做） |
| 清单摘要由代码截取 | 可见性由清单保证，细节可补取 | 补取率 >20% |
| 固定切片规则（四类命中） | 机械可追溯、可测量 | 轮次分数与"截断对象"负相关 |
| delta 只写触达对象 | 形状检查可强制 | 越界写尝试 >0 |
| atom 规范由代码拼装 | 逐字一致可断言 | 若拼装文本与用户语义不符（举例：缺标题/定义），再讨论是否让模型参与选段 |
| 一次补取 | 控制成本 | 未满足 need 的比例 |

## 9. 第一步实现（离线可验证，不动付费 run）

1. `core/view.ts`（纯函数）：清单 + 切片 + 补取解析；单测断言"请求里的对象 ⊆ 清单∪展开∪补取"、
   每次调用字节 ≤ 上限、展开逐条可追溯到四类规则之一；
2. delta applier：只改声明对象 + `expected_revision`；越界写、revision 冲突的单对象修复路径单测；
3. 离线复算：用 run `…203358`（旧）与 `…095735`（新）的 journal，按每轮真实状态计算三次操作的视图字节，
   断言不随轮数增长（这是一个纯离线脚本，不调用模型）；
4. 适配器加第三臂 `scoped` 的接线（先不跑真实 run）。

## 10. 现在不做
