# 提案的代码边界自查（2026-09-24）

**为什么要这张表。** 用户问"这一轮的提案里代码边界清楚吗"。项目已经有过一次教训（阶段 3 自创规则、r11d 过严规则）：**一条"该由代码判"的提案，如果说不清谁写、谁读、判在哪一层、违反会怎样，落成代码时就会长出一道没人要求过的规则，或者一个改不动的字段。** 所以每个要落代码的提案，先按同一张清单自查。

## 1. 每个提案必须能回答的八个问题

1. **谁写**：这个数据/判定由谁产生（哪个函数在哪一层）。
2. **谁读**：谁消费它（模型输入 / 机械门槛 / 独立核对 / 执行层 / 审计报告）。
3. **在哪一层判**：机械门槛、核对、执行层、还是只记录不判。
4. **判什么**：判定条件的精确定义（能写出夹具的那种精度）。
5. **违反会怎样**：拒绝（可修订还是终止）、改写、还是只记录；**下一步做什么**（重排队？保持禁止开始？）。
6. **旧数据怎么办**：已有 store / 存档候选撞上这条新判定时是红还是跳过。
7. **两份 schema 要不要同步**：发给 provider 的 strict schema 与校验答案的 canonical schema（r11c 就是这两份不同步）。
8. **明确不做什么**：这条不负责什么，避免下一个人往里加东西。

## 3. 五处会做出错误行为的地方

1. **P4 的分支**：如果 `consistent + findings 非空` 走"基础设施失败"，那么 provider 多说一句多余的话就能让整批作废，而且**不重提议**——正是 r11c 的形态。**决定：走"语义拒绝"分支**（把 findings 当作拒绝理由，在批预算内修订）。理由：形状合法、内容自相矛盾，属于核对员的判断，不是契约不匹配。
2. **P5 的位置**：`advance` 现在是**先把事件取走再组装请求**。在组装之后才量输入大小，超限时两条路都错：不重排队 = 事件丢了；重排队 = 下一批的请求只会更大（还要带上上一批的拒绝理由），确定性死循环。**决定：把这一条挪到取事件之前**——先量待处理事件的大小，超限就不取、不花批预算、记一次失败，事件留在待处理队列里，等宿主缩小输入。这条同时回答了"失败码"：与预算类失败同一形状。
3. **P10 与 D2 的冲突**："不许连续纯提问"要判"上一批问的还没有被回答"，而 D2 决定 v1 不追踪"已回答"，所以这条规则**判不准**。**决定：降级**——门槛只保留"提问批必须附一条 coverage 说明为什么现在做不了"（可判、不依赖追踪）；"连续纯提问"改成 `audit-report` 的一行观察，不作为门槛。理由与 §6.3 一致：不为没发生的形态预埋闸门；同时它把"连续提问"的代价交给预算本身（每次提问都要花一次提议，预算有限，run 会可见地结束）。
4. **P1 的边界**：`goal_refs` / `intent_basis` 现在写的是"输入里给过的 ref"。本批**新建**的原子（draft 里的 `a1`）是不是"给过"？说不清的话，校验要么形同虚设要么误伤。**决定：不接受本批新建的原子**——本批内的指认已经有一条路（coverage 用 `{local_ref}`），两类引用不混。这条要写进合同。
5. **P2 与 P12 是同一个问题的一半**：源引用不可解析既可能是"模型抄错"（该拒），也可能是"旧 store 的口径不同"（该跳）。两条提案各自处理了摘要/引用，但**没有一条说"旧 store 上这两条新判定怎么表现"**。**决定：合成一条**——凡新判定遇到"这一侧是旧口径写下的值"，一律**标不可比 + 记录 + 不阻断**；只有两侧都是当前口径时才判。

## 4. 仍然开放（需要数据或需要你表态）

- **P3 的 schema 双份**：要不要顺手把已有的防漂移测试从 `findings` 扩到整个候选 schema（现在只比对 check schema 的 findings 部分）。
- **P7（适配器路径解析）**：现在还只是"要做"，不是"知道怎么做"。它是安全项，建议**先只读调查**：看 OpenCode 的工具调用链上哪一层能拿到解析后的真实目标，拿不到就明确 `unsupported`（`CURRENT-DESIGN` §3.8 已经允许这个结论）。
- **P9 的字段形状**：放进请求的哪一层（与 `previous_rejection` 并列）、上限多少，等 `to-tickets` 时和 T05（增量形状）一起定。

## 5. 结论

按这张清单，本轮 13 个提案里：**2 个清楚、8 个缺 1–3 项、1 个缺 4 项、2 个有会做错的地方**（第 3 节已给出改正）。缺的部分都是**落码前必须补的**，不是"实现细节"：它们决定这条规则会不会误伤、会不会丢事件、会不会和旧数据打架。**建议：进 `to-tickets` 时把上面八个问题做成工单模板的一部分**——答不全的工单不许开工。
