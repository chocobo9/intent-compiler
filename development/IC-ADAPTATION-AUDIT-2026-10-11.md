# IC→SDD 适配审计（2026-10-11）

- **目的**：逐项审视冻结版 IC 之后为适配 SDD 加入的全部机制，判断哪些是必要适配，哪些是能力增强，哪些是应收回或通用化的局部补丁。
- **实验目标**：最终 verifier 分数满足 IC+SDD > SDD。
- **范围**：`src/core/sdd-*.ts`、`src/model/sdd-model.ts`、`src/adapters/sdd.ts`、`src/cli/sdd.ts`、`experiments/sdd/ic_bridge.py`、`run_ic_series.py`、`example_runner.py`。
- **方法**：本审计只读，不改代码。

## 1. 初版 IC 原有、在 SDD 模式下保留的能力

| 能力 | 现状 |
|---|---|
| IR 生成（V2 合同、指令） | 设计与指令未改；在模型输出之后加了一层代码规范化（见 §3） |
| 删除作废原文 | 保留，由代码执行，并记录 `removed` |
| 有效表述（被后续输入修改的需求，写明现在的要求） | 保留，由代码把关（见 §3） |
| check（独立核对交付） | 保留，增加分级（见 §3） |
| reopen、previous_voided | 保留 |

## 2. 收缩时删除、尚未恢复的能力

| 能力 | 删除理由（当时） | 建议 |
|---|---|---|
| 按条目重组原文 | 重组后原文结构被打乱：R1 原有 8 个小节标题，重组后只剩 1 个 | 不在原文上恢复。如需完整的功能清单，可作为附加视图（按 IR 条目列出），原文保持逐字 |
| change_summary | 未证明对 SDD 有效 | **已由"本轮变更清单"恢复**（v3），由代码核对每项对应 IR 变化 |
| input/output ids | 曾导致整批失败；对 SDD 无用 | 不恢复，SDD 不消费这类 id |
| 上一轮 PRD 作基线 | 真实运行中从未触发过 | 不恢复；"本轮变更清单"承担同一目的（让 SDD 聚焦本轮变化） |

这一节是"功能不退化"原则下唯一的缺口，由用户决定是否恢复"按条目重组"的附加视图。

## 3. 为适配 SDD 新增或加强的机制

### 3.1 必要适配（让 IC 在 SDD 上稳定、正确地运行）

| 机制 | 解决的已观察问题 | 判断 |
|---|---|---|
| 交付体 = 累积原文逐字 + 删除 + 有效表述 | SDD 只读节点 1；原文丢失会直接失分 | 保留 |
| 有效表述由代码把关（只允许确有多次输入的条目写；拒收与原文重复的文本） | R2/R3 把整份需求照抄了一遍（各约 4.4 万字符） | 保留 |
| 增量沿用（字段、示例、验收主题，按条目修订号沿用） | R3 每轮全量重写，48 次调用仍不收敛 | 保留；**需按根因 1 补齐**：条目有原文被删时也视为已修订（在下一批中） |
| check 分级（只有编造、已作废、与原文矛盾、删错四类 blocking） | 小问题导致整份退回、无法收敛 | 保留 |
| 返修带上一版草稿（last_draft/previous_draft），只改被指出处 | 返修时整份重写，修一处坏一处 | 保留 |
| IR 形状规范化（只修有唯一映射的形状错误，再走原有完整校验） | IR 格式失败约占 IR 调用的 60%；离线 56 个失败答案中 18 个修复后通过，无语义错误 | 保留 |
| 请求瘦身（CI/check 只附相关原文段落；`referenced_objects` 用占位符） | check 请求在 R4 达 17.5 万字符 | 保留 |
| 管理预算 15、用完即停 | 夜间曾逐次追加额度硬推 | 保留 |
| SDD 结果回传 `prd_check`（排除 CODE_ONLY） | 回传了不该当成需求的差异 | 保留 |

### 3.2 能力增强（IC 作为管理层的价值，针对已验证的 SDD 缺陷）

| 机制 | 针对的问题（证据） | 判断 |
|---|---|---|
| 字段表（按 PRD 模板"接口与数据"的格式）+ 代码核对字段名出自原文 | PRD 按功能粒度编写，参数名丢失（同一 R1 的 6 份 PRD 中 `condition` 出现 0 次）；加入后 3/3 份 PRD 保留了参数名 | 保留。形式贴合 SDD 的 PRD 模板，报告中说明 |
| 验收示例（期望值只取原文给出的值，参数名由代码核对） | 让参数名和固定文本进入 PRD 的验收标准 | 保留 |
| 本轮变更清单（v3） | R3/R4 新增操作和行为修正在 PRD 之后丢失（resample、watermark、crossjoin、checkpoint，以及 fill/zscore 修正） | 保留，正在 v3 中验证 |
| 可执行示例 + 失败账本（v3 只记录） | SDD 轮间只靠代码衔接，rollup 14 轮、resample 13 轮未修 | 保留。**反馈给 SDD 前必须通过留出验证**（上次留出：真检出 3，误报 34） |

### 3.3 应收回或通用化的局部补丁

| 机制 | 来源 | 问题 | 建议 |
|---|---|---|---|
| `completeFields` 把原文中所有 JSON 键和 `--opt` 追加到 "Other names" 一节 | 夜间 R3 修补 | 只有名字、没有含义和归属，增加 SDD 输入的体量；与增量沿用、字段表的职责重叠 | 改为只追加"本轮新增或修订条目"中出现、且字段表未覆盖的名字；或在验证后去掉，由字段表负责 |
| 编造字段的报错里提示对应的 `--option` | 夜间 R3 修补 | 只针对一种情形 | 通用化为"报错列出原文中最接近的名字" |
| changes 改为可选、缺失时由代码补项 | 回放 R4 连续 4 次漏写 | R3/R4 模型都没给 changes，等于"旧规则 → 新规则"这部分基本由代码补齐、内容变弱 | 查明漏写原因（schema 位置或指令），让模型稳定给出；代码补项保留作兜底 |
| 示例阶段在 v3 中每轮额外 2 次调用，但账本不反馈 | 留出验证未达标 | 有成本、暂时没有收益 | 接受（为留出验证积累真实数据），在 v4 打开反馈 |

## 4. Harness（实验控制器）

| 机制 | 判断 |
|---|---|
| 晋级规则：构建和测试通过即保留代码（`auto_keep_build_pass`），SpecArt/PRD 检查只记录 | 保留（用户规则，只看 verifier） |
| 每轮最多 2 次尝试、保留较好的一次（keep_better + adopt） | 在新规则下作废已很少，作用下降 |
| <90% 暂停诊断 | 今晚关闭；无人值守时会让串行停到天亮 |
| 回退与 adopt（v2 R5） | 能用但脆弱：回退时遗漏 host 请求文件导致 EEXIST。教训已记录 |
| `--keep-ic`（续跑时沿用冻结的 IC 构建，只替换 harness） | 保留；防止把未测试的代码带进运行中的串行 |
| 卡死看门狗（45 分钟无输出就终止该次请求）、防睡眠 | 今晚开到次日 12:00 |

## 5. 结论

1. **初版 IC 的核心能力全部保留**；收缩时删除的 4 项中，change_summary 已恢复，其余 3 项建议不恢复，"按条目重组"可作为附加视图由用户决定。
2. **夜间局部修补中，有 2 项应通用化或收回**：`completeFields` 的 "Other names" 一节、编造字段报错里的 `--option` 提示。另有 changes 漏写的原因需要查明。这几项并入下一批统一处理，不在运行中的串行里改。
3. **对分数影响最大的两项**是本轮变更清单（v3，正在验证）和带反馈的失败账本（v4，留出验证通过后从 v3 分叉）。
4. **今晚优先保证两条串行稳定跑到 R15**。
