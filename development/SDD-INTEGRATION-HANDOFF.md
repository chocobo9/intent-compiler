## 3 为什么做这次融合

IC 初版把原始材料作为用户输入，这是原设计，不是要修复的接入错误。它维护历史输入和 IR，再产生 CI，最终把选入的原文和执行合同装入 Atom，交给 OpenCode 执行。

初版的实际语义理解和编译能力有限。在已完成的长链路中，一个持续修订的 Atom 往往包含全任务要求、大量原文和分类信息，又承担实施、验证和回传约束。用户认为这里发生了职责偏移，Atom 与预期 CI 的职责重叠，和 SDD 的开发编排也产生冲突。

SDD 已有自己的需求澄清、设计、源码规格、实现、验证及修复流程。用户希望使用 SDD 的完整适用能力，由 IC 在更上层持续管理需求、组织交付内容、理解回传。不能通过删掉 SpecArt 或绕过设计验证来快速做出一个名为 SDD 的执行器。

用户的“优先减法”是：尽量复用现有逻辑，移除 IC 带来的重复职责。不是把 IC 退化为一次性文本预处理，也不是再加一个模型转换器把完整 Atom 翻译给 SDD。

目标是让 IC 加 SDD 的表现优于 SDD only，但这属于待验证目标。不能按官方测试答案补写需求、写 dpipe 专用规则、修改 verifier 或选择性丢弃失败结果来实现分数提升。

## 4 已确认的设计决策

### 4.1 Atom 的需求交付职责融入 CI

本次不优先开发“多个 Atom 各自映射到 Spec”的适配层。CI 表达一次管理交付，可以组织多个主题、要求、业务依赖及未解决事项；它不需要内部再维护多个独立执行对象。

这不是在模型输出后写 `atoms[0]`，也不是规定模型必须只生成一个 Atom。实施要调整职责和消费者，使新接入路径不再依赖 Atom 数量。已有多 Atom 历史记录不作为新实验起点，不需要为了融合先迁移全部历史数据。

| 信息或动作 | 融合后的职责 |
| --- | --- |
| 原始输入、来源、适用更新、要求范围 | IC 的 IR 维护 |
| 本次交付哪些要求、如何组织、哪些暂停或未解决 | CI 表达 |
| 原 Atom 中的需求正文、交付目标、用户规定的验收条件 | 融入 CI，复用来源装配逻辑 |
| 原 Atom 的工具权限、不可委派声明、执行前提、重试及后继派发 | 从新接入路径退出 |
| 任务拆分、源码规格、角色协作、实现、验证和内部修复 | SDD 负责 |
| 交付版本、实际运行、结果证据、需求层评估 | IC 保留管理记录，与 SDD 结果关联 |

“移除执行前提”不是删除用户规定的业务条件。例如“只有校验通过才能写出结果”是需求，必须保留；“先执行 Atom A，结束后再派发 Atom B”是 IC 的执行编排，应退出。不要按关键词机械删除，两者需要按含义区分。

同理，用户规定的验收条件需要交给 SDD；模型自行安排的工具调用或开发步骤不应再作为独立执行合同。当前正文把二者混在自然语言里，单纯删掉 JSON 的 authority 字段不能完成职责调整。

### 4.2 保留内容选取 不顺手修复初版语义

coverage 当前决定原文进入哪个 Atom，代码据此装配正文和 goal_refs。它不是只供展示的标签。融合后保留选取和处置的语义，取消独立 Atom 的目的地依赖。

不要为了省事交付全部 IR 或全部历史原文；这样会改变 B 组实际采用的内容。也不要手工补回被 IC 归为 context 的示例、补齐某个官方测试期待的字段或顺手优化覆盖解释漂移。初版的这些问题正是需要被测量的对象。

原文继续保留和随行，不代表旧要求每轮都要重新执行或重新验收。后续明确修改的要求按更新处理，其余要求继续有效。代码负责来源、顺序、身份和装配，不能把文本先后自动等同于语义覆盖。

### 4.3 SDD 内部统一调度

一次用户更新最多触发一次新的 SDD 工作流启动；如果管理判断没有获准交付的内容，可以不启动，但必须记录原因。SDD 工作流内部仍可按双方相同的预算完成修复和角色协作。

IC 收到结果后记录并评估，不因 not_satisfied、未完成回传、计划替换或后继解锁再启动第二轮 SDD。若保留技术重试，必须区分恢复同一次启动与新增开发执行，不能重复创建工作流。

这是本次比较的调度边界；“最多一次”的操作定义及恢复机制需要在最终合同中落实，不能仅在提示词里要求。

## 5 两组实验如何共用底座

| 项目 | A 组 SDD only | B 组 IC 加 SDD |
| --- | --- | --- |
| 每轮需求入口 | 按顺序累计的原始用户输入，标清本轮更新 | IC 实际选取、组织后的 CI 内容 |
| 需求进入后 | 进入共同 SDD 流程 | 进入同一个 SDD 流程 |
| 代码延续 | 本组上一轮代码 | 本组上一轮代码 |
| 历史设计与报告 | 使用共同的保留和失效规则 | 使用相同规则 |
| SDD 模型、角色、构建与修复预算 | 固定配置 | 相同配置 |
| 官方评测 | 相同轮次、同一官方流程 | 相同轮次、同一官方流程 |

A 组不是只给当轮输入的弱基线。B 组也不能在工作区额外放一个未经过 IC 选择的 TASK_SPEC.md，使 SDD 能绕过 CI 去读原文。IC 管理层可以读取历史原文，SDD 只能看到 B 组正式交付的内容及允许的项目历史。

两组必须使用相同初始项目、依赖环境和逐轮输入序列，代码和管理状态各自隔离。每轮记录实际使用的代码基线、需求输入摘要、SDD 配置及报告。失败、阻塞和中断也保留，不换一个工作区继续后宣称同一条连续运行。

建议每轮新建独立的 SDD PRD ID，并将本组上一轮代码作为输入仓库。原因是当前 SDD 会复用已有运行目录中的需求文件和代码副本；仅修改外部输入并加 strict-stale 未必生效。历史设计产物不是全部盲拷：SpecArt 验收记录有路径和内容关联，新一轮必须判断哪些作为背景、哪些需要重新验收。具体目录布局和复制规则尚待定稿。

正式评测使用 dpipe 官方逐轮机制。SDD 内部自行生成的测试可以作为开发证据，不能代替官方评分。官方用例和答案不用于事先补写 CI。是否有官方允许的反馈以及如何进入下一轮，必须按官方宿主实际行为核清，不能自建反馈捷径。

结果至少分别报告逐轮 reward、官方通过数及失败数、回归现象、完整链路结果、IC 管理调用与 token、SDD 执行调用与 token、墙钟时间。成本未知应标未知。正式重复次数、模型标识、超时和预算仍未获授权，不要自行启动。

## 6 回传需要怎样闭合

以下是行为合同，不是已经确定的新 TypeScript 字段定义。

1. IC 接受用户更新，维护 IR 并形成获准交付的 CI。保存确定的 CI 身份、版本和内容摘要。
2. 宿主为这次交付关联一次 SDD 运行。运行开始后的输入身份固定；后续 CI 修订不能冒充这次运行的输入。
3. SDD 执行自身工作流，保存设计、实现、验证及内部修复证据。
4. 宿主返回真实运行状态、产物和证据，并关联到实际执行的 CI 版本。
5. IC 记录结果和需求层评估，处理完回传事件；不留下一个等待 Atom 派发的队列继续驱动 SDD。
6. 下一轮用户更新读取既有结果继续管理。先前失败仍是失败记录，不能为了清空 pending 假报 completed。

必须区分三件事：SDD 流程结束、SDD 自身验证结论、IC 对要求满足程度的判断。流程结束不代表全部要求满足；一个局部 satisfied 也不能把整个任务所有要求标为完成。

尚需明确的异常行为：同一回传重复送达、进程在启动前后崩溃、旧 CI 的迟到回传、实际无代码变更、SDD 阻塞、管理回传处理失败。优先复用事件身份和持久化能力。无证据确认启动是否发生时，不能默认启动第二次。

一个易漏的反向写入：registrationChanges 会根据 Atom outputs/inputs 登记 IR outputs/bindings。融入 CI 时要确认产物声明如何保留，不能删掉 Atom 数组后顺带让产物和材料登记消失，也不应为每轮同一产物无意义新建身份。

另一个易漏的状态行为：recordExecutionOutcome 当前将 completed 映射为 completed，failed 映射为 failed，其余映射回 ready。新接入路径必须取消“阻塞或中断自然回到可再次派发”的含义。

### 8.3 HarmonyOS 假设和测试阶段

prdcheck 的 generate-harmonyos-system-design 技能包含 Ability、hvigor 等专用假设；测试规划面向 UI、设备和应用配置。要给 CLI 项目准备两组共同的适用配置，保留系统设计与验证职责，不能把 UI 步骤机械套在 CLI 上。

主脚本的 run_stage 对 testgen、testfix 当前直接输出 skip。需核清哪些验证由 SpecArt 已完成，哪些是被跳过的设备测试职责，以及 CLI 场景怎样承接必要验证。官方 dpipe 评分独立存在，不能因此省略 SDD 自身的验证流程。

SDD 的 passed 有些位置只保证产物存在；不能仅凭它宣称独立规格门禁通过。验收要查看真实设计接受记录、实现验证报告和构建结果。

## 9 实施顺序与完成标准

### 阶段一 完成设计并请求代码授权

先解决第 10 节未决项，形成具体文件和行为清单。提交授权时明确区分 IC 改动、外部共同配置、SDD 源码改动、离线验证、真实模型运行与官方评测。Go/CLI 共同底座已获后续授权并实施，其他未决合同继续保留。

### 阶段二 在授权范围内建立共同底座

先让两组共用同一 SDD 入口、项目延续规则和验证能力。完成标准不是 dpipe 高分，而是输入和代码基线正确、SpecArt 必要门禁真实运行、最终代码落到官方宿主期望的位置、结果可以追溯。不得为了让 B 组更强而只为 B 组增加 SDD 修复预算。

### 阶段三 改造 IC 交付与回传

按核心合同、装配与存储、消费者、OpenCode 宿主的顺序统一修改。不要只做一个抽取 atom.task 的外壳后保留全部旧调度。优先复用原有能力，不新增额外模型转换调用，不将下一版 IC 的语义优化一起合入。

### 阶段四 离线行为验证

以下是后续获得测试授权后的验证要求，本次不执行：

- 连续两轮更新后，未修改要求仍有效；被明确修改的部分可追溯到对应原文。
- 已选内容进入 CI，paused/unresolved 仍可追踪，未选 context 不被偷偷补回。
- 多主题要求可以交给同一次 SDD 流程，不因主题数产生额外开发运行。
- 同一回传重复送达不重复记账或再启动 SDD；迟到回传不会覆盖新 CI 的状态。
- failed、blocked、stopped 均记录真实结果，不变成旧 Atom ready 队列。
- SDD 子角色调用不递归触发 IC 编译或被旧 Atom 委派条款阻断。
- SDD 运行引用正确 CI 版本，管理评估不把局部成功提升为全任务成功。
- A/B 工作区与配置隔离正确，B 组执行侧无未交付原文旁路。
- 官方宿主得到正确代码产物和逐轮证据，统计不把未知成本记为零。

优先针对这些可观察行为验证；不要只为字段改名添加镜像测试。已有相关测试入口见 development/README.md。旧测试若约束已退出的职责，应说明删除或调整理由。

### 阶段五 获运行授权后正式比较

先冻结 IC、SDD、共同配置和测评版本，记录工作区差异，再按批准的预算运行。运行中发现缺陷，保留失败记录；代码修复和重新实验另记版本，不把不同版本拼成一条“完整成功”链路。

## 11 历史证据应怎样使用

最近完整链路 `intent-luna-dpipe-full-20261006-114022-53ca6c06` 冻结版本为 b8d0e46。R1 至 R15 全程单 Atom、无 Relation，16 个 Atom 版本、18 次执行。R15 task 约 101133 字符，原文附件前的执行指令约 1629 字符。它说明该链路的主要交付内容是原文，不说明当前代码默认必然单 Atom。

同一链路相邻 CI replace 批次中，355 对 coverage 的要求完整引用、处置和目标 Atom ID 均未变，其中 354 对 explanation 改写。比较目标使用 Atom ID，不是断言 Atom 版本不变。此现象支持重复表达的判断，不证明模型没有进行任何语义判断。

早期运行曾出现 4 或 5 个 Atom，但未形成同等完整的多 Atom 长链路。当前生成指令明确不强制固定 Atom 数。选择融合 CI 的主要理由是职责重叠，而不是对生成数量作统计假定。

原文和 snapshots 的定位入口在 dpipe README；不要把历史运行的 b8d0e46 与当前 ccf37ec 混同，也不要为重新证明这些历史事实启动模型。保存原文不等于原文每次都被执行或充分复核。

`delegation: not_supported` 已证实是 schema 和生成合同约束；目前没有证据证明该字段本身就是禁止子角色的运行时开关。逐工具授权和实际宿主行为应分别核查。
