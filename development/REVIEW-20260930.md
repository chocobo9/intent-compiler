## 2. 结构性诊断

1. **仪器错了。** dpipe 是"真实代码库上持续加功能"，每轮题面自足，解释权在题面，
   正是通用编码 agent 的强项（证据：只要派发成功，R1 219/219、旧 R2 480/481）。
   本项目声称的价值——跨轮演化的意图、修正/撤回、共同要求的作用范围——在这个 benchmark 里几乎不存在。
2. **修复方向负边际。** 176 条条款 / 58 条机械强制 / §13 约 28 批修复；
   每修好一道门，失败就推到下一道门（来源→账目→goal_refs→parent_issues→预算）。
   系统越"严密"，可拒绝工作的面越大；它拦的是**表述**，不是**工程**。
3. **反事实从未测过。** 项目要证明的是"显式 IR 维护 > 直接拿完整历史"；至今没有裸 agent 对照结果。
   我们只知道：执行器很强；管理层的门很爱拒。

    —— **别名域 = journal 事件 = 可解析来源域**，一一对应；`availableSources` 是它的子集。
  - 现实数据：36 个已记录 store，sequence 在每个 run 内唯一、从 1 连续、无重复；event_id 同样唯一。
  - 模型侧已有先例：`carried_delegations[].sequence` 本来就是事件 sequence，别名沿用同一个概念。
- **已知缺口（唯一）**：`readEvents()` 对无法解析的行"保留但不入内存"，此时 `nextSequence()` 的
  max 会忽略该行，理论上可复用其编号，使 `e{k}` 指向另一事件。全 id 方案没有这条路径
  （写错就是 `source_unknown`）。缓解：把事件 sequence 水位写进 snapshot，`nextSequence` 取
  `max(文件, 水位)+1`；或明确接受"journal 损坏属既有数据损坏路径"。待定。
- **允许支持的范围**：同一 run 内、journal 未损坏时，`e{sequence}` 是唯一、不可变、与来源域一一
  对应的别名，可安全用作请求/响应/反馈的统一事件身份；其稳定性不依赖请求内顺序。

### 11.2 复审补漏：坏行属于待处理事件本身（2026-09-30，提交 `3d611ca`）

- **复审提出的场景**：唯一待处理委托对应的 journal 行被破坏时，`popPending()` 会不会先移除 pending，
  然后因 `events=[]` 提前返回，根本走不到 `storage_unverified`。
- **核实（读代码 + 测试复现）**：会。`popPending()` 的 `pendingEvents()` 用 `readEvents().find(id)`
  取正文，坏行被跳过 → 映射为 `undefined` → 被 filter 掉 → `batch=[]` → `popped` 为空，
  **pending id 不会被移除**，但 `advance()` 在旧的检查位置之前就以 `ok:true, unchanged` 返回。
  即：指令不会丢，但会永久静默停住，且不报存储问题。新增用例先复现了这一点。
- **修复**：journal 的 malformed 检查移到 `popPending()` 之后、`unchanged` 提前返回之前，并在任何
  journal 派生工作与模型调用之前；strict 流程下 malformed>0 一律
  `storage_unverified`（requeue 已弹出的事件，不可重试）。范围因此从"会跑 IR 阶段的批次"
  扩到"strict 流程的每个批次"——因为队列本身由 journal 派生，回传评估批次同样会被坏行影响。
  非 strict（legacy）路径不变。
- **验证**：新用例（破坏唯一排队事件的 journal 行）断言 `ok:false`、`storage_unverified`、
  消息含坏行数、**零模型调用**、`pending_event_ids` 仍为 `["input-event-id"]`；
  连同既有的"追加坏行/3 条结构坏行/digest 冲突"用例。`npm test`：457 项 456 通过 1 跳过 0 失败。
