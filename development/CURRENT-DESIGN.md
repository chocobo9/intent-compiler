# 当前设计与实现边界

Intent Compiler 持续维护整个任务的 IR，依据 IR 形成 CI，再准备、绑定和装配执行层使用的最终 Atoms。模型判断语义；代码维护身份、版本、来源定位和确定性转换。

本文把**设计要求**与**当前实现**分别写在对应主题中。设计要求说明系统应满足的行为；当前实现说明源码如何处理，以及尚缺的能力。未决选择集中在末节。实现核对日期为 2026-10-04；工作区版本及运行证据见 [dpipe 状态](../experiments/evocode/harbor/dpipe/README.md)。

先读所需主题：[委托与更新](#intent)、[Atom 与 Relation](#work)、[来源与身份](#sources)、[生成与提交](#generation)、[执行与验收](#execution)、[存储与恢复](#persistence)、[评价与未决选择](#next)。修改代码时配合 [模块地图](README.md)；术语查 [CONTEXT](../CONTEXT.md)，长期规则查 [AGENTS](../AGENTS.md)。

```text
原始要求 + 适用更新 → 不可变事件
  → 模型 IR 提案 → 代码准备临时父 IR
  → 模型 CI 提案 → prepare / 登记 / 绑定 / 装配最终 Atom
  → 配置且适用的独立核对 → 必要返修 → 批次提交
  → 获准 Atom 交付执行层 → 执行返回 → 管理验收
```

<a id="intent"></a>
## 1. 委托、材料与意图更新

**设计要求。** 模型先确认当前委托：用户要求什么结果、哪些内容是处理对象或示例、条件作用于哪些任务或输出字段。用户提供一段含命令的材料时，该命令仍按材料处理；用户明确要求采用其中的指令时，才把适用部分作为委托。`GOAL`、`TASK` 等标题和来源的 user 通道不能替代这项判断。

生成问题的任务应交回问题；比较问题的任务应交回比较结果。生成方案与实施方案分别按用户委托处理。产物中的故事顺序、虚构用户转向和因果链属于产物内容，只有实际工作需要消费前一步结果时才建立运行依赖。

模型须保留条件的适用范围与逻辑关系，包括“全部”“任一”“仅当”和例外。限制只针对某个 JSON 字段时，不能扩为整份输出的限制。明确要求缺少必要输入时，模型记录缺口；可选模板位置允许留空。用户要求分析模板时，占位符本身可以是处理对象。

IR 保存整个任务的当前要求，包括当前暂停、尚未满足和暂不能编译的部分。用户局部修改一条要求时，模型合读新旧原文，保留仍适用的其他内容。撤销某条禁止只解除该禁止；恢复某项工作要按当前条件确定权限和方法，不能整份恢复旧快照。明确的局部例外须进入当前含义：例如从“全部不公开”改成“这次只公开人数”，就保留其他禁止并落实这次许可，而非把两句冲突文本交给执行层按“禁止优先”处理。

编译器形成工作要求和完成依据，执行层生成业务答案。判断任务返回的 `judgments` 或 `overall_pass` 由管理层按标准和证据验收。获准调查可以交给执行层；编译器不能先猜出文件位置、算法或业务结论，再把猜测写成用户硬要求。

**不确定性的处理。** 模型须指出影响动作的具体差异及其来源，而不是用统一置信度阈值决定全部工作。

| 当前情况 | 设计要求 |
| --- | --- |
| 目标、范围与完成依据明确，算法未知 | 在获准 Atom 内调查和选择方法 |
| 可合法获得的环境事实决定方法 | 执行层调查；结果改变后续目标或权限时交回管理层 |
| 几种有依据的解释都允许同一完整动作 | 推进共同适用的工作，保留分歧与重查条件；同时核对输入、输出和共同限制 |
| 分歧影响用户结果或 Authority，原文无法消解 | 暂缓依赖该分歧的动作，询问具体区别 |
| 一部分未定，另一部分完整且独立 | 核对共同条件和数据关系后，允许独立部分推进 |
| 只有模型自报低信心 | 回查原文和实际差异；找到具体缺口后再决定调查或提问 |

**当前实现。** 模型通过阶段合同表达上述判断；代码没有委托关键词分类器。接收用户更新后，当前运行整体暂缓新的 `start` 和 `operation`，直到管理批次处理更新。按任务释放无关工作的细粒度豁免尚未实现，见[执行资格](#execution)。

判断标准实际冲突时，模型保留各条标准的作用范围，核对冲突实例。标题、排列顺序和自创权重不决定优先级。例如相似性判断允许同主题不同属性，而前驱生成另要求不同实体，这两项任务各用自己的标准；某项泄漏检查的 lenient 指令也只作用于该项判断。

职责入口：[management-instructions.ts](../src/model/management-instructions.ts)、[compiler-model-v2.ts](../src/model/compiler-model-v2.ts)。

## 2. Atom、整体方案与 Relation

**设计要求。** 每个 Atom 写明本次对象和输入、完整交付、共同适用要求、操作及信息使用范围、开始前提、完成证据和交回条件。它可以包含多次推理、工具调用、实现和测试。

模型按以下顺序决定任务形状：

1. 从当前未满足结果形成完整工作单元，先确定交付及权限。
2. 遇到新用户决定、新授权阶段，或足以改变后续目标和范围的结果时，设置交回边界。预览补丁与获准写回分别接纳。
3. 只有结果有具体消费者、可独立验收，或需要独立暂停和恢复时，才进一步拆分。普通自查留在原 Atom；用户要求独立复核时，保留独立复核职责。
4. 检查拆分后共同限制是否仍作用于全部适用工作。共享数据、交叉条件和同一对象上的写入需要明确协调。
5. 为真实依赖建立 Relation，并核对各项要求的去向。已知的条件后继可以提前准备；内容尚不确定的远期工作保留在 IR。
6. 输入变化后重新判断剩余工作、可用成果及拆合需要，记录新旧对应。

句子数、字段数、CLI 数量和测试数量均不决定 Atom 数量。完整 CLI 可能包含几个独立交付；一个 Atom 也可能为同一交付操作多个文件。选择粒度时须说明管理或交付收益。

**Relation 的设计要求。** 每条关系说明前后 Atom、所需结果或用户规定的先后、依据和适用条件。共享主题、实体或列表顺序不足以建立依赖。后继绑定实际使用的结果版本及范围；前驱自报完成后，仍须评价其结果是否满足后继条件。

用户确认属于授权或开始前提。前驱获准使用的信息，只能按后继自己的 Authority 传递。用户只允许一个文件而工具只能读取整个敏感目录时，选择合法替代或报告能力缺口。

成果可用性包括两项判断：结果对当前任务是否正确且适用，以及当前是否允许使用该结果。撤回读取权限后，不得为了重新验证而再次读取该材料。输入局部变化时，按后继实际读取范围和共同条件决定是否重查。

两个 Atom 修改同一对象时，需要冲突安排和开始时的版本判断。全部任务互相等待时，回查拆分、依赖或真实冲突；有依据时合并任务或修订关系，保留用户明确要求的顺序。

**当前实现。** `CompiledIntent` 保存 Atoms、Relations 和 IR 依据；Atom 生命周期在独立台账中维护。Atom 内容变更形成新修订；同 id 的递增 revision 可建立接替关系，不同 id 的语义对应由模型提供。重试执行另分配 `execution_id`。

候选 Relation 可用 Atom `local_ref`。代码在正文绑定后解析为精确 Ref，拒绝未知或歧义端点、自依赖和环。派发及动作授权检查所有传入关系：指定版本的真实 completed 回传、最近管理验收为 satisfied，以及关系附加条件。当前没有另设“只表示先后、无需结果验收”的调度分支。

后继可通过回传后的 `reuse` 批次获得资格。已派发且未变化的工作保留原生命周期。交付包含所需前驱版本、管理证据与回传产物元数据；实际读取这些产物还要经过后继的操作授权。

职责入口：[compiled-intent.ts](../src/core/compiled-intent.ts)、[atom-admission.ts](../src/core/atom-admission.ts)、[execution-state.ts](../src/core/execution-state.ts)。

## 3. 来源、身份、IR 内容与正文装配

**来源选择。** 模型决定哪些原文表达当前要求、各段的作用和范围，以及更新保留或撤回什么。代码在不可变来源上解析位置。来源文本使用 UTF-16 半开区间 `[start,end)`，定位前保留原始字符和换行。

当前来源选择支持 segment、精确唯一 quote 或合法 span。quote 缺失、多次出现、范围非法或选择器冲突时，代码拒绝该选择并返回诊断。分段由代码按段落边界完成，仅提供定位单位。IR 阶段可用 `e{序号}` 别名；持久化来源恢复完整身份，CI 阶段使用完整身份。

**IR 内容。** 严格模式的 `IR.content` 保存规范性业务要求：有来源的正文、适用范围和版本。代码将模型选中的原文区间物化为 `text`；同一来源的相邻或重叠区间合并，不相邻段落以空行连接。模型的 `interpretation` 另存。

- `create` 建立新内容；`revise：指明目标及 expected_revision`，替换该条内容的来源集合。
- `edit` 对既有来源区间执行 remove/add，保留未受影响部分；纯增加允许 `remove=[]`，remove/add 同时为空会被拒绝。edit 保留原 interpretation。
- 代码根据实际移除、且未被同批其他内容继续选择的区间形成 superseded 记录。模型负责确认这种移除符合用户更新的含义。

`source_coverage` 仍在提案形状内，可以为空。当前代码不要求把本轮用户全文逐段分完，也不自动把未选择文本登记为 context。它检查显式来源处置的合法性、处置与已选要求的冲突、历史规范来源的删除，以及携带委托的处理去向。审阅者须从原文检查应保留内容是否进入 IR。

**身份与版本。** 持久 Ref 使用 `id/revision/digest`；代码计算摘要、检查期望修订和引用一致性。IR、CI、事件序号分别演进。任务和条目的 ID 按当前提案及登记接口处理；不能把旧文“所有 ID 都只由代码分配”套用于每个字段。阶段 CI 中父任务归属和要求引用由代码补全。

固定版本的引用始终指向同一内容。Atom 内容变化后，同一 id/revision 不得绑定不同摘要；执行状态、回传和验收分别记录。新的消息、事件序号或格式相同的文本，都不自动证明两个任务或结果相同。

材料绑定和业务成果分别维护。用户改变比较对象、archetype、avoid 集合或共享数量时，修订相关绑定与条件并保留其他输出要求。旧判断保持原输入版本；环境调查先记为证据，只有改变委托理解时才修订 IR。

**要求分配与装配。** 严格模式要求每条当前 IR.content 有唯一 coverage 去向。assigned/supported 指向实际 Atom，paused/unresolved 保留原因且不分配给 Atom。同一要求可作用于多个适用 Atom；模型负责选择这些 Atom 和作用范围。

代码把分配要求绑定为当前 Ref，并在模型工作说明后附上对应原文正文及身份标签。Atom.task 是这次装配后的实际交付正文。工作说明、输出描述和完成证据应落实 IR，不能另增业务规范。

Atom.constraints 默认空；重复要求时，text 和 scope 必须与已分配 IR 一致，再由代码绑定引用。要求内容变化后，当前严格实现拒绝 `reuse` 旧编译；新绑定若改变相同 Atom id/revision 的正文，须提高 Atom revision。

**声明登记。** 代码从 Atom 的输出与输入声明生成 IR.outputs/bindings 的登记变化，记录实际修改。与父 IR 的语义修订分开处理：普通阶段 CI 必须保持父 IR 已声明的 output format，以及材料 binding 的 ref/role；新声明可由代码登记。

登记层沿用的历史原文与现行适用范围如下，供既有 gate 夹具继续定位：

| 原文 | 当前适用范围 |
| --- | --- |
| 新 id 由代码按原子声明创建 | output/binding 登记项；不描述所有类型的 ID 分配 |
| 只有 **format** 不一致才算矛盾 | 同批相同 output_id 的输出形状比较；binding 比较 ref 和 role |
| `description` 是散文，措辞不同不算第二次声明 | 同 id/format 的输出不会因描述改写而冲突 |
| 形状不同的既有 id 由代码 `revise` 成原子声明的值（原子赢），不再拒绝 | `registrationChanges` 的登记行为；普通阶段 CI 在此前先检查固定父声明，冲突会被拒绝 |
| 唯一保留的两条硬拒 | 旧登记取舍中的两项：同批同 id 形状冲突；未绑定材料被 Atom 猜填。当前还检查 draft 任务归属、父声明及其他 gate |

职责入口：[source-payload.ts](../src/core/source-payload.ts)、[source-aliases.ts](../src/core/source-aliases.ts)、[intent-state-v2.ts](../src/core/intent-state-v2.ts)、[requirement-flow.ts](../src/core/requirement-flow.ts)、[intent-compiler-v2.ts](../src/core/intent-compiler-v2.ts)。

## 4. 生成、核对、返修与提交

**当前生成路径。** v2 默认 `strict`，旧运行可显式选择 `legacy`。有用户委托的严格批次先生成 IR 提案，由代码在原批次前态上准备临时父 IR；随后 CI 请求读取该父 IR 及其摘要。CI 的 `parent_basis` 必须匹配。

IR 请求读取当前 IR、本批事件和选入的历史来源，不携带旧 CI 与执行证据正文。历史来源按当前输入、IR 已引用事件及未决委托选择。普通 CI 请求读取准备后的父 IR 和计划所需执行状态，不携带 IR 阶段的 `source_history` 正文视图。

IR 阶段不生成 compilation、coverage、execution_decisions、assessments 或 checks。普通 CI 阶段不输出 `ir_changes/source_coverage`；它以父阶段 local_ref 关联任务，由代码补 basis、task_refs、depends_on、draft.task_id，以及 coverage 要求的当前完整 Ref。具体字段形状在 [generation-schema.ts](../src/model/generation-schema.ts) 维护。

**父 IR 问题按路径处理。**

| 路径 | 谁处理父 IR 语义问题 | 后续处理 |
| --- | --- | --- |
| 普通 CI，配置独立核对 | 独立核对可给 `repair_target=ir`；CI 不得返回 `parent_issues` | 使临时父态失效，重新生成 IR，再生成 CI |
| 普通 CI，未配置独立核对 | CI 可返回 `parent_issues` | 返回 IR 阶段修订 |
| 没有用户委托的执行评估批次 | 使用存储 IR，跳过 IR 生成；只有父问题妨碍本次判断时报告 `parent_issues` | 保存延后评估及 question，保留 IR/CI，留待后续用户委托处理 |

执行返回提供事实和证据；修改用户要求仍需相应委托来源。上述路径允许代码派生声明登记，范围见[来源与正文装配](#sources)。

每批最终候选须对齐 IR 修订与未决差异、CI 交付与未满足目标去向、旧执行继续/停止/等待决定，以及可复用成果。模型按当前合同生成需要改变的对象；核查应变和应保留行为，不新增固定自证报告，`checks` 默认空数组。

**prepare。** 编译器在私有管理器与台账上应用 IR 变化、登记、绑定、CI 构建、执行决定和交付，形成明确候选。独立核对读取这份 prepared 候选中的提交后 IR、最终 Atom 正文和资格；通过后提交同一份准备结果。

当前 `prepareCandidate` 不写正式 store。事件出队、调用记录、预算及失败草稿会分别保存，因此批次失败后仍有处理记录。IR 阶段成功、CI 阶段失败时，不单独接纳该候选 IR。

“编译器可以产生新的 IR 而暂不产生可执行内容”适用于暂停、未决等管理结果：最终候选仍须满足机械门槛及配置且适用的核对。当前已有要求正文改变时，直接 reuse 旧 CI 会被严格绑定检查拒绝。

**独立核对。** 配置 `model.verify` 后，有用户输入且候选关联任务的批次触发核对；无用户输入的批次按新编译任务触发。核对费用计入同批预算。核对器报告问题和返修目标，由生成阶段修改产物。

语义审阅须同时检查两条方向：从原文确认每项当前要求的去向；从最终 IR、CI 和 Atom 正文确认每项动作、条件及业务规范的依据。finding 要核对它所声称的实际字段。机械来源解析只能回答定位是否成立。

当前代码把来源证据可解析的 finding 作为阻断问题，保存原始 verdict 及过滤记录。它还没有把 finding 对候选字段的散文指控逐项核实；“inconsistent 但无可用 finding”和“consistent 同时带 finding”的整体语义裁决仍待决定。

**返修与预算。** 机械错误和核对问题进入有界返修。返修请求携带被拒候选、问题和依据状态；依据改变时，模型按当前输入重新判断。`ParentGeneration` 的 feedback/reject 更新当前 issues；历史 attempts 留在记录中。当前 issues 未保证持续携带此前所有尚未解决的语义问题。

当前工作区的来源修复补丁同时保留原始 `ir_proposal` 和代码派生的 `ir_repair_draft`。后者把已成功解析的引用规范化，保留失败引用并注明来源。继续使用草稿前检查 `source_basis`，从原批次前态重新准备父 IR 并核对摘要。

调度先预留完成剩余阶段所需调用：IR 阶段至少 IR+CI，CI 阶段至少 CI；适用独立核对时再加一次。每次生成、核对和重试计数。store 默认每批 3 次、总计 30 次；具体实验可另设限额，实际值查运行配置。当前主循环按请求次数限制；预算里的 token 字段主要用于记账，不能当作已落实的同等硬停止机制。

长调用返回后，提交前重新比较事件、IR、CI、派发、执行、Atom 状态、验收及资格等读取依据。变化时记录 `stale_basis` 并保留尝试和成本。配置核对无法执行或无法解析时记录 `check_unavailable`；所需调用无法安排时记录 `budget_exhausted`；有效语义问题未解决时记录 `semantic_unresolved`；机械候选错误与传输/JSON/schema 错误保留各自原因。

职责入口：[intent-compiler-v2.ts](../src/core/intent-compiler-v2.ts)、[parent-generation.ts](../src/core/parent-generation.ts)、[compiler-model-v2.ts](../src/model/compiler-model-v2.ts)。

<a id="execution"></a>
## 5. 宿主调用、执行资格与验收

可信宿主或 Adapter 调用 v2 接口，负责把真实事件、会话和操作绑定到运行。执行模型通过宿主提交结果。

| 调用 | 当前职责 |
| --- | --- |
| `acceptEvent(event): Promise<EventReceipt>` | 校验身份、去重和保存事件；登记待处理用户更新；接收合法执行回传并关闭该执行资格 |
| `advance({runId}): Promise<AdvanceResult>` | 处理一批待办，生成、准备、核对并提交管理结果，返回交付、等待、澄清或失败 |
| `authorize(request): AuthorizationResult` | 同步判断 start 或具体 operation，记录允许的执行/调用及拒绝；不调用模型 |
| `inspect({runId}): Promise<RunView>` | 返回当前 IR/CI、待办、委托缺口、执行状态、coverage、核对和拒绝记录 |

**交付与开始。** 当前直接交付最终 Atom。OpenCode Adapter 渲染、送达并通过 SDK 读回核对内容后发起 start。核心 start 检查 dispatch 对应的 Atom id/revision/digest 仍在当前 CI 中，Atom 状态为 ready，并通过范围、资格、前提和 Relation 检查。读回确认流程在 Adapter；核心 start 没有另设一项 delivery_ack 必须存在的检查。

相同 Atom 内容可复用 dispatch。已有未闭合执行时，重复 start 返回身份冲突；当前行为与旧文设想的“重传同一开始请求幂等返回”不同。

**用户更新。** 接收更新即登记 `unresolved_user_event_ids`。出队和生成失败都不清除它，期间整个 run 拒绝新的 start/operation。成功处理后，候选覆盖且 scope=proceed 的任务可进入执行资格。现有执行只有明确 continue、身份和内容未变且范围允许时才能继续；stop 关闭资格，await_result 等待回传。conditional 目前不提供启动保证。

**操作权限。** 用户委托可合理包含完成目标所需的读取、计算和指定写入，用户无须逐个指定工具名。模型从真实宿主能力中选择方法；增加敏感来源、修改对象、收件人或用途时须重新核对授权。设计要求对“输入—操作—输出用途”的组合判断 Authority，并按宿主实际能力落实。某项能力存在，不代表用户允许把任意输入送到任意输出。任务之间须按授权分离上下文和传递产物；生成器获准读取的答案背景不能随会话自动交给解题者。新执行使用与本次授权相符的上下文；若同一上下文中的资料不能流向全部输出，分离工作与上下文，或使用宿主已有的可靠数据约束。路径约束需要宿主解析真实目标及别名/链接；模型自报“已脱敏”不能替代公开输出许可。

当前代码检查活动执行、可信宿主身份、`host_call_id`、operation_id 及规则条件。规则声明 input/output refs 时，还检查 resource_ref 相同及请求 refs 属于允许集合；两组 refs 均为空时，按匹配 operation_id 放行，并记录宿主解析的工具与参数摘要。自然语言用途、参数中的具体路径及跨输出信息流没有通用强制解析，需由实际宿主接线提供相应约束。

**条件求值。** 条件支持 all/any 组合，解析后由代码判断。当前支持 scope_allows、capability_available 和 assessment_supports；最后一项匹配目标精确版本及最新验收。

旧夹具原文“其余 Condition 类型（artifact_exists、user_confirms、object_version_matches）仍按 unsupported 处理并拒绝”对应这些未实现的叶条件。实际组合使用三值逻辑：all 中有 unsatisfied 则不满足，否则有 unsupported 则未知；any 中有 satisfied 则满足，否则有 unsupported 则未知。最终准入只接受 satisfied，所以 any 的其他分支已经满足时，可以放行。

**返回与验收。** `execution_return` 必须对应真实 execution 和原 Atom 的精确版本，state_claim 与 outcome 建议状态一致。保存前由宿主核对声明文件路径的摘要；不匹配或无法核验时拒绝该回传，保留原执行状态。异步摘要核验后再次读取执行身份。

合法回传关闭本次执行资格并记录结果，blocked 交回也关闭资格；progress 不关闭。已关闭执行的身份匹配回传记为 historical，不重开执行或覆盖当前 Atom 状态。独立 operation_result 可以迟到。

管理层分别判断派发时 Atom 的完成、当前目标的满足，以及历史成果的可用性和允许用途。Assessment 保存 target_ref、criteria、evidence、结果和方法；不足以判断时用 unknown。执行层完成标签与业务自报结论作为证据输入，管理层核对其实际内容。

已受理的外部动作可能继续完成。宿主须提供实际效果或未知状态，权限台账不能撤销已经发生的读写。当前 OpenCode 零派发时返回 `COMPILER_HOST_WAIT_UNSUPPORTED` 并携带管理结果；正常暂停和呈现澄清的宿主体验仍缺接线。

职责入口：[intent-compiler-v2.ts](../src/core/intent-compiler-v2.ts)、[execution-state.ts](../src/core/execution-state.ts)、[adapters/opencode.ts](../src/adapters/opencode.ts)、[host-contract.ts](../src/harness/host-contract.ts)。

<a id="persistence"></a>
## 6. 存储、队列与恢复

**设计要求。** 保存用户原始输入、被拒候选、核对、已接纳产物、真实执行及验收，使后续处理能判断事件是否已处理、产物依据和动作效果。未查明效果的外部操作，应先与宿主核对，再决定是否重发。

**当前实现。** store 分开保存事件、snapshot 和 check-inputs。相同事件 ID 与摘要按重复处理；同 ID 不同内容拒绝。snapshot 用临时文件加 rename 写入；多个文件之间没有统一事务或完整 WAL 恢复机制。

待办队列与未决用户事件分开维护。当前优先以最新用户事件为主批，携带有界的较早委托缺口；失败不使未决用户输入从记录中消失。事件是否已登记按事件来源引用和管理记录判断，完整需求是否遗漏仍由语义审阅判断。

开始处理批次会重置批内请求计数，总请求数继续累计。重新打开 store 从事件和管理记录恢复未决委托及未消费回传，读取旧格式时进行兼容转换。当前没有“进程重开即统一冻结并核对所有未闭合宿主执行”的完整恢复流程。

同一 store 对象上的 advance 由进程内保护避免并发；不同实例或进程没有共用文件锁。长调用期间仍可接收新事件，提交前通过读取依据比较拒绝过时准备结果。

Observer、audit report 和 cost summary 从管理与运行记录生成观测视图；恢复正式状态使用对应 store。运行冻结源码、执行会话、工作区与 store 必须按同次运行对应，具体位置由 [dpipe 状态](../experiments/evocode/harbor/dpipe/README.md) 维护。

职责入口：[compiler-store-v2.ts](../src/core/compiler-store-v2.ts)、[runtime-factory.ts](../src/harness/runtime-factory.ts)、[observer](../src/observer/)。

## 7. 评价目标、实现差距与未决选择

下一阶段先逐轮准备 IR → CI → 最终 Atoms，返修并审阅管理产物，再按获准轮次交执行层连续运行，用原官方 verifier 观察长任务。当前产物、失败和执行起点统一查 [dpipe 状态](../experiments/evocode/harbor/dpipe/README.md)。

评价分别记录管理质量、生成与审阅成本、执行结果。质量检查覆盖委托/材料区分、局部更新与字段范围、Atom 拆分与真实依赖、授权、成果复用及最终正文。成本包括失败、返修、询问和人工介入。额外生成应对应新输入、事实变化、具体修正或可进一步检查的缺口；没有这些依据时，转入合法执行、调查、具体提问或等待。进展指取得所需证据、完成有效工作或消除真实缺口；等待、误拒绝和无依据的反复生成分别记录。

研究问题仍是管理层对持续任务可靠性、有效进展和总成本的增量。管理层 on/off 比较与“显式 IR / 同格式直接编译”比较分别回答整体系统与 IR 维护的贡献；选择比较时固定合法信息、执行接线及基础工具条件，记录实际差异。旧文的合成轨迹、模型型号和额度保留在历史协议中，下一次实验设计另定范围和预算。

| 尚待处理的问题 | 当前事实及设计工作 |
| --- | --- |
| 最终正文的语义完整性 | 机械装配完整保留已选要求；来源选择和模型核对仍有漏检。审阅需合读原文、更新和最终正文 |
| 返修问题的连续性 | 当前 issues 会被后续错误替换。需判断哪些语义 finding 仍适用，以及怎样呈现才减少返修负担 |
| finding 裁决 | 引用可解析与候选事实成立由不同检查回答；矛盾 verdict/findings 的处理仍需明确 |
| 局部变更与执行连续性 | 当前全 run 暂缓、要求变化拒绝 reuse、失败候选整批不接纳。设计希望保留无关合法进展，需研究可证明的影响范围 |
