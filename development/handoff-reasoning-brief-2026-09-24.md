# 任务：诊断一个「意图管理层」系统的失败，并给出方案（只推理，不写代码）

你拿到的是**一次真实工程实验的全部问题清单**：现象、我们观测到的数据、以及代码当前实际的行为。请从更全面的角度分析它，给出机制性的判断和方案。**不要写代码，不要列补丁清单。**

## 一、"更全面"在这里指什么（三个维度，逐条说明）

1. **范围上**：不要一条规则一条规则地修。这套系统在一轮真实运行里会因为**约 12 道顺序关卡中的任何一道**而整批作废，且每道关卡背后还有别的关卡。请把"这一轮为什么白跑"当成一个整体来解释：代码判定、模型判定、宿主编排、预算、评分这五处，哪一处是瓶颈，哪一处其实在做别人的活。
2. **视角上**：把系统当成**一个概率生成器 + 一份确定性契约**来审。要问的是契约的形状，不是某条规则的松紧：谁拥有身份（id、版本、摘要）；谁有权说"不"；判定发生在**信息最全的那一点**吗；说了"不"之后系统做什么；哪些话是"要求"，哪些只是"写给模型看的建议"——这两类现在混在同一份文本里。
3. **证据上**：下面每一条现象都配了"代码当前实际怎么做"。你要给出的不是"这里加点检查"，而是**一个能同时解释多条现象的机制性判断**，并且写出：**如果这个判断成立，下一轮真实运行会看到什么不同**（可证伪的预测）。如果多条现象在你的判断下其实是不同原因，也要说清哪几条是同一类、哪几条不是。

## 二、系统是什么（背景）

- 这是一个**意图管理层**：它本身不做业务工作，只负责把用户的持续委托（多轮、可以改口）编译成可执行的最小工作单元，交给底下的执行 agent 去做，并保留证据与状态。最终要作为**通用包/插件**接进别的项目——所以任何方案不能假定我们长期掌控宿主。
- 一次真实运行的管线：用户的委托作为事件进入 → 管理层模型生成一份**候选**（新的编译内容 + 对意图的修订 + 对交付物的声明 + 抽查项 + 要问用户的问题）→ 一串机械门槛判定 → 一次**独立的第二次模型调用**核对这份候选 → 通过则落库并派发 → 执行 agent 在容器里干活 → 回传执行结果 → 下一批。
- 管理层模型和执行层模型是两个不同的模型。一次真实运行的 agent 预算上限是 **30 分钟**。
- 评分：一个 49 用例的评测，**0/1 计分**——任务要么被完成，要么 0 分。
- **当前状态：至今没有任何一轮让执行层在有产物的情况下跑起来，奖励恒为 0。** 执行层至今只报过一次"找不到验证用的二进制"，即它根本没产出东西。

## 三、现象与代码行为（现状，逐条）

### 成本与时间

1. 管理层单次模型调用实测 **161–392 秒**（推理占输出 token 的 75%–85%）。一次真实运行里，管理层吃掉 **35%–50%** 的 30 分钟预算。
2. **两批被拒就基本耗尽预算。** 一批从提议到被拒要 5–11 分钟；被拒之后事件重新排队，下一批**从零开始**，只是多带一条"上一批为什么被拒"。
3. 我们实测的失败分布：空引用 + 反问被拒 / 核对的两份 schema 不同步被拒 / 同一交付物两句同义描述被判"第二次声明"被拒 / 模型把给它的**契约字段当成了输入来源**（因为请求里的字段按字母排序，契约排在事件前面，而契约文本最长最像指令）。

### 判定分布（我们逐条数过）

4. 我们把"项目对模型和代码提出的全部要求"逐条编号，共 **152 条**：给模型的编译合同 73 条、给核对员的合同 13 条、设计文档里的规范句 66 条。
5. 其中**只有 72 条完全由代码判定**；8 条只有核对能判；42 条判了一半（另一半没人判）；**26 条只是写给模型看的话、没有任何判定**；2 条连给模型的文本里都没有；2 条已经过时或首版不做。
6. 也就是说：**给模型看的文本里，有相当一部分是"要求"，但违反它没有任何后果**；同时代码里有判定在拦模型，而合同的措辞可能和它不一致（下面有实例）。

### 关键的行为缺口（这些是现在真实存在的问题）

7. **"提问"这条路是堵死的。** 合同明确告诉模型："这一批如果编译不出东西，可以提问并说明原因。" 但机械层的第一道门是："这批带着用户委托，却没有任何一个组认领任务 → 拒。" 模型只提问、不认领任务时，整批直接作废。**更糟的是**：独立核对只在"这批编译出了新原子"时才运行——**纯提问的批次完全不经过任何核对**。
8. **"暂停"这个取值算不出来。** 任务当前范围的取值设计有四种：推进 / 暂停 / 撤回 / **有条件**。条件求值器只认前三种：推进 = 允许；暂停和撤回 = 不允许；**"有条件" = 无法求值，于是它保护的所有操作被永久挡住**。写"有条件"等于永远不许动手，且没有任何机制会告诉用户这件事。
9. **"空引用"三处说法不一致。** 给模型的合同说"空引用只在这一批没有用户委托时才成立"；机械判定对**任何**批次都拒绝空引用；设计文档的验收段说"含空引用一律按可修订拒绝"。三处不同。
10. **每批的输入/输出 token 上限是死的。** 预算结构里写着"每批输入最多 64000、输出最多 6000"，但**全仓库没有任何地方读它们**。有一次真实运行的模型输出是 72k 字符，系统毫无反应。
11. **模型可以现编引用。** 候选里的引用有两种：① 指向原始文本的来源引用——代码会把摘要**改写成真实摘要**，所以模型写占位值没关系；② 指向对象的引用（带 id / 版本 / 摘要三件套）——**这三件套完全没有校验**，模型可以写一个不存在的 id，它会原样存进产物并派发出去。只有"接替上一个失败的原子"这一个字段做了校验。
12. **给模型看的范例自己违反了合同。** 范例里来源引用的 id 写的是一个**占位名**，而合同写明"有效的来源 id 只能是本批事件之一"。我们实测：把这份范例配上真实事件，机械门槛 0 问题，但 **6 个来源引用全部解析不了**、摘要保持占位值。也就是说，模型照着范例抄，就会写出合同禁止的东西。
13. **旧存档的摘要和新写的不是一回事。** 代码现在会把候选里的来源摘要改写成真摘要并落库；但**在那次改动之前**写下的原子，摘要还是当年的占位值。拿这类旧存档续跑时，同一份原子内容会被判成"内容变了，必须升版本"——**同一份内容被误判成改过了**。
14. **任务之间的关系只查形状。** 两条依赖关系只校验"前驱和后继是合法的对象引用"；中间那两栏"需要什么结果、什么先后条件"既不解析也不检查。所以关系图可以通过，但顺序和前提没人看。
15. **"未决项"字段只写不读。** 任务数据里有一个未决项列表（问题、备选答案、影响哪些对象、还缺什么证据），类型定义和归一化都有，但**合同不提它、门槛不读它、核对没有对应维度**。
16. **核对说"一致"却列出问题时没人管。** 核对答案有两栏：结论（一致 / 不一致）+ 具体问题列表。现在只校验形状，不校验"说了一致，却列了一堆问题"这种自相矛盾。
17. **失败码清单与实际不符。** 设计列了 10 个失败码，实现里没有"交付不符"与"效果未知"两个——前者实际发生在适配器层、用的是另一套名字；后者根本没实现。
18. **两类声明完全没有判定点。** 候选里有两类内容：① 对成果的评价（评什么、依据什么、结论）；② 对在途执行的继续 / 停止 / 等待决定。两类都**没有机械门槛，也没有核对维度**。
19. **"上一次被拒的理由"传下去了，但没人检查"是不是就地修了"。** 上一批的拒绝理由（含维度与"引用是否能解析"）会带进下一批的输入，合同也要求"就地修复这些理由，不要重新规划"；但机械层和核对都只看新候选**自己**过不过关。
20. **核对的反对意见只有"引用能解析"才能拦下整批。** 引用解析不了（指向本批不存在的东西）就只记录、不阻断。这条本意是防核对乱说，副作用是：**能引到原文但引错意思**的反对意见仍然可以整批作废。
21. **被拒之后没有"定向重试 + 一次性确认"的通路。** 现在是整批作废、事件重排队、下一批从零开始。对照：成熟实现里有"同一条命令 + 最窄的足够权限 + 一次性人工批准"的升权路径；我们只有"重掷"。
22. **失败整批之后还有一次"时间受限的再推进"**（10 分钟内），超时或预算不足就按原样失败。

### 我们已经确认的边界问题（内部）

23. 上面第 5 条的统计意味着：**没有一条机械手段保证"给模型的合同"与"代码实际的判定"一致**。已经发生过一次：核对的两份手写 schema 拷贝不同步（发给 provider 约束解码的那份、与我们校验答案的那份），导致核对答案永远判非法、整轮作废。现在只有这一处加了防漂移测试。
24. 设计文档内部也出现过前后矛盾的一句话（一句说"引用不存在的 id 要被拒绝"，后文又改成"原子声明的新 id 由代码自动登记、不拒绝"）。这类矛盾会让下一个执行者按错的那句去实现。

## 四、约束（方案必须满足，否则不成立）

1. **不要以"换模型 / 换 provider"作为主要出路**——这件事已经查证过，不是这里的瓶颈。
2. **不接受靠调参数解决**（放宽预算上限、加长超时、提高 token 上限）。要的是机制上的判断。
3. 这套系统最终要**作为一个通用包接进别的项目**，所以方案不能依赖"我们会一直掌控宿主"或"我们能看到宿主的全部状态"。
4. 系统里有一类不可让步的纪律：**拿不到保证就不许放行**（判定不了的条件必须挡住动作，不能默认通过）；**不许把"检查跑不起来"记成"检查说不行"**（基础设施失败与语义拒绝必须分开）。
5. 现实里管理层模型是**概率生成器**：同一条规则，它有时会犯、有时不犯；每一轮都是重新采样。

## 五、你要输出什么

1. **一个机制性的诊断**：把上面 24 条现象归成少数几类，说清哪些是同一个原因、哪些不是。重点回答：**这一轮为什么白跑——瓶颈到底在哪一层**。
2. **对契约形状的判断**（这是重点，不是逐条修规则）：
   - 判定应该发生在链路的哪一点？（信息最全的地方是哪一处？现在是不是判早了或判晚了？）
   - 哪些现在由代码判的事其实只能由模型判，反过来哪些由模型判的事其实代码就能判？
   - "拒绝"之后系统应该做什么？（现在只有"整批重掷"这一条路）
   - 身份（id / 版本 / 摘要）应该由谁拥有，边界划在哪里？
   - 那些"只写给模型看、没人判"的话，应该删掉、降级成建议、还是补上判定？
3. **可证伪的预测**：如果你判断成立，改完之后**下一轮运行会看到什么不同的数字或现象**（例如：单轮管理层调用次数、派发次数、失败落在哪一层）。如果观察不到这个差别，说明你的判断错了。
4. **明确写出你不确定的地方**，以及你会用什么证据去分辨。
