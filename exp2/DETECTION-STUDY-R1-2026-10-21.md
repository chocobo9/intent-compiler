# R1 检出研究：缺陷库、检出矩阵、差分测试（2026-10-21）

**目的**：在讨论"回修"之前，先度量判定依据本身——系统能发现产物里的哪些问题，漏掉哪些。全部用现有材料，不调用模型。

**材料**：
- 同一份 R1 原文的 16 份独立实现：luna high 10 份、6-luna medium 3 份、5.6-luna medium 3 份；
- 每份实现的官方逐题结果；
- Haiku 推导、已入库的 R1 检查，共 26 条；
- 第 9 块的检出脚本。

**工具**（`exp2/tools/` 下）：
- `defect_corpus.py`：建缺陷库；
- `case_tracking.py`：跨轮按稳定键跟踪用例。

检出脚本是 `intent-exp2-detect`，差分测试脚本是 scratchpad `b5/difftest.mjs`。

## 1. 缺陷库

- 16 份产物里，至少有一份失败的用例共 139 个。其中 71 个只在 6-luna medium 的 3 份半成品里失败，原因是没实现。
- 把 6-luna medium 去掉，剩下 13 份实现里的失败集中在 transform：
  - derive 和表达式语言；
  - window；
  - 另有少量 aggregate、pivot、sort、pipeline。

最常见的缺陷：

| 缺陷 | 13 份实现里失败几份 | 原文怎么写 | 性质 |
|---|---|---|---|
| `log(0)` 应为 NaN，实际给出 -Inf | 7 | 86 行写明：对非正数返回 `NaN` | 原文写明的边界被漏掉（Go 的 `math.Log(0)` 默认返回 -Inf） |
| window rank 的结果列没有名字 | 4 | 135 行写明：`as` 是新列的名字 | 实现错误：值算对了，列名丢了 |
| 表达式运算和函数（比较、逻辑、取反、clamp、coalesce） | 2–3 | 74–91 行都写明了 | 复杂子功能写错或写漏 |
| window 整体崩溃 | 1 | — | 整块做坏 |
| aggregate min/max、ntile | 1–3 | 写明了 | 实现错误 |
| sort 或 window 遇到不存在的列时报错、avg 没有数值时为 NaN、pivot 复合索引的行序 | 各 1 | 都写明了 | 原文写明的细节被漏掉 |

- 在这些缺陷里没有看到原文本身有歧义的情况，失败都对应原文写明的内容。原文有歧义的地方出现在检查一侧，见第 3 节。

## 2. 检出矩阵：26 条 R1 检查，跑在 16 份产物上

按"产物 × 缺陷区域"统计。官方认定的缺陷区域，系统是否判为没落地：

| 产物（官方分） | 官方缺陷区域 | 检查是否发现 |
|---|---|---|
| luna high 裸模型 1（219） | 无 | 无误报（两条错误检查判为有争议） |
| luna high 裸模型 2、4（218） | window 列名 | ✓ window |
| luna high 裸模型 3（218） | log(0) | ✗ |
| luna high 外壳（191） | window 崩溃、log(0) | ✓ window；✗ log |
| luna high 反事实 1（218） | log(0) | ✗ |
| luna high 反事实 2（217） | derive 函数、log(0) | ✗ ✗ |
| luna high 反事实 3（203） | 表达式解析 | ✓ |
| luna high 反事实 4（215） | log(0)、sort | ✗ ✗ |
| luna high IC（215） | aggregate、window | ✓ ✓ |
| 5.6 medium 1（201） | 表达式运算、ntile、pipeline 链 | ✓ ✓ ✓ |
| 5.6 medium 2（208） | 表达式；log(0)、avg、sort 报错、window 报错、pivot 行序 | ✓ 表达式；其余 5 处 ✗ |
| 5.6 medium 3（219） | 无 | 无误报 |
| 6 medium 1–3（91、84、122） | 没实现的操作 | 全部 ✓ |

- **整块的问题全部发现**：崩溃、没实现、整体算错，一次都没漏。
- **原文写明的边界和细节基本没发现**：除去 6 medium 的半成品，13 份实现里共有 23 个缺陷区域，发现了 11 个，约一半。漏掉的全是细节：`log(0)` 在 7 份实现里失败，没有一份被发现；还有 avg 为 NaN、不存在的列要报错、pivot 行序、sort 的细节。
- **误报**：pipeline_fail 在 3 份正确的产物上判为没落地；pipeline_ok 在每一份产物上都判为有争议。

## 3. 差分测试：同样的输入，比较 16 份实现的输出，不用任何期望值

做法：把 26 条检查的输入分别喂给 16 份实现，在同一个输入上，和多数输出不一样的实现记为"可疑"。

- **它发现的和检查发现的完全重合**：
  - window 输入上，少数派正好是 window 有缺陷的 5 份实现（裸模型 2、4，外壳，IC，5.6 medium 1）；
  - 表达式输入上，少数派是反事实 3 和 5.6 medium 1、2；
  - aggregate 输入上是 IC；
  - verify 输入上是反事实 3。
- **检查漏掉的，它同样漏掉**：没有任何输入用到 `log(0)`、avg 无数值、不存在的列等情况，所以两种方法都看不见。
- **它能识别错误的检查**：pipeline_ok 和 pipeline_fail 在多数实现上的输出一致，却和检查的期望不一致。这说明是检查有问题，不是程序有问题。差分测试因此可以作为裁决"检查是否写错"的一个独立信号；注意它可能有同源失效。
- **噪声**：manifest 带有 `generated_at` 时间戳，pipeline 的输出带有路径，所以几乎每份实现都不一样，必须先排除原文允许变化的字段才能比较；报错文字的细微差别也会造成分组。

## 4. 结论

1. **发现能力的上限，取决于输入覆盖了原文里多少条明确的规则，而不取决于期望值怎么判。** 检查和差分测试在同一组输入上发现的问题完全一样，漏掉的也完全一样。漏掉的都是原文写明的边界和细节，而这正是失分最多的一类：log(0) 在 7 份实现里失败。
2. **回修的前提是发现。** 现在检查只能稳定发现整块的问题，对细节的覆盖大约只有一半，所以"没人回头修"的主因是没发现。要提高回修的效果，首先要让检查的输入覆盖原文里每一条明确的规则。第 9 块按单位度量覆盖，测得 Haiku 的检查覆盖只有 20/130，与这里的结论一致。
3. **多份实现相互比较，可以帮着判断检查本身对不对**（第 3 节），但它不能替代覆盖。
4. **还没有检验的**：
   - 检查和实现出自同一个模型时会不会一起读错（这里的检查出自 Haiku，实现出自 luna，两者不同源）；
   - 回修本身（发现以后能不能修对、会不会只是修到让检查通过）。

   这两项需要用真实的 IC 运行来测。
