## 2. 数据结构与接口

### 2.1 工单（`WorkOrder`，DESIGN 第 6 节）

- **任务区**（`task`）：每项写明进入的原因 `why`，有三种。
  - `changed`：本轮有改动，附改动编号；
  - `not_landed`：上一轮判定里有判为未落地的检查，附这些检查的参数、输入文件名、期望与实际；
  - `carried`：在上一轮任务区里，但没有已提交的步骤完整覆盖它，并且状态不是已落地，附 `carried_from`（哪一步）。
  - "未知"本身永远不会让对象进任务区。
- **保护区**（`protect`）：已落地、并且与任务对象共享锚点的对象，附它们当前通过的检查。
- **状态区**（`status`）：判为未知、又不在任务区的对象，附原因码。
- **原文区**（`source`）：按对象分组，每个被分配的块的原文恰好出现一次。块前有一行标签：块编号、状态、标题路径。归 none 的块放在最后一组。被替代的块照样列出，并标出状态。
- **锚点区**（`anchors`）：任务和保护对象当前的锚点（编号、文件、行范围），以及最近几次涉及它们的步骤。
- `edges`：任务对象的边，只作参考，不作先后约束。

除原文区外，各区只有编号、原因码、检查的参数和实际输出，没有原文。有测试断言：原文区里每块恰好出现一次，原文区以外不出现任何块的原文。

### 2.2 锚点和对象

锚点编号形如 `A:transform.go:func:runTransform`、`A:main.go:dispatch:verify`。一个对象的锚点来自两处：
- 名字等于对象名的分派点；
- 已提交的步骤为它声明的对象改动过的锚点（`AnchorLink`，`via: "step"`）。

比较锚点时不算文件锚点，因为任何改动都会碰到文件。

### 2.3 执行方接口

- `Executor.open(context)` 返回 `ExecutorSession`。会话有三个方法：`propose(feedback)` 提议分步，`work(step, feedback)` 在工作树里为一步改代码（不提交），`close()` 关闭。
- 会话坏了就抛 `SessionBroken`。一次调用超过 `stepTimeoutMs` 也按会话坏了处理。
- 新会话的 `context.resume` 带着已完成的步骤和剩下的步骤。
- `OpenCodeExecutor` 是本地用的实现：每个执行方会话对应一个 OpenCode 会话；分步用结构化输出拿，每一步发一次 prompt。

### 2.4 执行流程（`executeRound`）

1. **分步提议**：代码只核对形状：
   - 步数上限，每步对象数上限；
   - 对象必须在任务区里，同一步里不重复；
   - 被部分覆盖的对象，后面必须有一步完整覆盖它。

   不通过就把问题交回同一个会话重新提议（`maxProposals` 次）。用完次数仍不通过，任务区全部对象进入下一轮。
2. **逐步执行**：每步开始时记下检查点（HEAD）和当时的锚点；执行方改完以后，代码依次做：
   - 编译（输出到工作树之外）。
   - 比较前后锚点。声明覆盖的对象如果已有锚点，就必须动到其中至少一个；还没有锚点的，至少要动到某个锚点。否则退回。
   - 运行相关检查：完整覆盖的对象，它自己的检查必须通过；部分覆盖的对象，等到完整覆盖的那一步再要求。步骤动了未声明对象的锚点时，跑那些对象的检查作为保护；只有在上一个好的检查点时已经通过的检查，才算回归。判为未知的失败只记录，不作证据。
3. **结果处理**：
   - 通过：提交，trailer 为 `IC-Round`、`IC-Step`、`IC-Session`、`IC-Object: O5@v1 full`、`IC-Anchors`、`IC-Checks: K4 pass`。随后登记锚点和对象的对应，更新通过的检查集合。
   - 不通过：把问题交给同一个会话继续改，工作树不回退，最多 `maxAttemptsPerStep` 次。用完仍不通过，回到检查点，这一步记为 `failed`，接着做下一步。
   - 会话坏了或挂死：回到检查点，另开会话（最多 `maxSessions` 个），只交剩下的步骤。
4. **预算**：
   - `roundAttempts` 是整轮的尝试次数上限。用完时，已提交的步骤保留，其余标为 `carried`，状态记为 `budget_spent`。
   - token 按步累计在 `usage` 里。
5. **执行记录**（`ExecutionRecord`）：包括全部提议及其问题、会话（正常关闭还是坏了）、每一步的状态、尝试次数、所在会话、检查点、提交、改动的锚点、检查结果、问题、执行方的说明，以及进入下一轮的对象和新的锚点对应。
6. **从 git 读回**：`stepsFromHistory` 只读 trailer。

## 4. 需要设计会话决定的问题

**4.1 检查在编码之前推导。** 第 9 节的顺序是先编码（第 5 步）、后推导检查（第 6 步）。这样一来，每步验证时只有前几轮的检查可用，本轮新增和修订的行为在编码过程中验证不到。第 5 块我打算把推导放到编码之前：基线本来就是上一轮验收通过的版本，与编码无关；本轮新检查的失败也就能作为反馈交给执行方。推导出的检查不作为需求交给执行方，只在验证时用。这改变了第 9 节的顺序，请确认。

**4.2 分步不必覆盖全部任务对象。** 我只要求"部分覆盖之后要有完整覆盖"，不要求每个任务对象都出现在分步里。没出现的对象记入 `carried`，下一轮仍在任务区。如果设计希望强制全覆盖，`planProblems` 里加一条即可。

**4.3 保护只守护原本通过的检查。** 设计写的是"动了没有声明的对象的锚点，就跑那个对象的保护检查"。如果一个对象还没做完（例如只被部分覆盖过），它的检查本来就不通过，算作回归会让后面的步骤全部失败。离线验证最初就因此连锁失败。现在只有在上一个好的检查点时已经通过的检查失败，才算破坏了保护。

**4.4 部分覆盖的步骤不要求被覆盖对象的检查通过。** 只编译、核对锚点、跑保护检查。

**4.5 新对象的锚点判定。** 还没有锚点的对象，只要这一步动到了任何锚点就算覆盖。这是能做到的最宽的判定，因为执行之前还不知道它会落在哪里。之后由步骤的登记和同名分派点把锚点和对象连起来。

**4.6 被带到下一轮的对象可能状态未知。** `carried` 的依据是执行记录（这一步没做完），不是"未知"状态。按"没完成的进下一轮的任务区"处理，已落地的除外。这与"未知不进任务区"不冲突，但请确认这个口径。

**4.7 失败的步骤整步丢弃。** 用完尝试次数仍不通过时回到检查点，执行方在这一步里做对的部分也一起丢掉。如果要保留，需要更细的检查点，目前没有做。

**4.8 原文区的标签行。** 只分配了段落的小节，它的标题行不属于任何被分配的块，不在原文里出现，只作为标签里的标题路径出现，可能出现多次。原文块本身只出现一次。

**4.9 token 预算。** 每一步的 token 都记下了，但目前只限制尝试次数和时间，没有限制 token 数。如果要按 token 止损，可以在 `ExecutionLimits` 里加一项。

**4.10 Go 工具链。** 锚点辅助程序和编译都要求本地有 `go`。云端环境有 Go 1.24，测试都实际跑过。
