# 第 12 块：台账、不做无效修补、定向运行、只做验收的回放

依据：exp2/DESIGN.md §12h（f0bdb58）和第 12 块的消息。重跑规则以本块为准：每个周期定向运行，每轮交付前全量兜底；其余以 §12g 为准。基础是 `exp2-block1` 1052bf9（第 11 块）。

下面每一项都写明三件事：做法，回应的是哪条证据（证据 1–4 指消息里"本地证据"的编号），新增的东西为什么现有机制做不到。不含任务内容的检查（`neutral.test.ts`）、官方测试不进系统、10c 的并行和资源限制都保留。

## E1 需要计算的值，不由阅读定对错

**做法**（`judge.ts`）
- 判断给 `compute` 时，必须同时给 `where`：程序输出里放这个值的位置。位置的写法和库检查的断言目标相同，可以是整个 stdout、某一行、某个文件、文件的某一行、stdout 或文件里的 JSON 指针、CSV 单元格。
- 代码用库检查现成的取值函数（`verdict.ts` 新导出的 `valueAt`，内部就是 `actualOf`）取出程序在该处的值，再用 `sameValue` 比较：JSON 值按值比，数字有容差；文本去掉首尾空白后比。原来的做法是只要计算结果出现在输出的任何地方就算一致，这一条已经删除。
- 判断的每个结论都带 `rests_on`，取值 reading 或 computation。一个"错"如果标为 computation 却没有给计算，代码把它当作无效答案退回一次，并写明理由："依据计算的错不被接受，请改用 compute，给出脚本和 where"。第二次仍然这样，结论记为 cannot_tell，不进纠错单。
- 计算结果与程序的值不一致时，交给裁决会话，即配置里的 `adjudicate` 角色。请求里有原文、计算打印的值、`where` 以及程序在该处的值，没有脚本。三种结论照旧：程序错、参考错、有歧义。
- 提示词里把"需要计算"的范围写明了：算术、统计量、摘要、值是怎么产生的、排序、计数、位置。

**回应**：证据 1。
- P132：判断读 IQR 读错了。依据计算的错现在要改成计算，代码按 R2 的分位数公式算出 0，与程序写的 0 相同，代码判通过。
- P87、P315：判断说"摘要是 SHA-256"，这是对"值是怎么产生的"下的结论，属于计算。改成计算以后，代码算出 BLAKE2b-256，与 `sha256` 字段里的值相同，判通过。
- 短值碰巧出现在输出别处的问题，对应验收的第一条测试。

**新加的**：`where`、`rests_on` 两个字段和 `computedAgrees` 函数。原来的比较是在输出全文里找子串，没法知道"对应的值"在哪里。位置只能由写计算的一方给出，代码只负责取值和比较。

## E2 一本台账

**做法**（新文件 `ledger.ts`）
- `buildLedger` / `ledgerOf` 是一个纯函数，从 state 里已有的记录推出台账，不调用模型，台账本身也不存进 state。用到的记录有：
  - 每个周期的条目记录 `CycleRecord.items`（新加，见下）；
  - 每个周期的裁决 `CycleRecord.ruled`；
  - 执行方的回复（`note` 里的 CONTEST 行，或回复开头）；
  - 每轮结束时仍失败的条目 `ExecutionRecord.final`；
  - 工单带进来的条目 `ExecutionRecord.carried_in`；
  - 探针过期和检查过期、退役的事件；
  - 第 11 块的 `gapState`（未覆盖、关为不可测）。
- 条目身份：
  - 探针条目是 `P12/R1.S2.P6.s2`，也就是现有的 pairKey。如果探针的 cover 写了情况，条目上记录情况号；
  - 库检查条目就是检查编号 `K5`，挂在检查的全部 block 上；
  - 未覆盖条目用单位号或情况号本身。
- 每个条目记录：
  - 打开的轮次和周期；
  - 每次送修的周期，工单带入记为 `R<n> work order`；
  - 被停送的周期；
  - 执行方的回应；
  - 结论的变化，以及是由运行、裁决还是轮末得出的；
  - 在哪些轮末仍然开放；
  - 最后一次的输出摘要；
  - 结束方式：fixed、superseded、ruled_program_right、ruled_ambiguous、expired、uncheckable。
- 状态有三种：open（还在处理）、report_only（只列在报告里，包括过期、有歧义、关为不可测的）、closed（已结束）。
- 报告是台账的投影：
  - `report.acceptance.open` 改由台账算出（`acceptanceFromLedger`），并多了一项 `expired`；
  - 新增 `report.ledger`：按原因列开放条目，列出只报告的条目，本轮结束的条目各以什么方式结束，送修多少次，停送多少条；
  - 每轮检查点里另写 `ledger.json` 和 `ledger.md`，每个条目一行。

**回应**：证据 1、2。原来 P132 每轮、每个周期都重新出现，却没有一个地方能看出它已经送修了多少次、执行方怎么回应、最后怎么结束。未决的东西散在四处：纠错单、开放条目、缺口、裁决。

**新加的**：`CycleRecord.items`（本周期看到的条目：摘要、结论、送或停）、`ruled`、`held`，`ExecutionRecord.carried_in`、`final`。原有的记录里没有"送修时的输出"和"本周期对条目做了什么"，判断不了有没有进展，也算不出用了几个周期。

## E3 不做无效修补

**做法**（`execution.ts` 的 `Sends`，以及 `judge.ts`）
- 同一轮里，每个条目记住它上次送出时的输出摘要。工单带进来的条目算作已经在工作消息里送过一次。规则如下：
  - 新条目，或输出变了：送出；
  - 送过一次以后输出没变：交裁决。探针条目用 `ruling`，即 `adjudicate` 角色的独立会话，请求里带上之前的结论和 `NO_PROGRESS` 说明。库检查条目走第 9 块现成的 settle，争议类型是 contested；
  - 执行方写了 CONTEST 行：同一个周期里直接交给同一个独立会话裁决。原来是交给判断自己重判；
  - 裁决为程序对或有歧义：条目结束。裁决记成判断缓存（`Judgment.ruled`），输出不变就一直沿用，以后的周期和轮次都不会再出现这个条目；
  - 裁决维持"程序错"：条目成为"已确认"，本轮停送（记为 held），不再为它花周期（见下面"到期规则的修改"）；
  - 没有可用的裁决方时，送过一次、输出没变就直接停送。
- 一个周期里没有要送的东西时，执行就结束，不论条目是否还开着。开着的条目照常带到下一轮。
- 跨轮的有效期（`EXPIRE_ROUNDS = 2`，只对没有经过裁决确认的条目）：条目在连续两轮的轮末输出相同，中间又送过，就转为"只列在报告里"（expired）。下一轮不再带进工单；周期里即使被选中运行，只要输出还是同一个摘要也只停送不发。输出一变，条目重新打开。

**回应**：
- 证据 1：R5–R10 每轮 4 个周期都花在同样的误报上。现在误报最多占一个修补周期就转裁决，裁为程序对以后不再占周期。
- 证据 1 里 R6 执行方的说明（"已核对 IQR"）只是普通文字，没有形成异议。现在不需要执行方写 CONTEST 行：代码看到输出没变，就自己提出裁决。
- 证据 3（BLAKE2b 的共模失败）不是本块的检出目标。它在台账上表现为同一条目连续两轮无进展，按有效期转为只列在报告里，不再消耗周期。

**新加的**：`Sends`（同一条目在一轮内的送修状态）、`NO_PROGRESS`、`EXPIRE_ROUNDS`，以及判断选项里异议改走 `ruling` 这一点。原有机制里，同一个条目每个周期都无条件重送，裁决只在执行方写 CONTEST 时才会发生，而执行方实际没有写。

## E4 定向运行，每轮全量兜底

**"实际执行到"怎么由代码确定**（新文件 `coverage.ts`）
- 每个周期的程序用 `go build -cover` 构建。`goBuilder` 新加了第四个参数 `cover`，docker 构建用 `DockerOptions.cover`；配置项是 `coverage`，默认 true。
- 每次运行都把计数写进运行目录之外、属于这次运行的 GOCOVERDIR，运行后由 Go 自带的 covdata 转成文本 profile，只保留执行到的块。本机运行用宿主机的 `go env GOTOOLDIR`；docker 批量运行时，批量脚本在容器里调用镜像自带的 covdata。
- 代码把执行到的块按行号映射到函数锚点（第 6 块的 anchors 工具输出的 func 锚点），得到"这次运行执行了哪些函数"。
- 带覆盖构建的程序如果没有设 GOCOVERDIR，会往 stderr 打警告，所以三处都设了：本机运行、docker 批量运行，以及 docker 单次运行（设为 `/tmp`）。

**每个周期选什么**（`selectRuns`，每一项带理由）
- changed text：本轮原文改动的单位，包括本轮重新写探针的缺口单位，以及本轮新入库的检查和探针；
- open item：台账里开放的条目，以及本轮出现过的条目；
- executed a changed function：上一次运行执行到了本周期改动过的函数；
- no coverage yet：还没有覆盖记录的；
- everything：本周期的改动发生在任何函数之外，比如类型、包级别的值或 dispatch 表、文件顶部，覆盖跟不住，于是全部运行。规则是：改动过的锚点不在任何改动过的函数里，或者某个文件变了而文件里没有任何锚点变化。

库检查和探针用同一套选择。没选中的不运行，沿用上次的结果。

**全量兜底**
- 一个周期选中的都跑完，没有要送的东西时，在这个周期的程序上把全部库检查和全部探针各跑一批。
- 全量里输出变了的探针结论，只在属于回归嫌疑时才送判断：该对的上一个结论是 ok 或 wrong，或者从没有结论。上一个结论是 cannot_tell 或 ambiguous 的，记为"未判断"（cannot_tell），不花 token。
- 全量里输出与上次所见不同、而该周期没有选中它的，记为选择遗漏（`sweep.omissions`，记下它上次是在哪个周期运行的）。全量新发现的失败记在 `sweep.found`，还有周期就照常送修。
- 轮末保留的周期如果没做过全量，例如周期用完或回退到较早的周期，就在保留周期的程序上补做一次。这次全量就是这一轮最终的探针结论，串行不再另跑一遍 "final probes"。库检查的最终判定仍由 `runRoundChecks` 跑一遍，不花 token。
- 全量记录下每个检查和探针执行到的函数和输出摘要（`ExecutionRecord.coverage`，函数编号存成索引），下一轮的选择从这里开始。

**回应**：
- 证据 4：确定性重跑不花 token，但 §12g 每个周期全部重跑，耗的是容器时间；判断 token 的主要部分花在输出变了的结论上。现在周期里只运行被选中的，全量里只重判有回归嫌疑的。
- 证据 2（修补在别处改坏东西要能发现）：执行到被改函数的探针当周期就会被选中；跟不住的改动由全量兜住，并记为遗漏。

**新加的**：覆盖构建和 covdata 转换、`changeScope`、`selectRuns`、全量和遗漏记录，以及 `judgeIf`（全量里哪些对要重判）。现有机制里只有"锚点名字和对象名对应"这种静态关系，没有任何记录说明一次运行实际执行了哪些代码。设计要求"实际执行到"，只能来自运行时的覆盖。

## E5 一轮之内能命中缓存

**做法**
- 判断的各批、写探针的各组，请求开头都是同样的系统提示加同样的 `sources`（`requestJson` 本来就把 sources 放在最前面）。原来它们三个一组同时发出，第一波全部未命中。现在第一批（第一组）先发，其余的等它的第一个回复返回以后再并行发出（`warmFirst`），这样它们到达时，提供方的缓存里已经有了这个前缀。
- 报告里给出写探针方和判断各自的缓存读取占比：cache read ÷ (input + cache read)，写在 "Cache reads of input" 一行。

**回应**：证据 4（R10 判断 309k 未缓存、20k 缓存）。这一项代码能做的只有"前缀相同、别同时发"。缓存能不能跨周期保留（周期之间隔着编码，常常超过提供方缓存的保留时间）取决于提供方，需要看真实运行的这一行。如果占比仍然低，可以在本地的 OpenCode 提供方配置里看看有没有延长缓存保留时间的选项，这不在代码里。

**新加的**：只有 `warmFirst` 一个函数。

## E6 只做验收的回放

**做法**（`acceptance.ts` 的 `replayAcceptance`，命令 `intent-exp2-replay`）
- 逐轮建出 R1–RN：归属、库检查（以空程序为基线）、探针。state 里已有的就复用，`--state` 可以带入现成的归属、检查和探针。
- 对产物列表里的每份冻结程序，在它自己的 state 副本上：
  - 运行它所在轮次的全部有效库检查，B 类不一致交裁决；
  - 运行该轮次的全部有效探针，判断时带沙箱和裁决方；
  - 把结果折成该程序的台账。
- 不编码，不改程序。产物路径可以写成 `<repo>@<commit>`，表示 git 仓库里任意一次提交，会克隆到 `<out>/frozen/<name>`。
- 带 `--defects` 时，按缺陷表把库检查和探针两边的条目文字合起来匹配（`scoreTexts`），出一张表。
  - 库检查的文字是：检查的 key、block 和失败说明；
  - 探针的文字沿用 `scoreDefects` 的写法：探针 key、单位和结论。
- 输出：`<out>/replay.md`、`replay.json`，以及 `<out>/products/<name>/ledger.{json,md}`。

```
intent-exp2-replay --config <配置> --products <list.tsv> --out <目录> [--state <exp2-state.json>] [--defects <缺陷表>]
```

**回应**：消息要求验收能力的比较在同一份冻结产物上进行。原来的两个工具（`intent-exp2-detect` 只跑库检查，`intent-exp2-probe-detect` 只跑探针）各出一张表，只能做 R1，而且没有台账。

## 可能影响验收的地方

- **覆盖依赖镜像里有 Go**。docker 批量脚本里如果找不到 `go`，就没有覆盖记录，所有对象都是"no coverage yet"，每个周期全部运行，相当于退回 §12g 的做法，结果不会错，只是更慢。带覆盖的程序运行稍慢；每次运行之后的 covdata 转换在容器里大约 20 ms。
- **覆盖跟不住的改动**。同一个文件里，如果包级别的常量或变量和某个函数一起改了，代码只看到函数变了，读那个值的检查可能这个周期没被选中，要到全量时才发现（记为遗漏）。只改包级别的值、类型或 dispatch 表时，会全部运行。
- **只送一次就转裁决**：执行方第一次修补没改到点上，而输出恰好没变时，也会去裁决。裁决维持以后条目已确认，每轮送一次，不会被放弃，所以真实的缺陷最多多花一次裁决调用。
- **全量不重判 cannot_tell、ambiguous**：这些对的输出变了也不重判，结论记为"未判断"。它们在 §12g 下本来也不算 ok。
- **裁决调用的数量**：每个无进展的条目在每个输出上只裁决一次（判断缓存里的 contested 和 ruled 标记）。
- **有效期只管没经过裁决确认的条目**：经裁决确认的真实缺陷每轮都带进工单，直到修好；没有裁决方（或裁决没被请求）的条目，连续两轮无进展就只列在报告里。
- **R1 的检出均值 ≥13/19**：用 `intent-exp2-replay --defects`，这时库检查和探针合在一起算。单独用 `intent-exp2-probe-detect` 仍然只算探针。

## 本地运行

1. `npm run build`。配置不需要新字段：`coverage` 默认 true；docker 镜像里要有 `go`，它和 `timeout`、支持 `%N` 的 `date` 一样都是 docker 运行的前提。
2. R1 检出 ×3，按缺陷合并：
   ```
   intent-exp2-replay --config <配置> --products exp2/acceptance/r1-products.tsv --defects exp2/acceptance/r1-defects.json --out <目录-1>
   ```
   换 3 个 `--out`。每次都会重新写归属、检查和探针；如果要固定这些、只看判断的波动，就给 `--state`。
3. 冻结产物的回放：
   - 产物列表里写 `IC_rep1_R4	4	<app 仓库>@<R4 的提交>`、`IC_rep1_R10	10	…@…`，对照组的 R5/R10/R15 满分产物同样写法；
   - 看每份产物的 `products/<name>/ledger.md`：
     - R4 应有行号和主键排序的 program_wrong 条目；
     - R5–R10 不应有 P132、P87 那样依据计算的误报；
     - 对照组满分产物上的 program_wrong 应只是原文写明的偏离。
4. 修复：`intent-exp2-repair` 没有改动，它内部用 `executeRound`，所以 E3 的停送规则同样生效；那里没有 target，所以每个周期全部运行。IC rep1 R10 的产物先用回放出检出结果，再按 BLOCK11-NOTES 第 8 节的方式修复。
5. 串行：`intent-exp2-serial --config <配置>`。每轮报告看：
   - "Runs per cycle"：每个周期选了多少、按什么理由，以及全量的行；
   - "Selection"：在哪个周期做了全量，遗漏几个；
   - "Ledger"：开放、只列、本轮结束各多少，送修多少次，停送多少条；
   - "Cache reads of input"；
   - "Wall time"。

   检查点目录里的 `ledger.md` 每个条目一行。

## 到期规则的修改（第 12 块的补充）

依据：第 12 块的修改消息（基于 1a1064d）。

**证据**：原来的规则不区分裁决已经确认"程序错"的条目，送修过且连续两轮轮末输出相同就到期。对照组里最后修好的两个真实缺陷都拖了 4–5 轮：rep1 的 validate 行号 R4 出现、R8 修好；rep2b 的 log(0) R1 出现、R6 修好。按原来的规则，两者都会在修好之前被放弃。原来的 E2 测试断言的正是这种放弃。

**做法**
- **已确认**的定义：独立裁决给出过"程序错"，而且之后没有裁决改判。
  - 探针条目：判断缓存里该对有 `ruled` 标记、结论为 wrong 的判定。这包括对无进展或 CONTEST 的裁决，也包括独立计算与程序不一致、裁决为程序错的情况，后者现在同样标为 `ruled`；
  - 库检查条目：state 里 `rulings` 有该检查的 `check_right`，任何争议类型都算（reference、contested、position 等）。
  - 台账按轮次取截至该轮的最后一次裁决，算出 `LedgerEntry.confirmed = { round }`。没有经过独立会话的判定（没有配置 `ruling` 时由判断自己重判）不算确认。
- **已确认的条目不到期**（`ledger.ts`）。它只在三种情况下结束：修好（fixed）；原文被取代（superseded）；后来的裁决改判，探针条目走 cycle 的 ruled 记录，库检查条目走裁决退役事件。没有确认的条目，到期规则不变。
- **每轮送一次，本轮内不变就停送**（`execution.ts` 的 `Sends`）：
  - 串行把台账里开放且已确认的条目作为 `target.confirmed` 传入执行，并照常把它们带进工单。工单里带入算作本轮的一次送修，纠错单里注明"an independent ruling confirmed this finding"；
  - 工单不带入的库检查条目，在本轮第一个失败的周期送一次；
  - 之后输出不变就停送，不再请求裁决（结论已经缓存），不占周期；输出变了而仍然失败，照常再送。
  - 本轮内刚被裁决确认的条目（settle 维持、或探针结论带 `ruled` 且为 wrong），在本轮剩下的周期里按同样的规则处理。
- **随之改变的一点**：第 12 块原先规定"裁决维持后再送一次，再不变才停送"。为了满足"每轮只为它花一次送修"，现在裁决维持以后直接停送：这一轮已经送过一次，下一轮工单再带入。
- **台账和报告分开显示**：
  - 台账每个条目有 `confirmed` 字段，`ledger.md` 多一列 confirmed；
  - `LedgerSummary.confirmed` 列出开放且已确认的条目，`report.acceptance.open.confirmed` 同样；
  - 报告的 Ledger 一行写成 "open program wrong n (confirmed by a ruling m)"；到期、只列在报告里的仍在 "listed only" 里，按结束方式计数。

**新加的**：只有 `confirmed` 这个字段，以及 `Sends` 的 `confirm`。确认的依据是已经存在的记录（裁决过的判断缓存和 rulings），没有新的模型调用，也没有存储新的东西。
