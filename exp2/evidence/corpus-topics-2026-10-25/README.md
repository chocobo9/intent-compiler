# 语料扫描：对象 vs 话题（2026-10-25，零模型成本）

目的：用户提出"对象是过拟合风险最大的一层；对象应当是话题"。本扫描只看 EvoCodeBench 全部 26 个任务、227 轮原文的结构，回答两个问题：(1) 我们的"对象 ≈ 命令/节"在多少任务上成立；(2) 原文里有哪些对象模型装不下、话题模型装得下的东西。全部为观察，正则计数粗糙（self_ref 会把 `v2` 之类也算进去），只看量级。

脚本：corpus-profile.py（结构画像）、topics.py（话题模式计数）；输出 profile.txt、topics.txt、corpus-profile.json。

## 1. dpipe 在语料里的位置

| 指标 | dpipe（d5_w9）| 26 任务范围 |
|---|---|---|
| 标题数 | 161（最多之一）| 0–228；9 个任务 0 标题 |
| 命令样标题占比 | 55% | 0–96% |
| 重复标题（同名节跨轮再现）| 72（最多）| 0–72 |
| 跨命令变更线索（"changes to X""all commands"）| 1 次 / 15 轮 | 0–8；9 个任务 0 |
| "未改部分照旧"的范围声明 | 1 次 | 0–18 |

读法：dpipe 是全语料里**最按命令分节、最爱用同名节跨轮重现**的任务，同时是**跨命令变更最少**的任务之一。"对象 = 命令节"在 dpipe 上几乎是文档替归属做好的；我们的对象层是在最适合它的任务上长出来的。这是过拟合风险的直接证据。

## 2. 语料里的四种"话题级"写法（对象模型装不下的）

1. **一个概念改变多个命令**（30 轮出现）。d8_w5 第 3 轮："迁移到语义化版本"，随后 "Changes to validate / build / diff / promote" 四段；d11_w2 第 6 轮：范数改为无穷范数，影响 sparse-solve、poisson、convdiff、heat 四个命令的输出；d8_w5 第 2 轮："所有部署相关命令现在必须写事件日志"。话题是"版本格式""范数""事件日志"，它们不是任何一个命令，却决定四个命令的行为。现在的模型只能用 applies_to 边指向对象，边到不了句子，rep1l/rep1m 里这种边一次没起作用。
2. **范围声明**（61 轮出现）。"All existing endpoints and behaviors not mentioned above continue to operate as previously specified"（d10_w4 每轮都有）、"All behavior from rounds 1 through 4 continues to hold without regression"（d12_w1 第 5 轮，接着列了 13 条早轮特性）。这是作者在说"守卫范围"，是话题级的，现在没有任何机制读它。
3. **文档自带索引**（66 轮出现）。d12_w1 用 F12…F27 给特性编号，后文全靠编号引用；d3_w9 "Correction (Section 21)"；d5_w1 用 2.5 这类节号；d10_w12 "conflict with v2–v5"。作者自己的编号系统比我们的 O# 稳定，而且是跨命令的话题编号（F16 = 结构化输出引用，被多个命令用）。
4. **显式新旧并列**（34 轮出现）。d5_w5 第 9 轮 "### Previous behavior / 新公式"；d3_w9 "Previously it averaged ALL steps… The corrected behavior…"；d10_w4 "demoted to staging instead of archived"。作者已经写了新旧并列，我们的修订记录是在重做一遍作者做过的事。

另：69 轮含 bug 修复类文本（棕地任务 d1_w11 整轮是三份 bug 报告：复现步骤、根因、要求的修法）。对象模型把它归到命令上没错，但"根因在 get_src_mtime 忽略 package.forge"这种话指的是代码位置，不是需求对象。

## 3. 对"话题"假设的含义（推断，未验证）

- 命令仍是最常见的单位（115 轮有命令段落），话题不是替代命令，而是命令之上的一层：一个话题管几个命令里的几句话。
- 话题的边界由作者的写法给出的比例不低（范围声明 + 自带编号 + 新旧并列合计覆盖约一半的轮次）。这些是可观察的文本特征，不需要模型"读出主旨"。
- 现在归属记的 applies_to 边是在用对象级边模拟话题，粒度不够，所以零收益。
- 过拟合的具体形状：对象层在 dpipe 上几乎零成本成立，在 d10_w4（0 标题、每轮范围声明、78 处自引用）这类文档上，对象要靠模型硬切，话题反而是现成的。

## 4. 下一步可零成本做的

- 挑 3 个与 dpipe 形状相反的任务（d10_w4 migration_upgrade、d12_w1 flowr、d8_w5 pipeline.sh），用现有归属跑一次离线（只归属，不执行），看对象怎么切、applies_to 边有多少、范围声明和编号被丢掉多少。这要模型调用，但只是归属一步，便宜。
- 在 dpipe 上找跨节话题样本（校验和、行号起算、空值处理），看现在的对象里怎么散落——用户之前提的第 2 项。
