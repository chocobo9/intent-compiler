## 首答失败的根源（按根源合并）

1. **refers_to 指向对象**：R6、R9、R11、R12、R15 共 5 轮。
   - 模型很自然地写出"这段引用对象 O20（共享错误约定）"。
   - 代码只接受原文块作为目标，报错写成"O20 does not exist"，与事实不符，O20 是存在的。
   - R6 因此丢了语义：全局 `--audit` 本应以"适用于"作用到各命令。修补时模型照着报错把目标换成了原文块，于是各命令都不会进入任务区。
2. **上级小节与子小节同时被归属**：R1、R9、R10 共 3 轮。
   - R9 和 R10 里，上级和子小节归给的是同一个对象。
   - R1 里，上级被标为 none。
   - 按根源合并后的报错一次就能修好。
3. **检查推导：用文字描述的值写成了逐字引用**：R1 9 条，R2 6 条。例如引用"填空字符串"，期望值写 `""`；引用"文件写到 X"，期望值写"存在 = true"。
   - 代码判不符是对的，这个值在原文里并不逐字出现。
   - 但报错没有指出应该改走推导，由参考脚本复核。
4. **检查推导：依据是共享约定的原文**：R1 1 条。filter 的报错检查引用了共享"错误"一节，那一节点名了 filter。
5. **检查推导：故意构造的错误摘要被当成手算值**：R1 1 条。修补时模型改用 `{{computed:OTHER}}`，由参考脚本对多一个字节的内容求摘要，路径正确，不需要额外提示。
6. **检查推导：推导值缺参考脚本**：R3 1 条，一次修好。

## 语义层面的观察（代码核对查不出来）

- **R15 对不可切分块的部分修订**：R15 只把 snapshot 的 row_hash 从 MD5 改为 SHA-256。但 R13 里写着 MD5 的 JSON 示例和字段表都是不可切分的整块，模型只能把整块标为被替换，于是示例和表里仍然有效的其他字段也从"当前原文"里消失了。
- **R5 末尾的改动清单**：这段只是复述上文，模型把它也当成了各对象的新增内容。不会出错，但任务区会出现重复条目。
- **R8、R10 的解释**：R8 的"一致性对 int/float 必为 1.0"，R10 的"`blake2b` 字段指 R1 示例里的旧字段"，两条解释都正确。
