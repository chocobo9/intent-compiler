## 4. 原文与对象（已定；经 Fable 两轮讨论和用户确认）

**4.1 什么算一个对象**
- 对象的身份**只看原文**：原文用一个稳定的名字指称它，并且它的各部分会一起被修订。参数、字段、选项永远不成为对象，它们是对象的内容；它们被修改时，算作对象的一次部分修订。
- 能不能验收不影响一个东西是不是对象，只影响它的状态。写不出检查的需求也照样是对象，照样进任务区由执行方按原文实现，只是状态为"未知"。
- 不预先声明对象的类型。"有没有自己的检查""有没有被别的检查用到""有没有成员"都由代码从登记的数据算出来，状态按同一套算法计算。
- 第 1 轮宁可切细，只在原文自己分条的地方细分。之后合并便宜，拆分贵。

**4.2 轴心：原文，按需细化的三层（已定）**

代码按文本结构切出三层并编号（只追加，永不改动）；模型读完整原文，理解语义后，为每一块选**能单独归一个对象的最粗那一层**。

| 层 | 代码怎么切 | 什么时候用 |
|---|---|---|
| 小节 | 一个标题及其下的全部内容 | **默认**。大多数新增内容一整节就是一个对象 |
| 段落 | 小节内按空行切；代码块、JSON 样例、列表整体不拆 | 一节里写了几个对象时才细分 |
| 句子 / 子句 | 段落内按句子切；需要时再按逗号、分号、括号切到子句 | 只在一段话混着说了几个对象，或"部分修订"要指明改了哪一句时用 |

- 每一块恰好被覆盖一次，由代码核对没有遗漏、没有重复。归属可以是一个对象，也可以是 `none`：每轮的前言、分隔线这类不是需求的文字。R1 的前言（用 Go 写、确定性）是真需求，要归给对象。
- 列表项、代码块、表格作为一个单元，不往句子切；但为了指明部分修订改了哪里，**列表项可以切到子句**（按逗号、分号、括号切，行内代码里的不切）。默认归属仍然取最粗的一层（第 1 块评审，已定）。
- 宽松列表（项与项之间有空行）在空行处切段，这样操作列表才能按操作分开（第 1 块评审，已定）。
- **归属是索引，不是切文本。** 交给模型和执行方的永远是完整的小节或段落，连同它所在的标题，归属的部分只是标出来。绝不交孤立的句子。每轮的完整原文仍然交给模型做当轮理解。【2026-10-23 已改，见 §12j.7 第 6、9 条：模型每次拿的是本轮增量加按关系取出的早轮块，不再是累计全文；全文只作消融。】
- 拆分或合并对象时，模型只说明各块如何重新分配，新旧对象的对应关系由代码按块的归属算出来。轴心不会漂移。代码锚点是第二条轴：执行报告和 AST 会让函数跟着对象走。
- 拆分和合并放到第二版。第一版只记录代码给出的"疑似该拆 / 疑似该合"信号，例如两个对象总是被同时修订、锚点高度重合。

**4.3 跨对象关系：只来自原文写出的句子**
- 一处原文写到别的对象时记成一条边，**边分两种**（第 1 块评审，已定）：
  - **引用定义**：这一块用到另一个对象定义的东西，比如"aggregate 的 having 使用与 filter 相同的条件语法"。边指向被引用的那一块。被引用的块被修订时，代码沿着这条边把相关检查标为过期，并在工单里附上被引用的原文。被引用的对象本身没有改动。
  - **适用于**：这一块提出的要求也落在另一个对象上，比如 R5 的"`ingest` and `transform` must remove it"归给 ingest，同时适用于 transform。被指向的对象也得到一条改动记录（来源记为这一块），升一版，进入本轮范围。
  - 两种边都只能由原文措辞本身点到的对象来标。归属仍然只有一个，轴心不变。
- 代码按名字找出新原文可能牵涉的已有对象，作为**候选**交给模型。模型只能回答"第几块本身的措辞写到了它"或"没写到"，不能回答"按理应该包括"。
- **不允许由模型归纳的规则自动生成对象或任务**。比如不能从几轮原文里归纳出"每个命令都对应一个 pipeline 步骤"，再去自动派活。
- 原文漏写的跨对象影响，只记一个**缺口信号**，放在状态区：不派活、不验收，接受这部分损失。原文是唯一权威。

**4.4 改动与修订**
- 每轮新原文到来时，模型判断每一块属于哪个对象，是新增、修订、撤回还是部分修订。代码据此登记改动、给对象升版本，并把被替代的旧块标为"被替代"或"被部分修改"。
- 改动类型按"对旧原文的影响"来定义，写在 schema 的说明里。这是定义，不是判断规则；判断仍由模型做（第 1 块评审，已定）：
  - 新增：没有旧原文因此不再成立；
  - 修订：某块旧原文整体被新原文取代；
  - 撤回：某块旧原文整体不再有效，且没有替代；
  - 部分修订：某块旧原文里有一部分不再成立，其余照旧。
- 替换目标只能是当前有效的原文。指向已被替换的旧块属于确定的错误；报错时要指出现在有效的是哪一块，方便一次改对。
- **部分修订用编号表达，零复制**：记录为"旧块的哪几句或哪几个子句，被新块的哪几句覆盖"。代码切出对应的原文，并排展示；模型不复制任何原文。编号越界或为空，就退回给模型。并排展示时，旧的一侧给被改单元所在的整段加上标题路径，而不是整节（第 1 块评审，已定）。
- 原文自相矛盾时，以新原文为准，这属于状态更新。只有同一轮内两块不一致，或部分修订的范围不清时，模型才写一条解读，附上依据的块，并标明"这是解读，不是原文"。权威仍然是原文。
- 完整原文按对象分组交付：v8 已验证每段逐字只出现一次，零复制；按小节归属后，单独一行的标题自然跟着它下面的内容走。【2026-10-23 已改，见 §12j.7 第 6、9 条：模型每次拿的是本轮增量加按关系取出的早轮块，不再是累计全文；全文只作消融。】

**4.5 共享约定**（报错格式、CSV 读写、确定性、seed 默认值、JSON 缩进等）
- 共享约定也是对象，有自己的版本。
- 验收是间接的：检查库里使用了某个约定的检查都要标注 `uses`（由模型标注，代码补充核对：期望里出现了约定的关键形式却没标注的，退回给模型）。约定相关的断言要单独成条，不和业务输出混在一起，这样才能分清是约定没做对还是业务没做对。
- 约定被修订时，代码把所有标注了 `uses` 的检查标为过期，模型只对这一批检查重新推导一次期望，不重推全库。用到这个约定的对象会出现在任务区的"受约定修订影响"小节里。

**4.6 模型调用的形态（第 1 块评审，已定）**
- **首答和修补用同一个 schema、同一个系统提示**：首答就是对一份空草稿打补丁。请求的开头是原文，后面依次是稳定的部分，上次的答案和代码找到的问题放在最后。这样修补可以复用首答的前缀缓存；这是实测中唯一能命中缓存的形态。其他需要多次调用的环节也照此处理。
- 第一版照样把全部原文交给模型；要不要裁剪，等真实运行拿到成本数据后再定。【成本数据已到：15 轮 R2 工单 64.6k 字符、R3 执行方缓存读 6.3M，见 §12j.7 第 9 条；裁剪为默认。】

## 6a. 原文的运行逻辑（已定，2026-10-23，用户确认；取代 §2.3、§4.2、§4.4、§6 原文区里"每轮把全部原文交给模型"的写法）

原则一句话：**每段原文只被模型读一次；之后谁要它，由代码按关系取给谁。** 早轮的要求不靠模型重读来记住，靠守卫来守。

按一轮的顺序：

0. **入库（代码）**：本轮原文切成节、段、句、子句，编号，追加进注册表；旧原文永不改动。
1. **归属与修订（模型读本轮，代码记关系）**：模型只读本轮原文，加代码挑出的候选（名字、命令、字段与本轮重合的早轮对象的块）。它回答：每块归哪个对象；本轮哪一句修订或撤回了早轮哪一句（细到句和子句，不是整段）；原文写明的跨对象关系。代码登记：对象升版本、被取代的旧句、关系边。这一步是地基，要有度量：本轮带 now / instead of / previously / no longer 等句子的段落里，归属记了几条修订，进报告。
2. **当前有效视图（代码）**：对每个对象，从历史算出"它现在的要求"：仍有效的句子按原位置排好，被取代的不出现，部分修订的只换那一句。模型看的永远是这个视图，不是两句原文加"新的为准"的标记。
3. **本轮包（代码按关系取）**：给执行方的只有四样：本轮新增/修订对象的当前有效视图；这些对象通过关系边连到的早轮对象的当前有效视图；**落在以上对象上的守卫列表（保护区：这些调用现在的输出，不能改坏，改完会重跑）**；上一轮未修完、代码确认过的条目原话。早轮其余要求不给。
4. **执行方编码（模型，新会话）**：读本轮包，写代码，目标环境试跑。它的记忆是仓库代码加本轮包。
5. **守卫（代码，不花 token）**：全部守卫在新程序上重跑。翻转的守卫先问：它背后的句子本轮是否被修订（第 1 步的关系）。是：被取代，交审查员确认后退役，附新旧两句；否：退化，送修。修补改坏别的守卫时，退回的是代码改动，发现保留，下次再送。
6. **审查员发现（模型，带工具，新会话）**：拿本轮包，加翻转的守卫（附新旧原文）和线索（假设检查的失败）。自己跑程序，报偏离，每条指向原文编号。
7. **定位（代码）**：每条偏离落成检查：输入先从线索取，再从审查员会话写过的文件和跑过的命令取，最后才让模型从文字重建。两条前提：所指句子仍有效；当前程序上复现。过了送修，修好固化为守卫。每条偏离必有一个结局，总数守恒。
8. **轮末（代码）**：库检查终判、守卫覆盖、台账、报告、检查点；成本按角色分列，假设检查的写作成本单列。

整条链：原文块 → 修订关系 → 对象版本 → 当前有效视图 → 关系闭包 → 本轮包 → 守卫 → 下一轮。2026-10-23 的现状：前三环有（第 1 环在 15 轮 R3 上块级召回满，但只有一轮一题的数据，要按 §12j.7 第 12 条持续度量）；第四环能算没用；第五、六环待做（§12j.7 第 9 条）；第七环有但顺序错（§12j.7 第 11 条）。全文交付（all/full）只作消融。

## 6b. 权威表与守卫规则（已定，2026-10-23 晚，用户确认）

### 项目身份（与 PROTOCOL 同文）
IC 是 harness 内的一层：**把需求原文切成带版本的句子，把审查员确认过的发现固化为绑在这些句子上的、由代码持有并每周期免费重跑的检查（守卫），用归属记录的修订关系而不是模型判断来决定一条守卫在原文改动后是被取代还是退化，并只按本轮改动和关系向执行方与审查员交付原文。**它的目标量是跨轮的返修减少和成本可控（§6b 三句话）。它的中间表示（单位编号、关系边、台账）只供系统内部使用，不暴露给用户；远期形态是 agent 系统内部的 AI-native 语言，现阶段只做"长时程任务稳定性"这一实际版本。叙事上不脱离 harness，不做跨代理共享接口。

### 三句话（其余都是可替换的实现）
1. 验证状态由代码跨轮持有：确认一次、免费守住，换的是审查成本。
2. 一个发现只有在当前程序上复现了才算数；共识不算数。
3. 归因从记录里读，不让模型回看日志。

### 权威表：每种事实只有一个主人，别处只读
| 事实 | 唯一主人 | 谁只能读 |
|---|---|---|
| 哪句原文现在有效、被哪句取代 | 归属登记的修订记录（块状态） | 过期、守卫翻转分流、带入、当前有效视图、本轮包 |
| 对象之间有什么关系 | 归属登记的关系边（只来自原文写明的句子） | 本轮包的关系闭包、保护区 |
| 对象现在要求什么 | 当前有效视图（由前两项算出） | 执行方、审查员、写检查 |
| 某个调用在某个程序上的输出 | 运行记录（代码跑出来的） | 守卫状态、翻转、复现 |
| 一条发现的来源和结局 | 台账（单位 + 版本 + 结局） | 报告、带入 |
| 程序在哪个状态 | git 提交 | 回退、首次交付 |

读的一方不得自行补判断（按引用推断过期、对象名出现在输入里之类的补丁，就是混乱的来源）；主人不准时修主人并度量主人，不在读的一方加规则。管理层和验收层各自的机制只要读同一个主人就不会打架。

### 守卫规则（三条）
守卫挂在原文的句子上，不挂在代码上。改了一个函数不会让任何守卫退役。
1. 句子没改、守卫翻了 → 退化，必须修回；新守卫（来自新发现）与旧守卫并存，各守各的句子。
2. 句子改了（修订记录）、守卫翻了 → 被取代，交审查员确认后退役，由新句子产生的新守卫接替。
3. 句子改了、守卫没翻 → 仍有效，留着。
守卫的期望值来源要记（verbatim / derived / computed）；派生值守卫的退役同样只走修订记录。翻转的分类先于任何回退（§12j.7 第 11 条）。

## 6c. 视图、本轮包、审查请求的规则（已定，2026-10-24；§6a 第 2、3、6 步的细则，串链块的依据）

### 当前有效视图（对象 × 轮次 → 一段原文）
1. 取该对象在该轮之前（含）归属到它的全部块，按轮次、再按原文顺序排。
2. 状态为 superseded / withdrawn 的块不出现；替换它的新块出现在新块自己的位置（不搬到旧位置）。
3. partially_modified 的块：被覆盖的句子/子句原位换成覆盖它的新句子；块的其余部分不动。列表项按项换，代码块和表格整块换（部分修订到不了它们内部）。
4. 撤回句本身不出现；撤回时附带的新义务（如"已有的要删掉"）作为新块出现在撤回所在轮的位置。
5. 标题路径保留一行；不加任何"新的为准""已修订"之类的标记。视图里每个句子仍带原编号，供审查员和定位引用。
6. 视图是纯函数：同样的注册表给同样的视图；可缓存，按对象版本失效。

### 本轮包（第 n 轮）
1. 对象集合 = 本轮新增或修订的对象 ∪ 这些对象通过归属记录的关系边（refers_to、applies_to，及第 13 块加的 same_rules 等）**一跳**连到的早轮对象 ∪ 未结条目依据句所在的对象。只走一跳；两跳以上由守卫守。
2. 每个对象给当前有效视图；本轮新增或修订的对象排前，早轮对象排后，各标"本轮"或"早轮，因 <边> 带入"。
3. 保护区 = 以上对象上的守卫，每条：命令、输入文件名、当前输出摘要、依据句编号；不给期望值的推导过程。
4. 未结条目 = 上轮送过、基线上仍失败的确认条目，原话加依据句编号。
5. 字符上限：本轮原文的 3 倍；超限时先去掉早轮对象中"depends_on"类带入的，再去掉守卫列表的输出摘要，不去掉本轮对象。超限次数进报告。
6. 归属没有记到的关系，包里不补推断；缺失由第 13 块的关系召回度量暴露。

### 本轮包的修订（提议，2026-10-25 晨；依据 rep1j 六轮的利用率度量）
事实：rep1j 中审查员发现引用到的对象全部在包内（无漏）；边带入的 O2、O4、O5 由 R1 的两条站在早轮的 applies_to 边逐轮拉入，R3–R6 一次未被引用；包在后期与全文同量级（45–55k 对 55–70k）。
1. 边只在本轮的句子指向早轮对象时才带入；早轮已存在的边不逐轮重带（其内容当时已交付，现由守卫守）。
2. 边带入到句或段（按来源块在目标对象里取同名/同命令的段落），取不到才退到对象视图。
3. 未结条目带依据句加所在段落，不带整个对象。
4. 守卫的两个用途分开：**守住**（别改坏）全由代码重跑、回退、送修完成，不向模型交付任何清单；**对照**（改一条早轮规则时现在绑在它上面的行为是什么）只交付本轮被修订句子上的守卫（命令、输入、当前输出，附新旧两句），其余一条不给。编号清单是否保留由一次消融（原文未改的翻转次数给/不给）定。
5. 上限改为绝对预算（起点 40k 字符），超预算按相关性裁：早轮边带入先裁、未结条目的段落次之、本轮单位不裁。
6. 每轮报告利用率：审查员引用到的对象 / 包内对象；执行方改动碰到的对象 / 包内对象。以后以利用率而非大小判包是否合理。
以上替换本节第二节第 1、3、5 条（待用户确认）。

### 审查请求（第 n 轮，每次审查）
1. 正文 = 本轮包里的对象视图（同执行方），不含守卫列表。
2. 附三段：本轮新增/修订的单位编号列表；翻转的守卫（命令、输入、期望与实际、改动前后的句子）；线索（最多 20 条，按守卫覆盖缺口优先）。
3. 早轮原文只以上述方式出现；审查员不再拿累计全文。对照组仍拿全文，这是两组方法的差异，不是对称项。
4. "没有新发现"= 本次审查没有任何条目存活到送修；条目去重按（依据句，输入）相同即同一条，不同输入算新。

## 7. 执行方：IC 控制过程（已定方向，细节为提议）

- IC 不管代码具体怎么写，但要管住过程：可以复用缓存，失败时保留正确的那部分产物，不需要整体重启。
- **分步（已定）**：执行方在 IC 给定的对象范围内**自己提议**怎么分步，每一步写明覆盖哪些对象（完整覆盖或部分覆盖）。允许"共享基础"这样的步骤，例如一个同时服务 filter、derive、aggregate 的表达式解析器。引用边只作为参考信息交给执行方，不作为先后约束。代码按锚点核对每一步：
  - 声明覆盖了某个对象，却没动它的锚点，退回；
  - 动了没有声明的对象的锚点，就跑那个对象的保护检查。
  代码只限制形状：步数上限，每步的对象数上限，每个对象被部分覆盖之后必须有一步完整覆盖它。每完成一步提交一次 git。
- **git 只作事实底座，语义外挂。** 提交、diff、回退由 git 完成；提交说明末尾用 git trailer 写统一词汇里的编号（例如 `IC-Step: P10.3`、`IC-Object: O.fill@v2`、`IC-Checks: K.fill.07 pass`），代码只读这几行，不读自由文字。这与 SpecArt 的"代码骨架加摘要"是同类思路，有现成的就直接用。
- **给模型看的是投影**，不是提交日志：IC 按对象挑出相关锚点在这些提交里对应的那几段 diff，再加上原文段落和检查结果。
- **每步验一次**：IC 在每个检查点跑构建和相关检查，通过的步骤保留。
- **失败时接着做**：在同一个会话里继续纠正，复用上下文和缓存；会话坏了，就从最后一个好的检查点另开会话，只交剩下的步骤。
- **预算和超时按步计**：超出时保留已完成的部分，没完成的进下一轮的任务区。
- 执行报告的格式固定：每一步为哪些对象改了哪些锚点，跑了什么，结果如何。代码核实锚点确实存在、确实改动过。

## 8. 验收：检查库（经 Fable 两轮讨论；第一版最小集合已定，扩大覆盖面的办法为提议）

- **权威**：原文段落，加上在当轮程序上实际运行、期望值能追溯到原文的检查。状态由代码按规则计算，模型不直接给出"已落地"。
- **模型做理解**：判断一段话里有没有可检查的东西、构造检查输入、推导期望、对照原文找出不符之处。**代码做判定和执行**。
- **检查入库**：命令名、选项名必须出现在原文的代码片段里。期望值要么逐字来自原文，要么由两种方法分别得出且一致（方法 A 直接推导；方法 B 写参考脚本，由代码执行）。
- **失败先判原因**：值不符，或命令、选项没实现，判未落地并派任务；调用被拒但功能存在，或触发了别的报错规则，判为输入可疑，算"未知"，不派任务。
- **区分做没做（已定）**：一条检查算"强"，要同时满足两个条件。
  1. 它在**代码构造的基线**上失败。基线永远不是执行方的工作树：第 1 轮的基线是代码生成的、对任何调用都以 exit 1 结束且无输出的程序；之后各轮的基线，是代码从上一轮**验收通过的提交**构建出的程序。
  2. 它至少有一条**和数据有关的断言**：期望里有来自样例输入、或由输入算出来的内容，而不只是退出码、命令存在或帮助文字。
  对象至少有一条强检查通过，才算已落地。对"撤回"类的修订，方向反过来：强检查应当在基线上通过、在当前程序上失败。
- **回归**：每轮把检查库全部重跑一遍，不花 token。
- **执行方异议**：必须附上实现位置和一条可运行的替代调用。最好的结果是把检查降为"未知"，不能借此变成"已落地"。
- **坏检查**：派过纠错、代码也改过、检查仍失败，连续两轮后不再派。
- **第 2 块评审的决定（已定）**：
  1. **和数据有关的断言**：读取产出内容（stdout、文件、JSON、CSV）且本次调用带有输入的断言，以及期望文字里带着输入内容的断言（例如 `ERROR: file not found: nope.csv` 里的文件名），都算和数据有关。只有退出码、文件是否存在、帮助文字的不算。
  2. **"未知"类的失败不阻止已落地**：输入可疑这类失败照样记录、照样展示，但不参与判定。同一条检查连续两轮都判为输入可疑，就退役。
  3. **原文被修订后，旧检查由代码自动标为过期**：检查所依据的原文块被替代，或者它引用的那几句被部分修改时，标为过期，不参与判定，等待重新推导。模型的退役建议只作为提议，代码核实这条检查确实依据了被修改的原文，才接受。这一项不等传播那一块，现在就做，否则旧检查会在正确的程序上失败，造成误判。
  4. **漏标 uses**：保持保守的判定，漏网的情况记录下来，留到真实运行时再看。
  5. **"命令没实现"**：原文点名的单元（命令、选项、操作名，以及等于某个对象名的输入值）在程序的源码里根本找不到，就判为没实现。
  6. **推导不一致按单条断言处理**：不一致的那条记为未知，其余的照常入库。
  7. **强弱在入库时判定一次**，之后不随基线变化而重算。
  8. **每条检查必须写明期望的退出码**，缺了由代码退回。
  9. 沙箱：真实运行时换成 docker，参考脚本也在容器里运行（由本地负责）。请求大小先不裁剪。
- **扩大覆盖面**（用现有方法，小模型留作底牌）：
  1. 参考实现差分：模型照原文写一个独立的参考实现，代码生成大量输入，同时跑参考实现和我们的程序并比对输出。结果不一致时，由模型对照原文判断哪边对。这能覆盖"原文写了规则、没写结果"的行为。
  2. 性质检查：提取原文写明的不变量（排序、确定性、计数），在随机输入上检查。
  3. 对照阅读：模型读原文和本轮改过的代码，指出不符之处。只有能变成检查的，才算证据。
  4. 执行方自己写的测试：只作信号，不作权威。
- **小模型路线**：验收里的判断大多窄而重复，现阶段用大模型加结构化输出，把每类判断的输入输出格式固定下来，作为以后训练小模型的数据来源。
- **第一版最小集合**（Fable 的建议）：
  - 逐字检查；
  - 失败原因分类；
  - 强弱区分；
  - 缺名反证：原文代码片段里的命令名、选项名、JSON 键，在代码里找不到；
  - 只接受可运行证据的异议；
  - 两种方法都一致才入库的推导检查。
  参考实现差分是否进入第一版，**未决**。

## 9. 每轮流程（提议）

1. 代码切分新原文，生成段落编号。
2. 模型对新段落分类和归属。代码登记改动、给对象升版本，并算出本轮范围。
3. 代码抽取锚点，读取检查库在当前程序上的状态，生成分区工单。
4. 执行方在任务区的对象范围内提议分步，代码核对分步的形状。
5. 执行方逐步编码。每步提交一次，IC 跑构建和相关检查，失败就在会话里接着纠正。
6. 模型为本轮新段落抽取或推导检查，代码核实后入库。
7. 代码在最终程序上重跑全库，计算各对象状态，生成本轮记录和下一轮的输入。

## 12b. 第 6 块的决定与同步（已定，2026-10-20）

**第 6 块提出的五个问题**

1. **共享约定引起的过期**：约定被修订时，用到它的对象（载体）进任务区，因为载体的代码要跟着改。只因依据块被修订或 refers_to 引起的过期，对象不进任务区，只在本轮重新推导检查（补充一）。
2. **算出来的值**：摘要、哈希这类要计算才能得到的输入或期望值，一律由代码执行方法 B 的参考脚本得到，模型不手算。这样 MISMATCH 只剩一种含义：程序的值不对，判"值不符 → 未落地"。方法 A 与方法 B 不一致时照旧不入库，记为未知。
3. **429**：普通的限流（429、rate limit）短退避后重试几次，计入本次调用的重试；只有明确的额度用完提示，才走第 14 节"每 30 分钟续跑"。两者按返回内容区分，分不清时按限流处理，重试用尽再按额度用完处理。

5. **Go 构建缓存**：单独提供一个只用于构建的缓存卷选项，不走 `runner.extra`；检查运行不挂这个卷，保持"只有输入文件"的隔离。

**本地验证第 6 块时发现的环境问题**

3. **编码会话的命令在哪里执行**：由本地决定，不归开发。SDD 单独执行是在 `sdd-unattended-preflight` 镜像里无人值守地运行的。本地接入时先核实它的编码代理是否也在容器里执行；如果是，OpenCode 也放进同一个镜像运行，保证"其他条件一致"。
4. **环境拦截时停下等人**：同意。不定时重试。
5. **识别不了的手写摘要**（base64、截断的前缀）：接受这个盲区，不加识别规则。

下面几条都是这批录音里反复出现、按根源归并后的问题。修法都在代码、schema 或词汇定义上，不加"看到 X 就怎样"的规则。

1. **refers_to 可以指向对象**（5 轮出现）。
   - "这段沿用共享错误约定 O20"本来就是引用一个对象。代码把对象目标确定地解析为该对象在这一轮的当前原文；那段原文被修订时，引用它的检查过期。指向原文块的写法照旧可用。
   - 系统提示里把两种边的含义写清楚：
     - refers_to：这段依赖那段原文或那个对象，那边改了，这边的检查要重推；
     - applies_to：这段改变了那个对象的行为，那个对象得到改动记录、进入任务区。
   - 这是词汇定义，不是规则。
   - 报错必须说出真实原因。R6 的报错说"O1 does not exist"，与事实不符，模型照着修补，把"全局 `--audit` 适用于各命令"的语义丢掉了。报错不准，就会让修补丢语义，这类问题算 IC 自身的问题。
2. **同一对象的嵌套归属由代码接受**（R9、R10）。上级小节和它的子小节归给同一个对象时，没有歧义，代码按"同一归属"去重。只有归给不同对象时才报 overlap。
3. **所有问题都按根源合并**，不只 overlap。同一检查、同一种问题合成一条，列出受影响的断言或编号。
4. **逐字引用与推导**：
   - 期望值不在引文里逐字出现时，报错要指出可以改为推导，由参考脚本计算，比如"填空字符串"→ `""`、"会写出文件"→ 存在。
   - 判定规则不放宽：不在原文里逐字出现的值，必须经过方法 B。
5. **检查可以以它在 uses 里列出的共享约定的原文为依据**（basis）。约定被修订时，这些检查本来就会按 uses 过期。
6. **不可切分块的部分修订**（R15 改 R13 的 JSON 示例和字段表）：
   - 代码块、表格、JSON 示例被新原文覆盖时，状态记为"被修正"，不记为"被替换"。这样的块仍留在对象的当前原文里，并带上指向修正它的新原文的编号；工单里两者都出现，按"新原文优先"读。
   - 以这种块为依据的检查照常过期、重推。
   - 能切分的句子和子句照旧整句替换。
8. **工单要把子句级的部分修订标出来**：这是对 R1–R3 实际工单的检查结果。
   - 现在来源区只在整块上标 `partially_modified`。归属阶段已经精确到子句，比如 R2 fill 的 "the cell remains empty" 被 R3.S2 修订、R2 normalize 的总体标准差被 R3.S3 修订，但这份精度没有交到执行方手里，执行方只能自己去比对新旧原文。这正是 v7 失分的一类原因。
   - 修法：在原文里被修订的句子或子句处，加上编号标记，形如 `⟦R2.S13.P4.s4.c3 → 已被 R3.S2.P2 修订⟧`，零复制，不重写原文；被修正的不可切分块（第 6 条）同样处理。
9. **锚点按对象归属，不按步骤**：
   - 现在一个步骤碰过的所有锚点，都记给这个步骤里的每个对象（`execution.ts` 中 `for (const o of step.objects) for (const a of verdict.touched)`）。结果是 filter 名下挂着 `opDrop`、`opSort`、`opRename`，保护区和锚点区都被放大。
   - 修法：
     - 执行方在步骤报告里按对象报出它改了哪些锚点，代码只核对这些锚点确实被这一步改过；
     - 名字能对上的（`op_filter.go`、`dispatch:filter`），由代码直接归属；
     - 归属不清的，记为步骤内各对象共享。
   - 对象名下的锚点不能多于它实际用到的。
10. **建立在原文没写明的读法上的期望值，要标出来，失败时判"未知"**：来自 R4 检查推导。
   - 模型自己注意到 validate 的两处原文没写明：违规的行号是不是从数据行算起，有违规时退出码是不是 0。它按自己的读法写了期望值，方法 A 和方法 B 都按同一读法计算，自然一致，于是作为强检查入库。它在 note 里写了这两处读法，但入库时没有保留。
   - 读法一旦错了，IC 会把正确的程序判为未落地，并推着执行方往错的方向改。这是 IC 自身造成的失分。
   - 修法：
     - 断言可以带 `reading` 字段，用一句话写明它依赖的、原文没写明的读法；代码保存这句话，工单里在失败证据旁边显示它。
     - 带 reading 的断言失败时判为"未知"，不判"未落地"，不阻止已落地，也不推动修补。
     - 以后的原文写明了这一点时，按归属的 refers_to 规则过期重推。
   - 系统提示里写两条词汇定义：一个断言只读一个事实；依赖读法的事实和不依赖读法的事实分开写成不同的断言。
     - 原因：现在一条断言把"行号、规则、值、消息"打包在一起，行号读错，整条都失败。
11. **不改**：
   - 改动清单式的复述（R5）被当作新增：只会造成任务区里的重复条目，不影响正确性，暂不处理，真实运行后看成本再说。
   - 故意构造的错误摘要：模型已经自己用 `{{computed:…}}` 走对了路径（第 12c 节第 6 条维持）。

## 12g. 验收的统一模型（已定，2026-10-22；同日按审查做了简化）

起因：真实 15 轮里，IC 的准确率不如"裸模型 + 带工具的审查员"这个对照组，而且更慢。分析见 EXPERIMENT-MAP 的夜间一节，原因有三：
- 判断不能动手计算；
- 没覆盖到的规则就此不了了之；
- 每个修补周期把全部探针逐个起容器重跑。

检查库（第 9 块）和探针（第 10 块）是两套平行的机制，"未决"的东西散在四个地方。按统一语义的做法，把验收也统一起来，只复用和接通现有机制，不新建。

- **检查**：
  - 第 9 块的检查和第 10 块的探针，都只是"检查"的来源；
  - 每条检查都有：依据（原文编号，可以细到子句或情况）、输入（调用方式和文件）、判定方式、结果历史。
- **判定方式**，按可靠程度依次优先：
  - **A 原文给定值**：验收方用编号指出原文里哪一段是期望值，代码取出原文逐字比对。模型不负责抄写期望值。
  - **B 可执行的参考**：验收方写一小段参考脚本，用来计算期望值或者断言某个性质，由代码执行并比对。
  - **C 阅读判断**：由模型判断。

  能用代码判定的，就不交给模型。
- **B 和程序结果不一致时**：交给另一个会话去裁决，只给它原文、程序输出和参考输出，不给参考代码，以免写参考的一方偏袒自己。裁决结果有三种：程序错、参考错、原文有歧义。
- **结论**只有四种：对、错、看不出、原文有歧义。
- **未决**只有一个概念，原因分四种：程序错（也就是纠错条目）、没覆盖到、参考不一致待裁决、原文有歧义。
  - 去路只有一条：本轮重试、带到下一轮、列进报告。
  - 结束方式有四种：
    1. 修好；
    2. 原文修订使它失效，记为"被取代"；
    3. 判为原文有歧义，转为单独记录，不再推着执行方去修；
    4. 没覆盖到的规则，验收方连续两次都写不出能覆盖它的检查，就标为"无法检查"并写明原因，仍然留在报告里。
- **重跑**（已由 §12h 修改为"每周期定向，每轮全量兜底"）：
  - 每个周期，全部 A、B 类检查放在一个容器里批量跑一遍（不花模型 token，也不会漏掉回归）；
  - C 类只在输出变化时才重判（用缓存）；
  - 不按锚点挑选重跑范围。
- **角色**：
  - 执行方：修代码；
  - 验收方：产出检查，并做 C 类判断。它和执行方不同源，输入只有"本轮原文的变化 + 相关检查的现状 + 代码的变化"，看不到执行方的过程；
  - 裁决会话：只裁决 B 类的不一致；
  - 代码：负责运行、比对、度量覆盖、维护状态、组装纠错单。
- **变异体**：默认关闭。消融结果是多换来 1 个命中，成本却是 3 倍；要度量检查强度时再单独打开。
- **复用**：
  - 第 9 块：检查库、参考脚本、逐条入库、裁决；
  - 第 10 块：探针、判断、歧义出口、纠错单、跨轮带入、判断缓存；
  - 失效规则。

  新增的东西，必须说明现有机制为什么做不到。

## 12h. 第 12 块：台账、无效修补、定向运行（已定，2026-10-22）

起因：用原始数据复核 10b 的 IC 15 轮 rep1，见 EXPERIMENT-MAP 的"白天复核"一节。要点：
- R5–R10 的修补周期全花在判断的误报上：P132 的 IQR 算错；P87、P315 看字段名就说摘要是 SHA-256。
- 真实失败从没进过纠错单。
- BLAKE2b 的 5 个失败是共模失败，从原文推不出。
- 未缓存 token 主要花在写探针和判断上。

在 §12g 的基础上，要达到的效果如下：
- **E1 需要计算的值，不靠阅读定对错**：
  - 计算出的期望值，必须和程序结果里对应的那个值比对，短值碰巧出现在输出别处不算一致；
  - 依据计算的"错"，在有独立计算支持之前，不进纠错单；
  - 计算和判断不一致时，由裁决会话依据原文和计算结果裁决。
- **E2 一本台账**：
  - 每个未决条目只有一个身份，挂在原文单位上，可以细到"情况"；
  - 跨轮保留历史：打开、送修、执行方回应、结论变化、结束方式；
  - 报告是台账的投影。由代码从现有事件推出，不加模型调用。
- **E3 不做无效修补**：
  - 一个条目送修一次后，如果程序在该条目上的输出没变，或者执行方表示程序正确，就转交裁决，不再重送；
  - 条目有有效期：原文被取代、修好、裁决结束，或者带过一定轮数仍然没有进展，都转为"只列在报告里"。
- **E4 每周期定向运行，每轮全量兜底**（取代 §12g 的重跑规则）：
  - 每个周期只运行、只判断三类：本轮原文改动的单位、台账中有效的条目、本周期代码改动实际执行到的检查。这三类由代码确定，不靠模型推断锚点；
  - 每轮交付前，全部 A/B 检查和探针跑一遍；
  - 兜底扫描发现、但定向时漏掉的，记为"选择遗漏"，写进报告。
- **E5** 判断和写探针的请求，在一轮之内能命中缓存，报告缓存读取的占比。
- **E6 只做验收的回放**：
  - 对任意一份冻结的程序，逐轮建出 R1–RN 的检查，输出台账；
  - 检出按缺陷合并库检查和探针两边的结果。

**验收**：
- 离线替身测试：
  - 短值碰巧出现在别处；
  - 复现 P132、P87；
  - 误报之后最多修补 1 个周期就转裁决；
  - 只凭台账就能回答一个条目的经过；
  - 改坏排序时，选择遗漏能被记下来。
- 本地运行：
  - R1 的 11 份产物检出跑 3 次，按缺陷合并，均值 ≥13/19；

## 12i. 验收重构：验证是一笔会累积的资产（已定，2026-10-23）

起因（证据在 `exp2/evidence/` 下）：
- 第 12 块离线回放：44 条"程序错"真假各半，两份官方满分产物上 10 条全假（VERIFY-2026-10-22.md）。误报出在前提上：输入退化 11、过期 6、位置假定 3、推导 1、矛盾 1；命令和输出都是真的。22 条里 21 条在某个产物上通过过；4 条是同一探针、输出未变、判断翻转。
- 中间层核对（MIDDLE-LAYER-CHECK-2026-10-22.md）：54 个过期条目 31 个不该过期，K8、P86 该过期没过期。
- 对照组（每轮新开、读全部原文、自己跑程序的审查员）：滞留失败都是审查员没发现，报了的当轮修好；同一审查员 45 次审查都漏了 log(0)，IC 的探针在 R1 抓到它。审查员也会误报。审查员占对照组非执行方成本约 79%（价格加权），上下文随累积原文线性增长；无发现的审查照样花 3–5 分钟。
- 审查员降为 gpt-5.6-luna-fast medium 后，对照组 L（执行方 low）R15 99.0%，M（执行方 medium）100%（OBSERVATIONS §17）。在 dpipe 上准确率已无空间。

**定位**：IC 验收的独有价值，不是比审查员更会找错，而是把验证从"每轮按全文重做的随机抽查"变成"按改动付费、确认一次后由代码免费守住"。这是 §5（外部状态当记忆）和 §2 第 2 条（确定性的事归代码）落在验收上的形态。

要达到的效果：
1. **审查员是主要发现者**：带工具、自己构建运行、列出偏离，设置与对照组相同。一个单位第一次出现（新增或被修订）时，审查员读全文认真核查；之后只看本轮新增和修订的单位，加上守卫新报的失败。没有新发现时，本轮不再跑第 2、3 次审查。
2. **送修前做前提核验**（代码，不花 token）：依据的原文单位当前有效；输入文件按其格式的标准解析器解析，解析结果与声称的情形一致（通用于有标准解析方式的格式，不针对某一种）；数值期望由执行的脚本算出，不由文字陈述。过不了的不送修，记入台账。
3. **守卫只收代码比对、且在本运行的程序上观察到通过过的检查**；模型的判断只能产生线索，永远不当守卫。审查员报的、执行方修好的偏离，由代码固化为确定性检查。全部守卫每轮成批重跑，不花 token。
4. **修补不能改坏守卫**：每次修补后重跑全部当前通过的守卫，任何一个由通过变失败，就回退这次修补（用已有的 git 检查点），丢弃这条线索。
5. **探针每个单位只写一次**：单位新增时写，被修订时重写，不再每轮都写；每轮写探针、判断默认关闭（配置项，不删代码）。
6. **过期用确定性触发，不再按引用推断**：本轮原文有改动的单位上，守卫由通过变失败，附上本轮原文改动交审查员判"退化还是被取代"；原文没改动的单位上变失败，直接判退化送修。
7. **覆盖由代码保证**：每个仍然有效的单位至少有一条执行到它的确定性检查（执行到与否从实际运行的命令和覆盖记录取，不由模型自报）；没有的列为"未覆盖"进报告。审查会话里没有一次成功运行程序的，该次审查作废重做。

台账、停送、有效期规则（第 12 块）保留。裁决会话不再处于送修路径上。

**预先登记的判定**（只做 dpipe）：
- 比较 IC（本节）与对照组 L（执行方 gpt-5.6-luna-fast low，审查员 gpt-5.6-luna-fast medium），15 轮各 ×2。
- 决定数字：R5–R15 累计非执行方成本之比 IC/对照，成本按"未缓存输入 + 0.1×缓存读 + 输出"计（口径待用户最终确认）。
- 门槛：R15 官方 ≥ 948/960。
- 比值 ≤ 0.5 且过门槛：IC 胜出；比值 ≥ 0.8 或不过门槛：失败；之间：未证明。
- 同时报告：每轮墙钟（不超过对照组每轮 2 倍）、首次交付诊断分、守卫数、退化次数（守卫由通过变失败）、被回退的修补数、前提核验挡下的线索数。

改动分类的粒度、当前有效视图、按关系挑原文，不在本节，属于第 13 块。

## 12j. 收编：一种检查记录、一套状态机、两条前提（提议，2026-10-23；用户授权起草）

**定位**：收编不改变 §12i 的定位和预先登记判定，只改变实现的形状。目标是接口从十几个减到四个（写检查的输出、审查员的回复、formalizer 的输出、程序运行的结果），每个都有真实回复的回归；任何机制保留的条件是能指出它在真实运行里救过分或省过周期。

### 12j.1 一种记录

一条检查 = 命令 + 输入文件 + 期望 + 依据的原文单位，加一个来源字段：

| origin | 来源 | 能做什么 |
|---|---|---|
| hypothesis | 模型从原文写出，未经确认（今天的 K 和 P） | 只当线索给审查员；失败不送修 |
| confirmed | 审查员在程序上实际跑过、报了偏离，代码从它的材料落成（今天的 V） | 过两条前提即送修 |
| guard | 在本运行某个程序上实际执行了目标命令并通过过（今天的 G） | 每周期免费重跑；翻转触发回退或问审查员 |

guard 是身份转换，不是另一条记录。编号可保留 K/V/G 前缀作为 origin 的显示，但只有一个列表和一份历史（append-only 事件：written、ran、became_guard、flipped、retired、superseded）。

### 12j.2 一套状态机

```
hypothesis ──在程序上跑──► 失败 ──► 线索给审查员（不送修）
                          通过 且 真执行了目标命令 ──► guard
                          通过 但 调用被程序拒绝 ──► 失败，告知写它的模型
审查员报偏离 ──代码从材料落成 confirmed──► 前提1 单位仍有效？ 前提2 当前程序上复现？
                                         都过 ──► 送修 ──► 修好后通过 ──► guard
                                         任一不过 ──► 记日志，不送
guard 翻转 ──► 本轮原文改过它背后的单位？ ──是──► 附改动问审查员：SUPERSEDED 则退役，否则送修
                                           ──否──► 直接送修；修补改坏其他 guard ──► 回退这次修补
```

材料来源的顺序（批次 C 已实现，保留）：线索编号 → 审查员会话里写过的文件和跑过的命令 → formalizer 从文字重建 → 三处都没有才是 no_input。

## 14. 运行规则（已定）

- **检查点**：每轮结束时把外部状态、代码的 git 提交和本轮报告写成一个检查点。第 N 轮只能从第 N−1 轮的检查点开始，不拼接不同时间的状态。
- **额度用完**：停下，每 30 分钟从被打断那一轮的检查点续跑一次，直到能跑。
- **会话挂死**：看门狗停掉不返回的调用。管理调用在本轮的修补上限内重试；编码会话从最后一个好的检查点另开一个会话，只交剩下的步骤。
- **预算**：每轮的管理调用和编码步骤都有上限。编码预算用完时，保留已完成的步骤，没完成的对象进入下一轮的任务区。归属那一步用完修补次数仍不通过时，这一轮无法继续，停下整个串行并报告，不强行跑过去。
- **每轮报告**：
  - 官方得分（只在本地计分，不回送给系统）；
  - 各环节的调用次数和 token；
  - 本轮范围和各区条目数；
  - 每个对象的状态及其依据；
  - 失分归因，分三类：原文没有可检查的期望（承认的边界）；IC 自身的问题（归属、分区、检查判错）；工单正确但执行方没做对。
