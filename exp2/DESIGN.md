# 实验 2：纯 IC 设计草稿（2026-10-20，讨论中）

## 结论

实验 2 让 IC 独自完成整个开发流程（理解需求、派活、编码、验收、纠错），与已有结果的 SDD 单独执行对比准确率和成本，并且要明显胜出。设计的骨架是一份由代码维护、版本化的外部状态（IC 的"记忆"），加上全系统共用的一套编号词汇。原文是需求的唯一权威。结构负责把每轮做准、做省。模型负责理解，代码负责确定性的事。执行过程由 IC 分步控制，失败时保留已完成的部分，不再"错一步、整批作废"。

## 2. 原则（已定）

1. 原文是需求的唯一权威，新的原文高于旧的原文。模型写的理解、IC 自己生成的东西（代码修复、检查）、执行方写的东西都不是需求。
2. 确定性的事归代码：身份、版本、来源定位、运行、比对、状态计算、投影。需要理解的事归模型：分类、拆分与归属、推导、对照判断、写代码。
3. 完整原文供模型做当轮理解，并保存下来作历史对照。结构负责当轮实现做准，并让后续理解更省。
4. 跨轮版本化是 IC 的核心，这正是 SDD 没有的。IC 不使用模型记忆，每次调用都由代码从外部状态取出需要的部分。
5. 全系统共用一套编号词汇，内部通信只传编号和引用，不在各层之间互相翻译。
6. 每个事实只有一个主人，别处只引用编号，不抄内容。关系可以分散在多处表达，但同一个事实不重复记录。
7. 落地只认在代码上实际跑出来的行为，期望值必须能追溯到原文。
8. 不做得机械死板：只有代码要依赖的编号必须统一，其余内容让模型自由书写。

## 4. 原文与对象（已定；经 Fable 两轮讨论和用户确认）

**4.1 什么算一个对象**
- 对象的身份**只看原文**：原文用一个稳定的名字指称它，并且它的各部分会一起被修订。参数、字段、选项永远不成为对象，它们是对象的内容；它们被修改时，算作对象的一次部分修订。
- 能不能验收不影响一个东西是不是对象，只影响它的状态。写不出检查的需求也照样是对象，照样进任务区由执行方按原文实现，只是状态为"未知"。
- 不预先声明对象的类型。"有没有自己的检查""有没有被别的检查用到""有没有成员"都由代码从登记的数据算出来，状态按同一套算法计算。
- 第 1 轮宁可切细，只在原文自己分条的地方细分。之后合并便宜，拆分贵。

**4.2 轴心：原文，按需细化的三层（已定）**

代码按文本结构切出三层并编号（只追加，永不改动）；模型读完整原文，理解语义后，为每一块选**能单独归一个对象的最粗那一层**。

| 层 | 代码怎么切 | 什么时候用 |
|---|---|---|
| 小节 | 一个标题及其下的全部内容 | **默认**。大多数新增内容一整节就是一个对象 |
| 段落 | 小节内按空行切；代码块、JSON 样例、列表整体不拆 | 一节里写了几个对象时才细分 |
| 句子 / 子句 | 段落内按句子切；需要时再按逗号、分号、括号切到子句 | 只在一段话混着说了几个对象，或"部分修订"要指明改了哪一句时用 |

- 每一块恰好被覆盖一次，由代码核对没有遗漏、没有重复。归属可以是一个对象，也可以是 `none`：每轮的前言、分隔线这类不是需求的文字。R1 的前言（用 Go 写、确定性）是真需求，要归给对象。
- 列表项、代码块、表格作为一个单元，不往句子切；但为了指明部分修订改了哪里，**列表项可以切到子句**（按逗号、分号、括号切，行内代码里的不切）。默认归属仍然取最粗的一层（第 1 块评审，已定）。
- 宽松列表（项与项之间有空行）在空行处切段，这样操作列表才能按操作分开（第 1 块评审，已定）。
- **归属是索引，不是切文本。** 交给模型和执行方的永远是完整的小节或段落，连同它所在的标题，归属的部分只是标出来。绝不交孤立的句子。每轮的完整原文仍然交给模型做当轮理解。
- 拆分或合并对象时，模型只说明各块如何重新分配，新旧对象的对应关系由代码按块的归属算出来。轴心不会漂移。代码锚点是第二条轴：执行报告和 AST 会让函数跟着对象走。
- 拆分和合并放到第二版。第一版只记录代码给出的"疑似该拆 / 疑似该合"信号，例如两个对象总是被同时修订、锚点高度重合。

**4.3 跨对象关系：只来自原文写出的句子**
- 一处原文写到别的对象时记成一条边，**边分两种**（第 1 块评审，已定）：
  - **引用定义**：这一块用到另一个对象定义的东西，比如"aggregate 的 having 使用与 filter 相同的条件语法"。边指向被引用的那一块。被引用的块被修订时，代码沿着这条边把相关检查标为过期，并在工单里附上被引用的原文。被引用的对象本身没有改动。
  - **适用于**：这一块提出的要求也落在另一个对象上，比如 R5 的"`ingest` and `transform` must remove it"归给 ingest，同时适用于 transform。被指向的对象也得到一条改动记录（来源记为这一块），升一版，进入本轮范围。
  - 两种边都只能由原文措辞本身点到的对象来标。归属仍然只有一个，轴心不变。
- 代码按名字找出新原文可能牵涉的已有对象，作为**候选**交给模型。模型只能回答"第几块本身的措辞写到了它"或"没写到"，不能回答"按理应该包括"。
- **不允许由模型归纳的规则自动生成对象或任务**。比如不能从几轮原文里归纳出"每个命令都对应一个 pipeline 步骤"，再去自动派活。
- 原文漏写的跨对象影响，只记一个**缺口信号**，放在状态区：不派活、不验收，接受这部分损失。原文是唯一权威。

**4.4 改动与修订**
- 每轮新原文到来时，模型判断每一块属于哪个对象，是新增、修订、撤回还是部分修订。代码据此登记改动、给对象升版本，并把被替代的旧块标为"被替代"或"被部分修改"。
- 改动类型按"对旧原文的影响"来定义，写在 schema 的说明里。这是定义，不是判断规则；判断仍由模型做（第 1 块评审，已定）：
  - 新增：没有旧原文因此不再成立；
  - 修订：某块旧原文整体被新原文取代；
  - 撤回：某块旧原文整体不再有效，且没有替代；
  - 部分修订：某块旧原文里有一部分不再成立，其余照旧。
- 替换目标只能是当前有效的原文。指向已被替换的旧块属于确定的错误；报错时要指出现在有效的是哪一块，方便一次改对。
- **部分修订用编号表达，零复制**：记录为"旧块的哪几句或哪几个子句，被新块的哪几句覆盖"。代码切出对应的原文，并排展示；模型不复制任何原文。编号越界或为空，就退回给模型。并排展示时，旧的一侧给被改单元所在的整段加上标题路径，而不是整节（第 1 块评审，已定）。
- 原文自相矛盾时，以新原文为准，这属于状态更新。只有同一轮内两块不一致，或部分修订的范围不清时，模型才写一条解读，附上依据的块，并标明"这是解读，不是原文"。权威仍然是原文。
- 完整原文按对象分组交付：v8 已验证每段逐字只出现一次，零复制；按小节归属后，单独一行的标题自然跟着它下面的内容走。

**4.5 共享约定**（报错格式、CSV 读写、确定性、seed 默认值、JSON 缩进等）
- 共享约定也是对象，有自己的版本。
- 验收是间接的：检查库里使用了某个约定的检查都要标注 `uses`（由模型标注，代码补充核对：期望里出现了约定的关键形式却没标注的，退回给模型）。约定相关的断言要单独成条，不和业务输出混在一起，这样才能分清是约定没做对还是业务没做对。
- 约定被修订时，代码把所有标注了 `uses` 的检查标为过期，模型只对这一批检查重新推导一次期望，不重推全库。用到这个约定的对象会出现在任务区的"受约定修订影响"小节里。

**4.6 模型调用的形态（第 1 块评审，已定）**
- **首答和修补用同一个 schema、同一个系统提示**：首答就是对一份空草稿打补丁。请求的开头是原文，后面依次是稳定的部分，上次的答案和代码找到的问题放在最后。这样修补可以复用首答的前缀缓存；这是实测中唯一能命中缓存的形态。其他需要多次调用的环节也照此处理。
- 第一版照样把全部原文交给模型；要不要裁剪，等真实运行拿到成本数据后再定。

## 6. 工单与分区（提议）

每轮发一张工单，按"改动类型 × 落地状态"分区，由代码计算：

| 区 | 内容 | 对执行方的含义 |
|---|---|---|
| 任务区 | 本轮的改动对象，加上有证据未落地的以前对象（附失败检查的输入和实际输出） | 必须做 |
| 保护区 | 本轮任务会碰到的已落地对象，以及它们当前通过的检查 | 不能改坏，IC 会重跑这些检查 |
| 状态区 | 判为"未知"的对象 | 只作说明，不是任务 |
| 原文区 | 全部原文，按对象分组，每段只出现一次 | 当轮理解用，以原文为准 |
| 锚点区 | 任务区和保护区对象的代码位置，以及上次的执行报告 | 知道要改哪里、以前改过哪里 |

规则：
- 只有"有证据的未落地"才能进任务区，"未确认""未知"永远不写成任务（v7 R10 的教训）。
- 各区只引用编号，原文只在原文区出现一次。

## 7. 执行方：IC 控制过程（已定方向，细节为提议）

- IC 不管代码具体怎么写，但要管住过程：可以复用缓存，失败时保留正确的那部分产物，不需要整体重启。
- **分步（已定）**：执行方在 IC 给定的对象范围内**自己提议**怎么分步，每一步写明覆盖哪些对象（完整覆盖或部分覆盖）。允许"共享基础"这样的步骤，例如一个同时服务 filter、derive、aggregate 的表达式解析器。引用边只作为参考信息交给执行方，不作为先后约束。代码按锚点核对每一步：
  - 声明覆盖了某个对象，却没动它的锚点，退回；
  - 动了没有声明的对象的锚点，就跑那个对象的保护检查。
  代码只限制形状：步数上限，每步的对象数上限，每个对象被部分覆盖之后必须有一步完整覆盖它。每完成一步提交一次 git。
- **git 只作事实底座，语义外挂。** 提交、diff、回退由 git 完成；提交说明末尾用 git trailer 写统一词汇里的编号（例如 `IC-Step: P10.3`、`IC-Object: O.fill@v2`、`IC-Checks: K.fill.07 pass`），代码只读这几行，不读自由文字。这与 SpecArt 的"代码骨架加摘要"是同类思路，有现成的就直接用。
- **给模型看的是投影**，不是提交日志：IC 按对象挑出相关锚点在这些提交里对应的那几段 diff，再加上原文段落和检查结果。
- **每步验一次**：IC 在每个检查点跑构建和相关检查，通过的步骤保留。
- **失败时接着做**：在同一个会话里继续纠正，复用上下文和缓存；会话坏了，就从最后一个好的检查点另开会话，只交剩下的步骤。
- **预算和超时按步计**：超出时保留已完成的部分，没完成的进下一轮的任务区。
- 执行报告的格式固定：每一步为哪些对象改了哪些锚点，跑了什么，结果如何。代码核实锚点确实存在、确实改动过。

## 8. 验收：检查库（经 Fable 两轮讨论；第一版最小集合已定，扩大覆盖面的办法为提议）

- **权威**：原文段落，加上在当轮程序上实际运行、期望值能追溯到原文的检查。状态由代码按规则计算，模型不直接给出"已落地"。
- **模型做理解**：判断一段话里有没有可检查的东西、构造检查输入、推导期望、对照原文找出不符之处。**代码做判定和执行**。
- **检查入库**：命令名、选项名必须出现在原文的代码片段里。期望值要么逐字来自原文，要么由两种方法分别得出且一致（方法 A 直接推导；方法 B 写参考脚本，由代码执行）。
- **失败先判原因**：值不符，或命令、选项没实现，判未落地并派任务；调用被拒但功能存在，或触发了别的报错规则，判为输入可疑，算"未知"，不派任务。
- **区分做没做（已定）**：一条检查算"强"，要同时满足两个条件。
  1. 它在**代码构造的基线**上失败。基线永远不是执行方的工作树：第 1 轮的基线是代码生成的、对任何调用都以 exit 1 结束且无输出的程序；之后各轮的基线，是代码从上一轮**验收通过的提交**构建出的程序。
  2. 它至少有一条**和数据有关的断言**：期望里有来自样例输入、或由输入算出来的内容，而不只是退出码、命令存在或帮助文字。
  对象至少有一条强检查通过，才算已落地。对"撤回"类的修订，方向反过来：强检查应当在基线上通过、在当前程序上失败。
- **回归**：每轮把检查库全部重跑一遍，不花 token。
- **执行方异议**：必须附上实现位置和一条可运行的替代调用。最好的结果是把检查降为"未知"，不能借此变成"已落地"。
- **坏检查**：派过纠错、代码也改过、检查仍失败，连续两轮后不再派。
- **第 2 块评审的决定（已定）**：
  1. **和数据有关的断言**：读取产出内容（stdout、文件、JSON、CSV）且本次调用带有输入的断言，以及期望文字里带着输入内容的断言（例如 `ERROR: file not found: nope.csv` 里的文件名），都算和数据有关。只有退出码、文件是否存在、帮助文字的不算。
  2. **"未知"类的失败不阻止已落地**：输入可疑这类失败照样记录、照样展示，但不参与判定。同一条检查连续两轮都判为输入可疑，就退役。
  3. **原文被修订后，旧检查由代码自动标为过期**：检查所依据的原文块被替代，或者它引用的那几句被部分修改时，标为过期，不参与判定，等待重新推导。模型的退役建议只作为提议，代码核实这条检查确实依据了被修改的原文，才接受。这一项不等传播那一块，现在就做，否则旧检查会在正确的程序上失败，造成误判。
  4. **漏标 uses**：保持保守的判定，漏网的情况记录下来，留到真实运行时再看。
  5. **"命令没实现"**：原文点名的单元（命令、选项、操作名，以及等于某个对象名的输入值）在程序的源码里根本找不到，就判为没实现。
  6. **推导不一致按单条断言处理**：不一致的那条记为未知，其余的照常入库。
  7. **强弱在入库时判定一次**，之后不随基线变化而重算。
  8. **每条检查必须写明期望的退出码**，缺了由代码退回。
  9. 沙箱：真实运行时换成 docker，参考脚本也在容器里运行（由本地负责）。请求大小先不裁剪。
- **扩大覆盖面**（用现有方法，小模型留作底牌）：
  1. 参考实现差分：模型照原文写一个独立的参考实现，代码生成大量输入，同时跑参考实现和我们的程序并比对输出。结果不一致时，由模型对照原文判断哪边对。这能覆盖"原文写了规则、没写结果"的行为。
  2. 性质检查：提取原文写明的不变量（排序、确定性、计数），在随机输入上检查。
  3. 对照阅读：模型读原文和本轮改过的代码，指出不符之处。只有能变成检查的，才算证据。
  4. 执行方自己写的测试：只作信号，不作权威。
- **小模型路线**：验收里的判断大多窄而重复，现阶段用大模型加结构化输出，把每类判断的输入输出格式固定下来，作为以后训练小模型的数据来源。
- **第一版最小集合**（Fable 的建议）：
  - 逐字检查；
  - 失败原因分类；
  - 强弱区分；
  - 缺名反证：原文代码片段里的命令名、选项名、JSON 键，在代码里找不到；
  - 只接受可运行证据的异议；
  - 两种方法都一致才入库的推导检查。
  参考实现差分是否进入第一版，**未决**。

## 9. 每轮流程（提议）

1. 代码切分新原文，生成段落编号。
2. 模型对新段落分类和归属。代码登记改动、给对象升版本，并算出本轮范围。
3. 代码抽取锚点，读取检查库在当前程序上的状态，生成分区工单。
4. 执行方在任务区的对象范围内提议分步，代码核对分步的形状。
5. 执行方逐步编码。每步提交一次，IC 跑构建和相关检查，失败就在会话里接着纠正。
6. 模型为本轮新段落抽取或推导检查，代码核实后入库。
7. 代码在最终程序上重跑全库，计算各对象状态，生成本轮记录和下一轮的输入。

## 10. 模型与代码的分工一览

| 环节 | 模型 | 代码 |
|---|---|---|
| 原文 | 分类、拆分、归属；矛盾时写解读 | 切分、编号、登记、版本、按对象分组 |
| 范围 | — | 从版本差异算出本轮范围，从依赖边算出影响范围 |
| 工单 | 执行方提议分步 | 分区、投影、引用、核对分步形状与锚点覆盖 |
| 执行 | 写代码，写执行报告 | 提交、检查点、构建、预算、超时、核实报告 |
| 验收 | 抽取、推导、构造输入、对照判断 | 核实、运行、比对、判定、回归 |

## 12. 实现顺序（提议）

机制已经不少，按下面的顺序一块一块做，每做完一块就离线验证一块（见 DEV-GUIDELINES 第 3 节），不要一次全部铺开：

1. 原文三层切分与编号，对象登记与归属核对，改动记录与版本。
2. 检查库：入库核实、运行与比对、失败原因分类、强弱判定、状态计算。
3. 分区工单与投影；执行层：分步提议的核对、git 检查点与 trailer、每步验证、失败后续做、预算与超时。
4. 传播：引用边、`uses` 过期、部分修订的子句索引。
5. 端到端串行：把前四块串成每轮流程（第 9 节），加上检查点、续跑、止损和每轮报告（第 14 节）。离线时用替身模型和替身执行方跑完 15 轮。
6. 本地接入（由本地负责）：OpenCode 管理调用、编码会话执行方、docker 运行器、官方验证器计分。

## 12a. 第 3–5 块评审的决定（已定）

- 采纳开发在 BLOCK3–5 NOTES 里的各项取舍：
  - 检查改在编码之前推导，只用于验证，不作为需求交给执行方；
  - 保护只守护上一个好的检查点时已经通过的检查；
  - 分步不必覆盖全部任务对象，没做完的按执行记录带到下一轮；
  - 失败的步骤整步丢弃；
  - 过期按检查引用的那一块判断，引用粗块时过期也粗；
  - 共享约定的任何改动都让用到它的检查过期；
  - refers_to 只传播一层；
  - 推导失败时本轮照常进行；
  - 轮初状态来自在基线上的一次试跑；
  - 续跑最多 48 次；
  - 非编码环节的 token 目标只做事后核对，超出时在报告里标出，不作为运行时的硬上限。
- **补充一**：一轮里新变为过期的检查，在同一轮重新推导。所属对象即使不在本轮范围内，也加入本轮的推导名单，但不进任务区。
- **补充二**：真实运行在本地 Windows 上。代码和测试都要在 Windows 上成立：编译出的程序带 `.exe` 后缀；Python 解释器可以配置（Windows 上的 `python3` 是应用商店的占位程序）；不要依赖 shebang 直接执行脚本。检查运行和参考脚本，在真实运行时放进 docker。

## 14. 运行规则（已定）

- **检查点**：每轮结束时把外部状态、代码的 git 提交和本轮报告写成一个检查点。第 N 轮只能从第 N−1 轮的检查点开始，不拼接不同时间的状态。
- **额度用完**：停下，每 30 分钟从被打断那一轮的检查点续跑一次，直到能跑。
- **会话挂死**：看门狗停掉不返回的调用。管理调用在本轮的修补上限内重试；编码会话从最后一个好的检查点另开一个会话，只交剩下的步骤。
- **预算**：每轮的管理调用和编码步骤都有上限。编码预算用完时，保留已完成的步骤，没完成的对象进入下一轮的任务区。归属那一步用完修补次数仍不通过时，这一轮无法继续，停下整个串行并报告，不强行跑过去。
- **每轮报告**：
  - 官方得分（只在本地计分，不回送给系统）；
  - 各环节的调用次数和 token；
  - 本轮范围和各区条目数；
  - 每个对象的状态及其依据；
  - 失分归因，分三类：原文没有可检查的期望（承认的边界）；IC 自身的问题（归属、分区、检查判错）；工单正确但执行方没做对。
