## 2. 数据结构与接口

### 2.1 一条检查（`CheckRecord`）

- `id`（K1、K2……，永不复用）、入库轮次 `round`、所属对象 `object`、依据的块 `blocks`、用到的约定对象 `uses`。
- `direction`：
  - `holds`：断言写的是现在必须成立的事；
  - `withdrawn`：断言写的是原文已经撤掉的行为。
- `input`：命令行参数 `args`（跟在程序名后面），以及写进空目录的输入文件 `files`。
- `assertions`：每条只说一件事。
  - `role`：约定或业务。
  - `target`：可以是退出码、stdout/stderr 整体或某一行、某个文件整体或某一行、文件是否存在、JSON 字段（JSON pointer）、CSV 单元格（数据行加列名）。
  - `expect`：期望值。
  - `tolerance`：数值误差，按 max(1, |值|) 的相对值，默认 1e-9。
  - `source`：期望的来源。逐字的写块编号和原文引文；推导的另附方法 B 的值。
- `unknown`：两种方法不一致或无法比较的推导断言，连同原因记下，不进入比对。
- `admission`：至少剩一条断言就是 `admitted`；一条都没剩就是 `unknown`，只留记录。
- `strength`：入库时对照当轮基线判定，记录是否为强、所用基线、基线结果、和数据有关的断言、理由。
- 状态在条目里固定为 `active`。之后的变化写成只追加的 `check_events`：`retired` 已用，`stale` 留给第 4 块的传播。

### 2.2 模型这一步

- 请求结构：`sources`（全部原文，带编号，放在最前）、`scope`、`objects`、`checks`、`round`，最后是 `issues` 和 `previous_draft`。各字段的内容：
  - `scope`：本轮有改动的对象，以及它们当前持有的块和本轮带来改动的块；
  - `objects`：全部对象的编号和名字，供 `uses` 使用；
  - `checks`：这些对象在库里已有的有效检查（只给编号、块、uses、断言条数）。
- 回答是对草稿的补丁：`upsert`、`remove`（按草稿 key）、`retire_add`、`retire_remove`。首答和修补用同一个 schema、同一个系统提示。有测试断言修补请求在 `"issues"` 之前与首答逐字节相同。
- 方法 B：模型写一个参考脚本，代码在只放了输入文件的临时目录里限时运行它。脚本打印 `{断言 id: 值}`，与方法 A（模型直接写的期望值）一致的推导断言才入库。

### 2.3 入库核对（只拦确定的错误）

| 代码 | 含义 |
|---|---|
| `object_not_in_scope`、`unknown_object` | 对象不是本轮改动的；对象或 uses 不存在 |
| `unknown_block`、`basis_not_object` | 依据块不存在；依据块没有一块是该对象自己的原文（或经 applies_to 落到它身上的块） |
| `name_unknown` | 命令名、选项名、输入 JSON 的键、JSON pointer 里的键，没有出现在截至本轮的任何原文代码片段（行内代码和围栏代码）里 |
| `verbatim_not_found`、`verbatim_mismatch` | 引文不在所指的块里；期望值和引文说的不一样（引文本身、引文里填了占位符的行内代码形式、或引文里的数字） |
| `uses_missing` | 期望文字匹配了某个对象原文里的带占位符行内代码（如 `` `ERROR: file not found: <path>` ``），而检查自己的对象原文里没有这个形式，uses 里也没有任何一个拥有它的对象 |
| `script_missing`、`expect_invalid`、`target_invalid`、`input_invalid`、`retire_invalid`、`duplicate_key`、`shape` | 结构性错误 |

不拦的内容：检查选什么输入、读哪一行、uses 是否多余、故意构造的坏 JSON 输入（有测试）。

### 2.4 运行与比对

`CheckRunner`（`run`、`literals`）和 `ScriptSandbox` 两个接口。本地实现：
- 每次运行在新的临时目录里，环境变量只留 PATH、LANG、HOME，有超时，运行后把目录里的全部文件收回来；
- 输入路径必须是相对路径，不能含 `..`；
- 参考脚本用 `python3 -I` 或 node 运行。

比对规则：
- JSON 先解析，再按 pointer 取值比较；
- CSV 先解析，再取单元格；
- 数值在误差范围内算相等，数字字符串也按数值比较。

### 2.5 失败原因（按顺序判）

1. 超时：未知。
2. withdrawn 检查的断言仍然成立：未落地（`still_present`）。
3. 命令名、选项名，或输入 JSON 里出现的对象名（例如 `"op": "normalize"`），在程序源码的字符串字面量里根本没有：未落地（`missing_name`）。选项也认不带 `--` 的写法，Go 的 flag 包就是这样写的。
4. 输出的某一行匹配了原文里一条带占位符的规则，而这条检查并没有期望它：输入可疑，未知（`other_error_rule`）。
5. 期望成功（期望退出码 0，或没有写退出码断言），实际退出码非 0：输入可疑，未知（`rejected`）。
6. 其余：值不符，未落地（`value_mismatch`）。

失败的断言如果是业务断言，记在检查的对象上；如果是约定断言，记在 uses 里的约定对象上。

### 2.6 强弱与状态

强检查要同时满足两条：
1. 在基线上失败（withdrawn 检查反过来，要在基线上成立）。第 1 轮的基线是代码生成的程序，对任何调用都 exit 1 且无输出（`nullBaseline`）；之后的基线由调用方传入。
2. 至少有一条和数据有关的断言。判定办法见 4.1。

状态每轮只从这一轮的运行结果算，不继承上一轮：
- 只要有一条判为未落地的失败：未落地。
- 否则，有为它说话的强检查通过、且没有任何失败：已落地。
- 其余：未知，附原因码 `no_checks`、`only_weak`、`suspect_input`、`timeout`、`derived_disagreement`、`not_run`。

一条检查为谁说话：业务断言为它自己的对象说话，约定断言为 uses 里的约定说话。只按当轮的对象和当轮已入库的检查计算。回归：每轮把库里全部有效检查重跑一遍。

## 4. 需要设计会话决定的问题

**4.1 只有报错信息的检查算不算"和数据有关"。** 按字面，退出码加 stderr 的检查都不算数据断言，这样报错类约定永远只有弱检查，永远到不了已落地。我的判定：读产出内容（stdout、文件、JSON、CSV）且这次调用有输入文件的断言，或者期望文字里带着输入里的东西（某个参数值、输入文件的一行）的断言，都算和数据有关。于是 "ERROR: file not found: nope.csv" 算数据断言（文件名来自输入），只有退出码、文件是否存在、帮助文字不算。请确认这个口径。

**4.2 "没有失败才算已落地"会让一条坏输入的检查长期压住对象。** R1 那条算错摘要的 verify 检查每轮都判为输入可疑，verify 就一直是未知，尽管另一条强检查一直通过。设计里的"坏检查连续两轮后不再派"针对的是未落地的派活，对未知类失败没有说法。可选做法：
- 未知类失败不阻止已落地；
- 连续 N 轮输入可疑就退役；
- 把它交给模型复核。

**4.3 原文修订后旧检查怎么办。** R3 改了 z-score 的分母以后，R2 的检查在 R3 的正确程序上会失败，normalize 会被误判为未落地。传播（`stale`）留到第 4 块，所以这次让模型在推导时用 `retire_add` 退役它认为依据已被替换的检查，代码只核对编号存在、仍然有效。第 4 块做传播以后，是保留模型退役，还是全部改由代码按块状态标为过期？

**4.4 uses 漏标的判据。** 我只把带占位符的行内代码当作约定的"关键形式"，至少要有 4 个固定字符。只要检查自己对象的原文里有同一形式，就不要求标 uses。例如 R2 profile 自己写了 file not found 的格式，它的检查不标 error handling 也不退回。这样保守，但也会放过"本该标"的情况。同一形式出现在多个对象里时，uses 里有其中任何一个就算标了。

**4.5 "命令没实现"的代码事实。** 除了命令名和选项名，我把输入 JSON 里等于某个对象名的值（如 `"op": "fill"`）也算进来。否则一个没实现的操作会被程序以 `ERROR: invalid recipe: …` 拒绝，判成输入可疑，而不是未落地。字面量存在但没接上的情况，会落到后面几类。

**4.6 推导不一致的粒度。** 我按断言处理：不一致的那条记为未知并写明原因，同一检查里其余一致的断言照常入库；一条都没剩时，检查只留记录（`admission: unknown`），对象原因里记 `derived_disagreement`。如果设计要求整条检查判为未知，改一处即可。

**4.7 强弱在入库时判定一次，之后不重算。** 依据是当轮传入的基线。以后基线换了，强弱不跟着变。

**4.8 沙箱的隔离程度。** 本地实现只做到新目录、最小环境变量、`python -I` 和超时，没有文件系统层面的限制。真实运行换成 docker 时，参考脚本也应该放进容器。

**4.9 请求大小。** 检查推导的请求和归属一样，带全部原文（R1 约 21K 字符，越往后越大）。每轮对每个改动对象推导一次，要不要裁剪原文，等真实成本出来再定。

**4.10 没写成规则的地方。** 失败分类按"规则形式"匹配：只认原文里带占位符的行内代码，不认 dpipe 特有的写法。没有退出码断言的检查一律按"期望成功"处理；如果有合法的检查期望非 0 却不写退出码，它的失败会被判成值不符而不是输入可疑。
