# 实验 1：探针 + 小模型判断，能否发现产物的偏离（R1，2026-10-21）

**问题**：先运行产物，再对照原文判断对不对，生成一份纠错单。这条流程能发现多少问题？换写探针的模型、换判断的模型，结果差多少？

**做法**（原型，不是 IC 代码；脚本在 scratchpad `b5/hk2/judge/`）：
1. **探针**：写探针的模型拿到 R1 原文，以及原文中 130 条含具体值或代码的规则（第 9 块的单位度量），为每条规则写出一个能运行的调用。只写输入，不写期望。没有被任何探针覆盖的规则，由代码列出来，退回去补。
2. **运行**：每个探针在 16 份 R1 产物上各跑一次，在不联网的容器里。
3. **判断**：判断模型看到三样东西——规则原文、调用和输入、程序的实际输出——给出"对 / 错 / 看不出"，错的写进纠错单。

   每个批次里，同一个探针只放一份输出，判断模型无法拿不同产物互相比较。第一次组批时没有做这个限制，判断理由里出现了"同样的输入在不同运行里结果不同"，说明它在偷偷做差分测试。这一批结果已作废重做。
4. **度量**：拿纠错单对照缺陷库（`DETECTION-STUDY-R1-2026-10-21.md`）里官方认定的缺陷，逐个看是否命中。

**组合**：写探针 × 判断，各有 Haiku medium（上限参照）和 luna 5.6 medium（同一条链路）两种，共四组。

## 1. 两份探针

| | luna 5.6 medium | Haiku medium |
|---|---|---|
| 探针数 | 20（1 次补齐覆盖） | 46 |
| 每个探针覆盖的规则（中位数） | 约 7 条；最大的一个覆盖 31 条 | 2 条 |
| 有没有专门测边界 | 很少。例如表达式只用了 `log(abs(value))`，没有测 log(0) | 有。log 测了 0 和负数，还测了不存在的列、空值、旧行为的报错 |

luna 写探针时照样追求最少：把很多条规则塞进一次调用。凡是只被"列为覆盖"、实际没有被输入触发的规则，代码只能检查是否列出，查不出有没有真正测到。

## 2. 发现了哪些官方缺陷（不含 6-luna medium 的半成品）

| 缺陷（涉及的产物） | luna 探针，两种判断都一样 | Haiku 探针 + luna 判断 | Haiku 探针 + Haiku 判断 |
|---|---|---|---|
| log(0) 应为 NaN（7 份） | 0/7 | 6/7（另一份的表达式先崩溃，掩盖了它） | 同左 |
| window 结果列没有名字（3 份） | ✓ | ✓ | ✓ |
| window 崩溃（1 份） | ✓ | ✓ | ✓ |
| ntile 分组（3 份） | 部分 | ✓ | ✓ |
| aggregate min/max（1 份） | ✓ | ✓ | ✓ |
| 表达式解析或运算（2 份） | ✓ | ✓ | ✓ |
| 一元取反（1 份） | ✓ | ✓ | ✓ |
| avg 在没有数值时应为 NaN（1 份） | ✗（发现的是同类的 max） | ✓ | ✓ |
| window 不存在的列，报错文字不对（1 份） | ✓ | ✓ | ✓ |
| sort 不存在的列，应当报错（1 份） | ✗ | ✓ | ✓ |
| pivot 复合索引的行序（1 份） | ✗ | ✗ | ✗ |

- **结论一：决定能发现多少的，是谁来写探针，而不是谁来判断。** 同一份探针，Haiku 判断和 luna 判断得到的结论几乎一样；换成 Haiku 写的探针，luna 判断也能发现 log(0)、avg、sort 报错这些细节。
- **结论二：用好的探针，这条流程能发现上一份研究里漏掉的大部分细节。** 上一份研究用的是预先算好期望值的检查，13 份实现里 22 个缺陷区域只发现了 10 个；这里除 pivot 外基本都发现了。
- **结论三：它还发现了官方测试没有覆盖、但违反原文的地方**，几乎每份产物都有。例如：
  - 没有数值时 max 应为 NaN，程序给出 -Inf 或 0（原文 R1 第 109 行写明了）；
  - 校验顺序应当先类型、后范围，程序报成了范围错误（原文第 29 行）。

## 3. 误报：在官方满分的产物上（裸模型 1 和 5.6 medium 第 3 次，都是 219/219）

| 组合 | 满分产物上被判错的地方 |
|---|---|
| luna 探针，两种判断 | 无 |
| Haiku 探针 + luna 判断 | pipeline 失败信息要不要带 `ERROR:` 前缀；manifest 遇到空 CSV 文件时报错退出 |
| Haiku 探针 + Haiku 判断 | 上面两条，再加：逻辑运算结果输出成 `-0`；校验顺序（见上） |

满分产物上被判错的地方分两类：
- **原文确实有两种读法**：pipeline 的失败信息、`-0` 算不算 `0`、空 CSV 文件算不算要扫描的文件。这类问题判断模型自己定不下来，需要一个"原文歧义"的出口。不能当作缺陷派给执行方，否则它会被来回改。
- **原文写明了、官方没有测**：例如校验顺序。按原文这就是缺陷，派回去修是对的。只是官方分数体现不出来。

## 4. 成本（量级）

- **写探针**：luna 每次约 2.5 万 token（输出约 4 千），补齐一次；Haiku 一次。
- **判断**：每组十几个批次。luna 每批 1.5–6 万 token 输入，大多 30 秒内完成。

  如果实际流程里只判一份产物，每轮只需要几次调用。
- 这一轮的大头成本，来自同时测了 16 份产物和四种组合。

## 5. 对设计的含义

1. **探针的质量是关键，而且不能交给偏向"最少"的模型去自觉写全。** 光靠代码检查"规则是否被列出"不够。需要一个能发现"列了但没测到"的手段，例如：要求每个探针对每条规则写明它用哪个输入值去触发；或者把规则拆成更细的单位，一个探针只对应少数几条规则。这一条要在设计里正面解决。
2. **判断可以交给较小或不同来源的模型**：结论和 Haiku 基本一致，误报主要来自原文歧义。需要给判断加"原文歧义"这一类结论，并且这类结论不派给执行方。
3. **纠错单能直接告诉修复者"哪条原文、哪个输入、实际输出了什么"。** 这正是实验 2（回修）要检验的输入。
4. **还没有检验的**：
   - 修复者拿到纠错单后能否修对、会不会改坏别的（实验 2）；
   - 写探针的模型和写代码的模型是同一个时，会不会一起读错（这里写代码的大多是 luna high，写探针的是 Haiku 或 luna 5.6）。
