## 2. 数据结构与接口

### 2.1 原文块

- 每块是本轮原文的一个切片 `[start, end)`，带 `text`、`hash`（sha256 前 8 位）、`level`、`kind`、`parent`、`children`。每一层恰好拼回上一层，段落和句子带着它后面的空白，所以拼接逐字等于原文。
- 编号：`R3.S2`（小节）、`R3.S2.P1`（段落）、`R3.S2.P1.s2`（单元）、`R3.S2.P1.s2.c1`（子句）。小节按标题出现顺序平铺编号，嵌套关系记在 `parent`；第一个标题之前的文字是 `S0`。哈希不放进编号本身，引用时可以写成 `R3.S2.P1#ab12cd34`，代码核对哈希。
- 切法：
  - 小节：标题加其下全部内容，直到同级或更高级的标题（围栏代码里的 `#` 不算标题）。小节的子块是它自己的段落，然后是子小节。
  - 段落：小节自己的内容按空行切，围栏代码内的空行不切。
  - 单元（`s`）：围栏代码、表格、列表项（连同续行和项内的代码）各是一个单元，不再往下切；散文按句切。嵌套列表的每一项各是一个单元。
  - 子句（`c`）：句子按逗号、分号、括号切，行内代码里的不切；纯标点的碎片并到相邻子句。

### 2.2 模型这一步的输入

```
{ task: "attribute", round, sources, outline, objects, candidates }
```
- `sources`：R1 到本轮的全部原文，带编号标记（`⟦R3.S2#hash⟧`、`⟦R3.S2.P1#hash⟧`、段内多于一个单元时 `‹s2›`、句内多于一个子句时 `‹s2.c1›`）。去掉标记就是原文（有测试）。
- `outline`：本轮小节和段落编号及单元数，例如 `R3.S2 ### Fill linear…: P1(1) P2(4) P3(2)`。
- `objects`：已有对象只给 `id`、`name`、`version`、当前持有的块编号，以及已被替换过的部分（`modified`，有才给）。不重复原文。
- `candidates`：代码按名字在本轮段落里找到的已有对象及出现位置，只是候选。
- 修补请求在此基础上加 `previous_draft`（上次答案）和 `issues`（代码找到的具体问题），字段名与 `requestJson` 的排序约定一致：原文在最前，变化的部分在最后。

### 2.3 模型这一步的输出

```
assignments: [{ block, object_id | new_object, change: add|revise|withdraw|partial|none,
                replaces: [旧编号], overrides: [{ old: [旧编号], by: [本块内编号] }], note }]
references:  [{ from: 本轮块, to: 被引用块 }]
interpretations: [{ blocks, text }]
```
- 新对象只给名字，编号由代码按首块在文中的顺序分配（`O1`、`O2`……，永不复用）。同一答案里同名的新对象是同一个。
- `replaces`：整体替换（revise）或删除（withdraw）的旧单元。`overrides`：部分修订，旧的哪些单元或子句被本块的哪些单元覆盖。都只写编号；支持 `R2.S13.P4.s2..s4` 这样的范围。
- 修补的输出是补丁：`upsert`（按块替换或新增一条分配）、`remove`、`references_add`、`references_remove`。代码把补丁打到上次答案上，没提到的部分原样保留。
- 两个 schema 都通过了仓库里的 `strictSchemaProblems`。

### 2.4 代码核对（只拦确定的错误）

| 代码 | 含义 |
|---|---|
| `unknown_block`、`hash_mismatch` | 编号不存在（同时列出父块实际有哪些子块）；哈希对不上 |
| `not_this_round` | 分配了别的轮次的块 |
| `duplicate`、`overlap` | 同一块分配两次；选了粗层又分配了它里面的细层 |
| `uncovered` | 有块没被覆盖（报最粗的那一层） |
| `range_invalid` | 范围反向、为空或越界（说明实际范围，如 `s1..s5`） |
| `object_choice`、`unknown_object`、`name_taken` | 对象写法不对；对象不存在；新名字与已有对象重名（提示用哪个编号） |
| `change_shape` | `add`/`none` 却带了替换目标；`revise`/`withdraw` 没有目标；`partial` 没有 overrides |
| `by_outside_block` | 覆盖方的编号不在本条分配的块里 |
| `target_not_earlier`、`target_unowned`、`target_replaced` | 替换目标不是更早的轮次；没有对象持有；已经被替换过（应引用当前有效的新文） |
| `reference_invalid` | 引用边的引用方不在本轮，或指向更晚的轮次 |
| `unparseable`、`shape`、`transport` | 回答不是 JSON；结构不符；调用本身失败 |

哪一块归哪个对象、是新增还是修订、引用边该不该有，都不核对（有测试：把 normalize 的修正归给 fill、把 pipeline 扩展标成 profile 的部分修订，都照样通过）。

重试：首答之后最多 `maxRepairs` 次修补（默认 2），每次调用都记录在状态里，包括请求全文、回复原文、核对出的问题、token 用量、是否替身。回答读不出来时下一次重新请求首答，不对空答案打补丁。用完次数仍不通过，本轮记为失败，对象不登记，可以重新喂这一轮。

### 2.5 对象、版本、改动记录

- 对象：`id`、`name`、`created_round`、`version`、`blocks`（每块的状态 active / partially_modified / superseded / withdrawn，以及收到的修改）、`history`。
- 状态规则：`replaces` 指向一个整块，该块变为 superseded（revise）或 withdrawn（withdraw）；指向块内的一部分，或者来自 `overrides`，该块变为 partially_modified，旧文保留，被改的部分记下来。部分修订从不删文本。
- 改动记录按（轮次，对象）一条：`C5.2`、类型集合、本轮分给它的块（`entries`）、它的旧块收到的修改（`received`，可能来自别的对象的新块）。对象只要有改动就升一版，这包括"自己的旧块被别的对象的新文覆盖"。
- 本轮范围 = 本轮有改动记录的对象，即版本变化的对象，代码算出。
- 引用边、解读按轮次追加。
- "疑似该拆/该合"只在状态里留了 `signals` 位置，没有计算。

### 2.6 存储

`exp2-state.json`：`sources`（每轮原文与哈希）、`calls`（每次模型调用）、`rounds`（每轮结果：接受的答案与新对象编号分配，或失败的问题）、`signals`。对象和改动记录不存，每次从 `sources` 加 `rounds` 重放出来，所以同一事实只有一处。写入前核对四个列表只追加、旧条目逐字不变；锁文件写进程号，活着的进程占锁时拒绝写入。

`npm test`：742 项，735 通过，1 项失败为原本就失败的 `repair-batch`（缺夹具）。在不含本次改动的基线上同样只有它失败。新增 54 项全部通过。

切分（15 轮全部）：
- 四层逐字拼回原文，没有空块，哈希与切片一致。

- R12：normalize 再升一版，`R2.S11` 依次收到 R3、R3、R12 三处修改。

跨轮：
- 每一轮的块都恰好被覆盖一次，原文块不丢。
- 对象编号连续不复用，名字不重复；版本数等于改动记录数，每条记录 from/to 连续。
- 每一轮相对上一轮：已有对象编号和名字不变；只有本轮范围内的对象升一版，其余对象完全不变；已登记的归属不变，块状态只往前走；改动记录和引用边只追加。
- 状态文件重新打开后重放出同一个登记；同样的输入和替身答案跑两遍，状态文件逐字节相同。
- 20 次调用（15 次首答加 5 次修补）全部记录，usage 全为 0 且标为替身（`stub:scripted` 或 `stub:rule`）。

其他：修补不收敛时第 3 次调用后停止，本轮记失败、不登记对象，之后可重新喂；回答不是 JSON 时下一次重新请求首答；调用失败时本轮记失败并保留这次调用的记录；乱序喂轮次、同一轮换文本、修改已有条目、活锁都被拒绝。

规模：R15 的请求约 114K 字符，其中带标记的原文 105K（原文本身 89K，标记约占 18%），对象清单 4.3K。状态文件跑完 15 轮约 2 MB，大部分是每次调用的请求全文。

## 4. 设计问题、我的取舍、需要设计会话决定的地方

**4.1 列表项不往句子切，和"句中片段"的修订冲突。** 任务要求列表项不再切句子。但很多修订落在列表项的半句上：R5 让 transform 的结尾项 "write the result CSV to `<output>`, its SHA-256 to `<output>.sha256`" 只失效后半句；R2 fill linear 第 4 条只失效"缺一侧锚点"的情形；R13 的第 4 步。现在只能整项引用，所以这类修订一律记为部分修订（块标被部分修改，旧文保留，靠并排展示让读者对照），不会误删仍有效的前半句。是否允许列表项按子句再切，请决定。

**4.2 一个不可再切的单元同时写到两个对象。** R5 的 "The `.sha256` sidecar files produced during `ingest` and `transform` are removed" 和 "If `<output>.sha256` exists…, `ingest` and `transform` must remove it" 都是单个列表项。每块只能归一个对象，我的处理：
- 如果这句覆盖了另一个对象的旧文（前一句覆盖 transform 的结尾项），那个对象通过"收到修改"自动得到改动记录并升版，进入本轮范围。
- 如果只是新增要求、没有覆盖旧文（后一句"必须删除旧文件"对 transform 也成立），transform 只能拿到一条引用边，它的改动记录里看不到这条要求。R5 的替身答案里 transform 仍在范围内，是因为同一节的另一项点名了它；换一份原文就不一定。

可选方向：允许一块有次要归属；或者让引用边也算被引用对象的改动；或者接受这个缺口，作为第 4.3 节的缺口信号。请决定。

**4.3 不是需求的文字。** 每轮的前言（"Add the following capabilities…"）和分隔线 `---` 不属于任何对象。设计写的是每块恰好归一个对象，我加了 `change: "none"`（不归对象，但算已覆盖）。R1 的前言是真需求（Go、确定性），替身答案把它归给了一个"tool"对象。

**4.4 版本号。** fill 在 R2 新增了 linear 策略，按"有改动就升版"已经是 v2，所以 R3 之后是 v3，不是任务描述里举例的 v2。测试断言的是"R3 升一版"。

**4.5 新增还是部分修订，由模型判断，代码不拦。** R2 的 fill linear（R1 的策略列表写成封闭的三选一）和 R12 的 normalize 默认值，替身答案都记成部分修订，把旧的列表项标为被部分修改；按 `UPDATE-TAXONOMY.md` 的口径这两处"不作废"。两种记法代码都接受，版本和范围也一样（对象都会升版）；差别只在旧块是否标出。真实模型怎么选，会影响以后传播块的过期标记。

**4.6 已被替换的文本不能再当替换目标（`target_replaced`）。** 我把它当成确定错误：新的修订应该引用当前有效的那段新文。如果设计认为模型同时引用新旧两处是合理的，可以把它降为提示。

**4.7 宽松列表在空行处切段。** R1 的 Supported operations 是一个各项之间有空行的列表，项内还有缩进段落。如果"列表整体不拆"也覆盖这种情况，整个操作列表就是一个段落，无法按段落细分到操作。我只保证没有空行的连续列表不被切，宽松列表按空行切。这样 R1 transform 一节切出 24 个段落，各操作可以按段落或列表项分开。

**4.8 对象视图里，整节归属的旧块，旧的一侧是整节。** 例如 fill 的 `R2.S13`，并排的旧侧是整节文字。规则是不给孤立的句子，所以我取持有的那一块作上下文；如果希望旧侧只给被改单元所在的段落，改 `view.ts` 一处即可。

**4.9 成本。** 每轮把全部原文交给模型，R15 一次首答约 114K 字符。修补的 schema 和系统提示与首答不同，按 BACKGROUND §5 的实测，两者之间不能复用缓存。如果要省，可以考虑首答和修补共用一个 schema（例如都输出补丁形式）。请决定是否值得。

**4.10 候选对象按名字匹配。** "pipeline"、"transform"、"lineage" 这类名字几乎每轮都会命中。候选只作提示，不进入核对，所以命中多一些只是请求长一些。

**4.11 规则替身。** R4、R6、R8、R9、R11、R14 用规则替身：每个顶层小节（有轮标题时取二级小节）一个对象，按标题里的反引号名字或标题文字取名，名字与已有对象相同就归给它，标为 `stub:rule`。它只用来验证跨轮不漂移，不代表合理的归属，例如它把 R8 的 Pipeline/Lineage extension 子节归给了 quality。

**4.12 OpenCode 接入。** `createOpenCodeAttributionTransport` 按首答和修补各建一个结构化传输，返回 usage 和 schema 错误。本次没有调用，真实运行前需要在本地验证一次。
