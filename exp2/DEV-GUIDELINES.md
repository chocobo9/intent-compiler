# 开发守则

## 1. 分工：确定性交给代码，理解交给模型

- **代码做**：编号、版本、来源定位、登记、投影、运行、比对、按规则计算状态、提交与检查点、预算与超时。
- **模型做**：分类、拆分与归属、推导、构造输入、对照判断、写代码。
- 模型的输出必须落到统一词汇的编号上（对象、段落、改动、检查……），代码才能接着处理。其余内容是模型自由书写的文字，代码只引用，不解析。

## 2. 不要把规则写死（实验 1 一再吃亏的地方）

代码负责确定性，并不等于把规则写成一张"看到 X 就判 Y"的清单。实验 1 中这类规则多次把范围收得过窄、过严，结果是误判、整批作废，局部补丁越积越多。写规则之前先问三个问题：

1. **这条规则是按需求的含义写的，还是按这一份 dpipe 文本的样子写的？** 比如"原文代码片段里出现的 JSON 键名，在代码里应该存在"是按含义写的；"有 `--seed` 的命令要……"是按文本写的，不要写。
2. **遇到没见过的情况，它会怎样？** 应当退回给模型去判断，或者判为"未知"；不能误判，也不能让整批作废。
3. **它会不会把正确的东西挡在外面？** 门禁只拦确定的错误：编号不存在、段落不存在、期望值在原文里找不到。凡是需要理解的地方，都不设硬门禁。

具体做法：
- 宁可多出一个"未知"，也不要一条硬判。
- 输出格式要求模型写的结构尽量少：能由代码推出来的，就不要让模型写（参见 `BACKGROUND.md` §4.2 的 SpecArt）。
- 模型输出校验失败时，把具体哪里不对告诉模型，让它修改原答案，不要从头重写，也不要无限重试。重试次数要有上限，并且记录下来。
- 不为单个失败案例加专门的规则。先看清这一类失败的共同原因，再改通用机制。

## 3. 离线验证要贴近真实设计

离线验证不调用模型。它要回答的问题是：**这套设计放到真实运行里，会不会照预期工作。**
- **用真实的输入**：`inputs/dpipe/` 里的原文，按轮次一轮一轮地喂。不要用为测试临时编的短文本，只验证代码分支有没有走到。
- **模型的那部分，用固定答案替代**：写一份"假如模型这样回答"的样本，形态要接近真实的模型输出，包括常见错误（漏一个对象、段落归属错、编号写错）。然后检查代码的反应是否符合设计：能核实的核实，能退回的退回，不能判断的记为"未知"。
- **执行方也可以替身**：用一个脚本按工单改代码、提交，模拟"做对一部分、做错一部分、中途失败"，验证分步保留和继续执行是否成立。
- **跨轮测**：至少连续跑几轮，验证版本、对象归属、改动记录、检查库在轮与轮之间不漂移，也不重复。
- **验证要对着设计意图写**，而不是对着实现写：断言"第 3 轮修订了 fill 之后，fill 的对象升到 v2，旧段落标为被部分修改，下一轮工单的任务区里有它"，而不是断言"某个函数返回了某个值"。
- `reference/UPDATE-TAXONOMY.md` 给出了每轮更新的类型和"当前有效要求"的读法，可以用来**设计**离线验证的场景和期望（例如某一轮应该产生哪类改动），**但不能把它写成系统规则**，也不能让系统只认这几种类型。另外，它包含未来轮次的内容，**绝不能作为任何模型调用的输入**。

## 4. 不能做的事

- 不读、不推断、不反推官方测试和参考答案。
- 不写针对 dpipe 的专用规则。
- 不把执行方写的东西（文档、注释、它自己的测试）当成需求，也不当成落地的证据。
- 不因为一次失败就加规则，也不因为一次成功就认为稳定。
- 发现设计有问题、需要改设计的地方，写下来交回设计会话，不要自己扩大或收窄范围。

## 5. 记录

- 每次模型调用都记录 token：输入、缓存读、输出，按环节分开（理解、工单、编码、验收、纠错）。
- 每轮生成一份结构化记录：本轮范围、各区条目、每一步的提交和检查结果、各对象的状态及其依据。之后的每轮报告从这份记录生成。
