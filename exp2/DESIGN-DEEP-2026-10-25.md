# IC 实验 2：深度设计（2026-10-25）

状态：设计稿，交用户验收。它取代 DESIGN.md §6a–§6c 中与之冲突的部分；不冲突的部分（§6b 三句话、权威表、守卫规则、§12i 判定、§12j 合并决定）继续有效。每条机制后面标注它对应的**失败类**和**证据位置**；没有失败类的机制一律不进。

## 0. 痛点与主张

痛点（观察）：便宜档位的执行方在多轮规格上有两种错——**漏做**本轮新需求，**改坏**早轮已成立的行为。对照组（同一执行方 + 带工具审查员 + 累积全文）也有这两种错，它靠审查员一遍遍重读全文来压，所以贵。

主张（待 §12i 证明）：把"看见、送到、修好"三件事拆开，各由一种事实驱动，能在不涨成本的前提下压住这两种错。

四次运行（rep1j/k/l/m）给出的分工图：

| 能力 | 现状 | 证据 |
|---|---|---|
| 看见（审查→检查→守卫）| 做到大半：挂掉的命令 70–90% 被审查员提到；守卫抓到真实回退（sha256）且翻转分类正确 | evidence/review-recall-2026-10-25 |
| 送到（发现送修、原文交付）| 有两个洞：存在性断言被 value_not_stated 记录不送（rep1j R5 三次）；横切变更只送到部分命令（manifest 漏 10+5 用例）| 同上 §3、§4 |
| 修好（修补回路）| 主要丢分处：轮末仍挂的用例 90% 以上在审查员已报过的命令上；材料送到，执行方只做一部分，规则把"没碰"当"无进展"停送 | NIGHT rep1l §2、rep1m |
| 底座（原文状态：句子、修订、分组）| 句子与修订可靠（修订召回完整，精度 rep1j 0/7、rep1l 一致）；分组按"部件"不按"变化"，关系边零收益 | corpus-scan、evidence/corpus-topics |

下面按四层写：每层先写它拥有的**事实**，再写**机制**，再写**度量**（预先写死，基线取自四次运行）。

## 1. 底座：原文状态层

### 1.1 事实

三种，各一个主人：
- **句子**（代码）：R{n}.S.P.s 编号，append-only，永不改写。不变。
- **修订**（模型提出，可反驳）：句子 → 句子的 revise / withdraw / partial。每条修订必须带一个**出处标签**：`cue`（原文有作者线索：changes to、previously、instead of、no longer、unchanged、作者编号）、`inferred`（模型判断，原文无线索）。`cue` 的线索片段原样记录。
- **变化单元**（新，替代"对象"做分组）：一组会一起被改的句子。定义不是"讲同一个部件"，是"文档说它们一起变"。来源四种，每个单元带来源标签：
  1. `cue`：作者写了"版本格式变了 → validate/build/diff/promote 各怎么变"、"Changes to X"、Previous/New、F16 这类编号——这些段落里被点名的句子组成一个单元；
  2. `revision`：一条修订把新旧两句连成一个单元（修订本身就是"一起变"的最直接证据）；
  3. `guard`：一条检查运行时读到的句子集合（检查的 units）组成一个单元——这是**观察出来的**共依赖，不是声称；
  4. `model`：只在前三种都没有时由归属模型提出，标 `model`。
  一句可属多个单元。单元可跨命令。

**对象（命令、部件）降级为标签**：仍由归属起名，仍用于任务区列表和三方共同语言，不再是交付单位、不再是边的端点。

依据：语料扫描（evidence/corpus-topics）——26 个任务里 30 轮有"一个概念改多个命令"，61 轮有范围声明，66 轮有作者编号，34 轮有显式新旧并列；dpipe 是全语料最按命令分节、横切变更最少的任务（15 轮 1 次），"对象 = 命令"在它上面几乎不用判断，所以在它上面长出来的对象层证明不了通用性。rep1j R5 哈希改法漏掉 manifest 是横切变更在本系统里真实丢分的一例。

### 1.2 机制

- 归属的输出从"每句一个对象 + 对象级边"改为"每句 ≥1 标签 + 修订（带出处）+ 变化单元（带来源）"。applies_to / refers_to 对象级边**取消**（四次运行零收益）。
- 范围声明进入状态：原文说"没提到的行为全部照旧 / 第 1–4 轮行为继续成立"，代码记为"本轮所有守卫在力"，不需要模型。这是把作者已经写明的守卫范围读出来（可观察文本特征）。
- 当前有效文本的计算只依赖句子 + 修订，与分组无关（现在就是如此，写明）。

### 1.3 度量

| 量 | 线 | 基线/来源 |
|---|---|---|
| 修订召回对 gold（dpipe）| 100% | rep1j/rep1k 已达 |
| 修订精度对 gold | ≥ 90%，`cue` 类 100% | rep1j 0/7、rep1k 0/1、rep1l 一致（三次方差大，先看 cue 类）|
| 变化单元来源分布 | 报告，不设线 | 新 |
| 横切单元被送到的命令数 / 单元涉及的命令数 | 100% | rep1j R5 manifest 0/1 |

## 2. 看见：验收层

### 2.1 事实

- **发现**（审查员）：指向句子。
- **检查**（formalizer → 代码运行）：命令、输入、断言；断言的期望形式有三种：值、关系、**存在性**（文件/输出/字段应有或应无）。第三种现在不存在，这是 rep1j R5 三条"transform 写了禁止的旁路文件"被 value_not_stated 记录不送的直接原因。
- **守卫**：通过的检查；绑在句子上；翻转按修订记录分类。不变。

### 2.2 机制

- 存在性断言成为一等期望形式；`value_not_stated` 对存在性断言不触发。（失败类：看见了没送出；证据 review-recall §4。）
- 审查请求按**变化单元**组织横切条目：本轮某单元跨 k 个命令时，审查请求列出这 k 个命令，各要一条检查；缺的记为覆盖缺口。（失败类：横切漏看；证据 manifest 10+5 用例。）
- 盲区账本：离线用官方首次交付失败对审查发现算 op 级召回（已有脚本），每次真实运行后更新；运行中不用它（运行中没有官方测试）。
- 其余（三次审查、复现、两条前提、守恒、按原话送出的兜底）不变。

### 2.3 度量

| 量 | 线 | 基线 |
|---|---|---|
| 首次交付挂掉的 op 被提到 | ≥ 85% | 70–90% |
| 看见了没送出（logged 且当轮对应 op 轮末仍挂）| 0 | rep1j R5 一类 3 条 |
| 复现成立率（发出条目）| ≥ 90% | rep1m 15/15、rep1i 8/9 |
| 原文未改的翻转 | 不高于前一版本 | rep1k 1 次 |

## 3. 送到：交付层

### 3.1 事实

本轮包（给执行方、审查员、formalizer 同一份）的内容只有五类，每类有理由：
1. 本轮新增/修订句子所在的段（带标题路径）——本轮任务；
2. 被本轮修订的早轮句所在的段，新旧并列——让执行方知道删什么；
3. 本轮触及的**变化单元**里、落在其他命令上的句子所在的段——横切交付（这是"按关系交付"的真正内容，取代对象级边）；
4. 未结条目所在的段；
5. 对照守卫：只给绑在被修订句上的守卫（命令、输入、当前输出）。
不给：整对象视图、守卫清单、未触及单元的任何早轮文本。

### 3.2 机制

- 绝对预算 40k；超限先裁第 3 类里"单元来源为 model"的段，再裁第 4 类，第 1、2 类不裁；每轮报告各类字符数和裁掉的段。（失败类：R2 预算挡住规则带回的段；证据 NIGHT O2 测量。）
- 守住全在代码，不交付。不变。

### 3.3 度量

| 量 | 线 | 基线 |
|---|---|---|
| R3+ 包字符 | ≤ 本轮原文 × 2 + 10k | 已达（9–24k）|
| 审查员引用的句子 100% 在包内 | 100% | rep1k/l/m 100%，rep1j R2 3/4（常驻边）|
| 第 3 类段被审查员或执行方用到的比例 | 报告，不设线 | 新 |

## 4. 修好：修补回路（重做）

### 4.1 事实

每条送出的条目，在每个修补周期后有一个**结局**，由代码判定，不读执行方的话，也不靠名字映射：
- `fixed`：条目的检查通过；
- `touched`：检查未通过，但该检查的输出与上一周期不同（程序在这条输入上的行为变了）；
- `untouched`：检查未通过且输出与上一周期逐字相同（程序在这条输入上没变）。

修订说明（2026-10-25 晚，依据 evidence/repair-outcome-2026-10-25）：初稿用"diff 是否碰到命令锚点"定义 touched。离线一算，锚点名与对象名几乎对不上（310 条里 160 条映射不到），要靠去词尾的启发式才能算。输出比对是现成的、可观察的、不需要任何映射，所以改用它。现行停送规则其实已经按"输出摘要未变"判，错的不是检测，是把"未变"当成"试过无进展"去停送。

离线基线（stem 映射口径，四次运行 310 条送出）：有结局的 232 条里 fixed 55%、touched 10%、**untouched 35%**；81 条 untouched 里 74 条被"无进展"停送，48 条带入下一轮；rep1k R3/R4 的 untouched 10/16、12/20 全部被停送。

### 4.2 机制

- **停送只对 touched**：touched 两个周期仍不 fixed → 停送、送审查员裁决（现有 contest 路径）。untouched 不停送，**单独重发**（一条一消息），直到 touched 或周期用尽。（失败类：送到了没碰；证据 repair-outcome：74 条 untouched 被停送。）
- **消息条目上限：不设。** 初稿提议每消息 ≤ 6 条；离线分组显示 1–5 条消息的 untouched 占比（43%）并不低于 11 条以上（33%），"大消息导致没碰"不成立，撤回。
- **排序**：本轮新命令的条目先于带入条目。依据只有 rep1l R2 一例（执行方首次交付收尾做的全是 R1 带入条目），标为假设，下一次真实运行看。
- **周期预算按条目算**：轮结束条件 = 全部 fixed，或剩余全部为 touched 且已裁决，或周期上限。untouched 带入下一轮任务区顶部，标 "untouched since R{n}"。
- 执行方回复里的条目确认（done / not done / disagree）只用于**路由**（disagree → 审查员），不作为事实；事实仍是检查结果。
- 环境错误（docker 不在等）终止周期而不是作为失败送执行方。（证据 rep1f。）

### 4.3 度量

| 量 | 线 | 基线 |
|---|---|---|
| 送出条目中 untouched 占比（轮末）| ≤ 10% | 35%（四次运行，232 条有结局）|
| 送出条目 fixed 占比（轮末）| ≥ 70% | 55% |
| 因"无进展"停送的 untouched 条目数 | 0 | 74 / 四次运行 |
| 轮末仍挂且 op 已被提到的用例数 | 比基线降一半 | rep1l R2 110、rep1m R2 27 |

## 5. 守卫：不变的部分

守卫出生（库检查 + 审查确认）、每周期重跑、翻转按修订记录分类、未改即回退、改过即过期——不变。新增一条：范围声明（§1.2）使所有守卫在力，不需要模型。

## 6. 删掉的

对象级关系边；对象作为交付单位；利用率验收线；formalizer 的输入声称（已删）；回放工具 strict 列（已删）；"无进展"作为停送的唯一判据。

## 7. 验证顺序（给用户的验收路径）

全部离线先行，模型运行最后：
1. **修补结局分类**（零成本）：对四次运行每条送出条目按 §4.1 判 fixed/touched/untouched，出表。这是 §4 的前提，也是"修好"层的基线。
2. **变化单元的 cue 提取**（零成本）：在 dpipe 和三个形状相反的任务（d10_w4、d12_w1、d8_w5）上只做代码侧的 cue 提取，数出 cue 单元、范围声明、作者编号；看 §1 的 cue 层能覆盖多少。
3. **存在性断言**（离线重放 rep1j R5）：三条旁路文件发现应送出。
4. 开发按 §2–§4 做批，重放验收 §2.3/§3.3/§4.3 的离线项。
5. 一次 6 轮真实运行，验 §4.3 的四个量和准确率线；通过后 §12i。

## 8. 为什么这是"深"而不是"重"

每层只有一种事实、一个主人；新增机制四条（存在性断言、横切审查、修补结局、范围声明），每条对应一个有编号的失败类和一处证据；删掉的比加的多。模型只在两处做判断（归属提出修订与 model 类单元；审查员报发现），两处都可被后面的事实反驳（gold、检查、守卫）。代码不读模型文本来定事实，只读它来路由。
