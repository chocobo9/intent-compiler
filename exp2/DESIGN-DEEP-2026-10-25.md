# IC 实验 2：深度设计（2026-10-25）

状态：设计稿，交用户验收。它取代 DESIGN.md §6a–§6c 中与之冲突的部分；不冲突的部分（§6b 三句话、权威表、守卫规则、§12i 判定、§12j 合并决定）继续有效。每条机制后面标注它对应的**失败类**和**证据位置**；没有失败类的机制一律不进。

## 0. 痛点与主张

痛点（观察）：便宜档位的执行方在多轮规格上有两种错——**漏做**本轮新需求，**改坏**早轮已成立的行为。对照组（同一执行方 + 带工具审查员 + 累积全文）也有这两种错，它靠审查员一遍遍重读全文来压，所以贵。

主张（待 §12i 证明）：把"看见、送到、修好"三件事拆开，各由一种事实驱动，能在不涨成本的前提下压住这两种错。

四次运行（rep1j/k/l/m）给出的分工图：

| 能力 | 现状 | 证据 |
|---|---|---|
| 看见（审查→检查→守卫）| 做到大半：挂掉的命令 70–90% 被审查员提到；守卫抓到真实回退（sha256）且翻转分类正确 | evidence/review-recall-2026-10-25 |
| 送到（发现送修、原文交付）| 一个洞：横切变更只送到部分命令（manifest 漏 10+5 用例）。初稿写的"存在性断言被记录不送"经重放证伪：三条都送出并复现，真正卡点是一条方向写反的守卫 G57 把三次正确修补回退（见 §2.2）| 同上 §3；repair-outcome / NOTES §28 |
| 修好（修补回路）| 主要丢分处：轮末仍挂的用例 90% 以上在审查员已报过的命令上；材料送到，执行方只做一部分，规则把"没碰"当"无进展"停送 | NIGHT rep1l §2、rep1m |
| 底座（原文状态：句子、修订、分组）| 句子与修订可靠（修订召回完整，精度 rep1j 0/7、rep1l 一致）；分组按"部件"不按"变化"，关系边零收益 | corpus-scan、evidence/corpus-topics |

下面按四层写：每层先写它拥有的**事实**，再写**机制**，再写**度量**（预先写死，基线取自四次运行）。

## 1. 底座：原文状态层

### 1.1 事实

三种，各一个主人：
- **句子**（代码）：R{n}.S.P.s 编号，append-only，永不改写。不变。
- **修订**（模型提出，可反驳）：句子 → 句子的 revise / withdraw / partial。每条修订必须带一个**出处标签**：`cue`（原文有作者线索：changes to、previously、instead of、no longer、unchanged、作者编号）、`inferred`（模型判断，原文无线索）。`cue` 的线索片段原样记录。
- **变化单元**（新，替代"对象"做分组）：一组会一起被改的句子。定义不是"讲同一个部件"，是"文档说它们一起变"。来源四种，每个单元带来源标签：
  1. `cue`：作者写了"版本格式变了 → validate/build/diff/promote 各怎么变"、"Changes to X"、Previous/New、F16 这类编号——这些段落里被点名的句子组成一个单元；
  2. `revision`：一条修订把新旧两句连成一个单元（修订本身就是"一起变"的最直接证据）；
  3. `guard`：一条检查运行时读到的句子集合（检查的 units）组成一个单元——这是**观察出来的**共依赖，不是声称；
  4. `model`：只在前三种都没有时由归属模型提出，标 `model`。
  一句可属多个单元。单元可跨命令。

**对象（命令、部件）降级为标签**：仍由归属起名，仍用于任务区列表和三方共同语言，不再是交付单位、不再是边的端点。

依据：语料扫描（evidence/corpus-topics）——26 个任务里 30 轮有"一个概念改多个命令"，61 轮有范围声明，66 轮有作者编号，34 轮有显式新旧并列；dpipe 是全语料最按命令分节、横切变更最少的任务（15 轮 1 次），"对象 = 命令"在它上面几乎不用判断，所以在它上面长出来的对象层证明不了通用性。rep1j R5 哈希改法漏掉 manifest 是横切变更在本系统里真实丢分的一例。

### 1.2 机制

- 归属的输出从"每句一个对象 + 对象级边"改为"每句一个属主标签（实现上保持单一属主，跨命令由单元表达）+ 修订（带出处）+ 变化单元（带来源）"。翻转分类、检查重新派生、任务区中原来依赖边的地方改为单元同属（guard 单元不参与翻转分类）。applies_to / refers_to 对象级边**取消**（四次运行零收益）。
- 范围声明进入状态：原文说"没提到的行为全部照旧 / 第 1–4 轮行为继续成立"，代码记为"本轮所有守卫在力"，不需要模型。这是把作者已经写明的守卫范围读出来（可观察文本特征）。
- 当前有效文本的计算只依赖句子 + 修订，与分组无关（现在就是如此，写明）。

### 1.3 度量

| 量 | 线 | 基线/来源 |
|---|---|---|
| 修订召回对 gold（dpipe）| 100% | rep1j/rep1k 已达 |
| 修订精度对 gold | ≥ 90%，`cue` 类 100% | rep1j 0/7、rep1k 0/1、rep1l 一致（三次方差大，先看 cue 类）|
| 变化单元来源分布 | 报告，不设线 | 新 |
| 横切单元被送到的命令数 / 单元涉及的命令数 | 100% | rep1j R5 manifest 0/1 |

## 2. 看见：验收层

### 2.1 事实

- **发现**（审查员）：指向句子。
- **检查**（formalizer → 代码运行）：命令、输入、断言；期望形式有值、关系、存在性（file_exists，已有）。修正（10-25 晚）：初稿说存在性断言不存在、导致 rep1j R5 三条被记录不送——重放证伪，三条都送出并复现。真实缺陷有两个，都在代码里：(a) 布尔期望 `false` 永远不会逐字出现在原文里，所以 file_exists 必触发 value_not_stated（只记录，不挡）；(b) 守卫 G57 由库检查 K37 出生时 direction=withdrawn 把断言取反，而断言已经按新要求写成"文件不存在"，双重否定后守卫守的是已撤回的旧行为，三次正确修补被判 regression 回退，条目因"回退后已重发过一次"停送，R6 才修好。
- **守卫**：通过的检查；绑在句子上；翻转按修订记录分类。不变。

### 2.2 机制

- **检查只陈述当前文本要求的行为，不再有取反方向**：direction=withdrawn 作为对断言的否定算子删除；撤回由断言本身表达（file_exists=false）。（方向删除后不存在"冲突"，不加出生校验；旧记录的 withdrawn 一律按 holds 读，并记一笔。）（失败类：守卫守旧行为、回退正确修补；证据 G57，rep1j R5 三次回退。）
- 布尔期望的"已陈述"判定改为"引用单元提到该文件（名或扩展名）"，两处调用点共用一个函数。（失败类：存在性检查永远 value_not_stated；证据 NOTES §28。）
- 审查请求按**变化单元**组织横切条目：本轮某单元跨 k 个命令时，审查请求列出这 k 个命令，各要一条检查；缺的记为覆盖缺口。（失败类：横切漏看；证据 manifest 10+5 用例。）
- **审查范围不再由文本体积决定，由两张名单决定**（2026-10-25 晚，依据 rep1n 与 r2-findings-on-r1 对照）：
  1. 未结名单：轮末仍有失败检查、untouched 条目或开放项的命令；
  2. 轮巡名单：上次被审查员发现过问题、但已 ≥ 2 轮没有任何条目的早轮命令，每轮最多 2 个，轮转。
  审查请求为名单上的每个命令附其当前段（不是整对象视图），并要求各至少一条检查。证据：三次运行 R2 落在 R1 命令上的发现，引用的句子全部来自包里恰好出现的 R1 文本（rep1j 整对象视图、rep1k/rep1n 开放项段）；没有被开放项指着的 R1 命令，审查员看不到也不报。rep1n R1 末挂 52、开放项只覆盖一部分，16 个用例从 R2 挂到 R6。按对象交付时这件事被整对象视图"顺带"做了，代价是全文体积；名单是把这件事做成显式的、有上界的机制。
- 盲区账本：离线用官方首次交付失败对审查发现算 op 级召回（已有脚本），每次真实运行后更新；运行中不用它（运行中没有官方测试）。
- 其余（三次审查、复现、两条前提、守恒、按原话送出的兜底）不变。

### 2.3 度量

| 量 | 线 | 基线 |
|---|---|---|
| 首次交付挂掉的 op 被提到 | ≥ 85% | 70–90% |
| R2 末 R1 用例残留 | ≤ 基线（rep1j 1、rep1k 1）| rep1n 16 |
| 轮巡名单带来的发现数 | 报告 | 新 |
| 因错误守卫回退的正确修补次数 | 0 | rep1j R5 3 次（G57）|
| 复现成立率（发出条目）| ≥ 90% | rep1m 15/15、rep1i 8/9 |
| 原文未改的翻转 | 不高于前一版本 | rep1k 1 次 |

## 3. 送到：交付层

### 3.1 事实

本轮包（给执行方、审查员、formalizer 同一份）的内容只有五类，每类有理由：
1. 本轮新增/修订句子所在的段（带标题路径）——本轮任务；
2. 被本轮修订的早轮句所在的段，新旧并列——让执行方知道删什么；
3. 本轮触及的**变化单元**里、落在其他命令上的句子所在的段——横切交付（这是"按关系交付"的真正内容，取代对象级边）；
4. 未结条目所在的段；
5. 对照守卫：只给绑在被修订句上的守卫（命令、输入、当前输出）。
不给：整对象视图、守卫清单、未触及单元的任何早轮文本。

### 3.2 机制

- 绝对预算 40k；超限先裁第 3 类里"单元来源为 model"的段，再裁第 4 类，第 1、2 类不裁；每轮报告各类字符数和裁掉的段。（失败类：R2 预算挡住规则带回的段；证据 NIGHT O2 测量。）
- 守住全在代码，不交付。不变。

### 3.3 度量

| 量 | 线 | 基线 |
|---|---|---|
| R3+ 包字符 | ≤ 本轮原文 × 2 + 10k | 已达（9–24k）|
| 审查员引用的句子 100% 在包内 | 100% | rep1k/l/m 100%，rep1j R2 3/4（常驻边）|
| 第 3 类段被审查员或执行方用到的比例 | 报告，不设线 | 新 |

## 4. 修好：修补回路（重做）

### 4.1 事实

每条送出的条目，在每个修补周期后有一个**结局**，由代码判定，不读执行方的话，也不靠名字映射：
- `fixed`：条目的检查通过；
- `touched`：检查未通过，但该检查的输出与上一周期不同（程序在这条输入上的行为变了）；
- `untouched`：检查未通过且输出与上一周期逐字相同（程序在这条输入上没变）。

修订说明（2026-10-25 晚，依据 evidence/repair-outcome-2026-10-25）：初稿用"diff 是否碰到命令锚点"定义 touched。离线一算，锚点名与对象名几乎对不上（310 条里 160 条映射不到），要靠去词尾的启发式才能算。输出比对是现成的、可观察的、不需要任何映射，所以改用它。现行停送规则其实已经按"输出摘要未变"判，错的不是检测，是把"未变"当成"试过无进展"去停送。

离线基线（输出口径，四次运行 310 条送出；no_check 20、build_failed 15 单列）：有结局的 275 条里 fixed 47%、touched 2%、**untouched 51%**；141 条 untouched 里 120 条被"无进展"停送。与 stem 映射口径轮末一致率 91%，分歧的两类正是预期的：派发改了但该检查输出没变（输出口径判 untouched）、共用函数改动带动输出（判 touched）。

### 4.2 机制

- **停送只对 touched**：touched 连续两个周期仍不 fixed → 停送，连同其检查送审查员问题通道裁决（审查验收模式里现成的通道，不新开路径）。untouched 不停送：每周期把全部 untouched 合成**一条单独的修补消息**，与 touched、新条目分开；同一条目一轮内最多送两次（首发 + 一次单独重发），仍 untouched 则带入下一轮。周期上限不变（3），成本上界只多这一条消息。（失败类：送到了没碰；证据 repair-outcome：输出口径 120 条 untouched 被停送。现行规则恰好反了：Sends.plan 对输出未变的 hold、对变了的照送，即停的全是 untouched、touched 从不停。）
- **回退与结局的合并**：被回退的周期结局记为 `reverted`，不算 untouched，不推进 touched 计数；"回退后重发一次"保留；同一条目第二次被回退时不再静默 hold，把挂掉的守卫与条目一起送审查员裁决"守卫与条目冲突"。（证据：rep1j R5 两次回退后条目停送，若当时把 G57 与条目一起送裁决，方向错误在 R5 即暴露。）
- **跨轮停送同样改**：ledger 的 expired/quiet（"no progress over rounds"）现按输出未变停，改为按 touched 计。
- **消息条目上限：不设。** 初稿提议每消息 ≤ 6 条；离线分组显示 1–5 条消息的 untouched 占比（43%）并不低于 11 条以上（33%），"大消息导致没碰"不成立，撤回。
- **排序**：本轮新命令的条目先于带入条目。依据只有 rep1l R2 一例（执行方首次交付收尾做的全是 R1 带入条目），标为假设，下一次真实运行看。
- **周期预算按条目算**：轮结束条件 = 全部 fixed，或剩余全部为 touched 且已裁决，或周期上限。untouched 带入下一轮任务区顶部（现在带入条目放在工单末尾），标 "untouched since R{n}"，n = 首次送出且此后输出一直未变的那轮。
- 单独消息要求执行方**逐条作答** done / not done / disagree，只用于**路由**：disagree，或答 done 但检查仍挂 → 连检查送审查员问题通道；事实仍是检查结果。（依据 carry.md：带入下一轮大工作消息的 untouched 条目 55% 仍 untouched，重发必须单独且要求作答。）
- **预注册停止条件**：下一次真实运行中，单独消息后仍 untouched 的比例 ≥ 26%（现状 52% 的一半），判为执行方档位的回避不可由消息形态改变，修补回路不再加机制。
- 环境错误（docker 不在等）终止周期而不是作为失败送执行方。（证据 rep1f。）

## 5. 守卫

守卫出生（库检查 + 审查确认）、每周期重跑、翻转按修订记录分类、改过即过期——不变。**修订（2026-10-26，依据 rep1o 与 revert-cost.md）：未改即回退改为未改即回归条目。** 修补周期里的回归不再触发整周期回退：回归成为带完整材料（守卫、绑定句、命令、输入、现在输出 vs 期望）的修补条目进下一周期；持续到下一周期仍失败的回归连守卫送审查员裁决（守卫可能错，见 G57）；轮末遗留回归保留并带入下一轮。证据：六次运行 23 次整周期回退丢掉 131 个已修好的条目（rep1o 14 次、109 条），守卫全部正确而处置过重；回退说明只给编号导致 8/14 重复打破同一守卫。新增一条：范围声明（§1.2）使所有守卫在力，不需要模型。

## 6. 删掉的

对象级关系边；对象作为交付单位；利用率验收线；formalizer 的输入声称（已删）；回放工具 strict 列（已删）；"无进展"作为停送的唯一判据。

## 7. 验证顺序（给用户的验收路径）

全部离线先行，模型运行最后：
1. **修补结局分类**（零成本）：对四次运行每条送出条目按 §4.1 判 fixed/touched/untouched，出表。这是 §4 的前提，也是"修好"层的基线。
2. **变化单元的 cue 提取**（零成本）：在 dpipe 和三个形状相反的任务（d10_w4、d12_w1、d8_w5）上只做代码侧的 cue 提取，数出 cue 单元、范围声明、作者编号；看 §1 的 cue 层能覆盖多少。
3. **G57 类守卫**（离线重放 rep1j R5）：删取反方向后 K37 不再出生为守旧行为的守卫，三次修补不被回退。
4. 开发按 §2–§4 做批，重放验收 §2.3/§3.3/§4.3 的离线项。
5. 一次 6 轮真实运行，验 §4.3 的四个量和准确率线；通过后 §12i。

## 8. 为什么这是"深"而不是"重"

每层只有一种事实、一个主人；新增机制四条（删取反方向、横切审查、修补结局、范围声明），每条对应一个有编号的失败类和一处证据；删掉的比加的多。模型只在两处做判断（归属提出修订与 model 类单元；审查员报发现），两处都可被后面的事实反驳（gold、检查、守卫）。代码不读模型文本来定事实，只读它来路由。
