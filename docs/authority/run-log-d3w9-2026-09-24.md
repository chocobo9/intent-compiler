## 6. r11f（2026-09-24 13:18–13:29）：第一次带着新计量与 A′ 规则的真实运行

**结果**：11m27s，reward 0，verifier `FAIL: repro-verify binary not found`；零派发。管理两次 propose（166s + 340s），批次 `mgmt-1` 以 `invalid_candidate` 失败。

**这次运行验证了三件事**：

1. **A′ 生效**：非传输类失败没有触发第二轮 advance——整个运行 11m27s 结束（r10 同形态是 22m39s）。适配器按照 `AdvanceResult.retryable=false` 直接收尾。
2. **`attempts[]` 让诊断一次到位**：两次尝试的原文都留档，直接看出 attempt 1（1,958 字符）与 attempt 2（610 字符）都返回 `basis.event_ids: []` + `compilation.decision: "reuse"` + 零 atoms，attempt 2 只是在 `reason` 里"叙述"了它打算怎么做。
3. **失败形态是"模型没把事件当委托"**：attempt 1 的 `checks[].sources` 引用了 `context`、`rules`、`atom_contract`、`candidate_shape`——**这些恰好是 `contract` 对象的字段名**，而请求里明明带着真实事件与能力目录（含 `/app`、`/app/docs/spec_v1.md`）。

**根因（提示词形状，不是语义）**：管理请求的 user 消息是整份 `canonicalJson(request)`；按字母序 `contract` 排在 `events` 之前，且它是最大、最像指令的一段，于是模型把契约当成了"要处理的材料"，并据此宣称"本批没有委托"。系统提示词当时只有三句话，没有说明这份 JSON 各部分的角色。

**本轮修复（2026-09-24，代码 + 测试通过）**：

- `structured-provider-transport.ts` 的系统提示词改为**逐段说明**：`events` 是本批待处理事件、其中的 `user_input.payload.text` **就是**委托；空 IR 是正常起点；`capabilities` 是宿主事实；`budget`/`contract` 只说明"怎么答"，**契约字段永远不是材料、也不是来源**；合法的 `source_id` 只可能是 `events` 里的 event id。
- `V2_COMPILER_CONTRACT.reference_contract` 同步写明这条（契约字段名、路径等一律不是来源）。
- 顺带把 §11（阶段 3）里"output/binding create 可选"的契约与示例改动一并生效。

**修复的一次性验证（不进容器、只花一次管理调用）**：用 `experiments/evocode/replay-mgmt-v2.mjs --provider dashscope --cases runtime-d3w9-r1-r11f/…/mgmt-1` 把**同一条存档请求**按新提示词重放：schema 通过；13/13 引用可解析（digest 全部由代码改写）；**机械门槛 0 issues**；产出 1 个原子 `a-repro-verify`（tools=read/write/edit/bash/glob/grep）+ 1 条 coverage；用时 28s、输出 3,235 tokens。工件在 `results/evocodebench/intent-on/replay-cases-2026-09-24T173230/`。
